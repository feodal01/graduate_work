# Настройки и запуск процессов

[← README сервиса](../README.md)

## Где задаются настройки

Docker Compose запускает процессы сервиса в отдельных контейнерах.
Переменные окружения (**env**) задают настройки, аргументы командной строки (**CLI**) —
параметры конкретного запуска. **Pydantic Settings** — библиотека чтения и проверки env.
**Батч** — ограниченная пачка записей, обрабатываемая за один проход.
**Лимитер** — общий ограничитель скорости отправки писем: хранит запас разрешений
в общем хранилище Redis, а отправитель получает разрешение перед каждым обращением к почтовому серверу.

Пример окружения — [корневой `.env.example`](../../../.env.example), передача значений
контейнерам — [compose.yaml](../../../compose.yaml). При обычном запуске скопируйте
пример в корневой `.env` и измените нужные значения. После изменения пересоздайте
соответствующие контейнеры. Короткий сценарий ревью в README читает `.env.example` явно.

Модели настроек на базе Pydantic Settings: [Settings, BatchSettings, TimingSettings, WorkerSettings](../src/notifications/config.py),
[LimiterSettings](../src/notifications/delivery/limiter_config.py).
Продуктовые параметры (флаги, интервалы, порог) обязательны: значения из примера
передаются явно. Технические размеры батчей имеют умолчания, приведённые ниже.

## Команды отдельных процессов

Python 3.12.12; зависимости закреплены в `uv.lock`. Команды ниже выполняются
из `services/notifications` в окружении установленных зависимостей (`uv run …`)
или внутри образа сервиса, с переменными соответствующего процесса.
Названия процессов и хранилищ:

| Название | Назначение |
| --- | --- |
| PostgreSQL | База локальных данных, заданий и результатов отправки |
| Kafka / consumer | Брокер событий источников / процесс, обновляющий по ним локальные данные |
| RabbitMQ | Брокер очередей заданий на отправку |
| Outbox | Таблица исходящих заданий, ожидающих передачи в RabbitMQ |
| Publisher | Процесс пересылки готовых записей outbox в RabbitMQ |
| Scheduler | Планировщик сводных писем за период (дайджестов) |
| SMTP-сервер / worker | Почтовый сервер / процесс, передающий ему готовые письма |
| API подписок | HTTP-процесс для чтения и изменения флагов рассылок пользователя |
| Campaign API | Отдельный HTTP-процесс приёма внешних кампаний — рассылок выбранным адресатам |
| Миграция | Изменение схемы таблиц PostgreSQL |
| Снимок UGC | Зафиксированные исходные счётчики лайков из сервиса комментариев и голосов |

Worker разделены по классам: `transactional` — срочные служебные письма,
`service` — несрочные уведомления, `bulk` — массовые рассылки. Для каждого класса
есть своя очередь RabbitMQ и доля разрешений лимитера.

Каждый процесс запускается отдельно:

| Процесс | Команда |
| --- | --- |
| Миграция | `alembic upgrade head` |
| Campaign API | `uvicorn notifications.campaigns.app:create_campaign_app --factory --host 0.0.0.0 --port 8000` |
| HTTP API | `uvicorn notifications.main:create_app --factory --host 0.0.0.0 --port 8000` |
| Kafka consumer | `python -m notifications --group notifications-v1` |
| Scheduler | `python -m notifications.scheduling.scheduler` |
| Publisher | `python -m notifications.delivery.publisher --poll-seconds 1` |
| SMTP worker | `python -m notifications.delivery.worker --send-class transactional --max-concurrency 2 --retry-seconds 60 --max-attempts 5` |
| Инициализация лимитера оператором | `python -m notifications.delivery.rate_limit initialize --cooldown-seconds 60` |
| Проверка состояния лимитера | `python -m notifications.delivery.rate_limit status` |
| Регистрация снимка UGC | `python -m notifications.ingest.bootstrap register --manifest manifest.json` |
| Проверка снимка UGC | `python -m notifications.ingest.bootstrap finalize --load-id initial-likes-v1` |

## Обязательные переменные по процессам

Все настройки начинаются с `NOTIFICATIONS_`. `PROCESS` и `DATABASE_URL` нужны каждому процессу; URL использует `postgresql+asyncpg://`. Миграция читает только URL.

| PROCESS | Дополнительные обязательные настройки |
| --- | --- |
| `api` | `JWT_SECRET`, `JWT_ALGORITHM` |
| `campaign-api` | `CAMPAIGN_API_KEY` |
| `consumer` | `KAFKA_BOOTSTRAP_SERVERS`, `INITIAL_LIKES`, `INITIAL_NEW_FILMS`, `INITIAL_MARKETING` |
| `scheduler` | `LIKES_MIN_DELTA`, `LIKES_INTERVAL_SECONDS`, `FILMS_INTERVAL_SECONDS`, `LIKES_BOOTSTRAP_LOAD_ID` |
| `publisher` | `RABBITMQ_URL` |
| `worker` | `RABBITMQ_URL`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, `SMTP_STARTTLS`, `FALLBACK_LOCALE`, `FALLBACK_TZ`, настройки контактов Auth ниже; `SEND_CLASS`, `MAX_CONCURRENCY`, `RETRY_SECONDS`, `MAX_ATTEMPTS` через env или CLI |
| `bootstrap` | — |

Полные имена переменных имеют префикс: например, `SMTP_HOST` в таблице означает
`NOTIFICATIONS_SMTP_HOST`. Для worker дополнительно обязательны настройки лимитера.
Начальные флаги относятся только к созданию профиля; существующий выбор пользователя
не перезаписывается. Расписание и дневное окно описаны в [README](../README.md#расписание-и-дневное-окно).

## Получение контактов из Auth

Внутренний API Auth возвращает контакты для подготовки письма по идентификаторам пользователей.
Worker передаёт сервисный ключ в `X-Service-Key`; в Kafka и локальном профиле контактов нет.
Все параметры ниже читаются Pydantic Settings; секрет не выводится в диагностике.

| Переменная | Пример / назначение |
| --- | --- |
| `NOTIFICATIONS_AUTH_CONTACTS_URL` | В Compose: `http://auth:8000/api/v1/internal/notification-contacts` |
| `NOTIFICATIONS_AUTH_CONTACTS_API_KEY` | В Compose берётся из `SERVICE_API_KEY`, общего с Auth |
| `NOTIFICATIONS_AUTH_CONTACTS_TIMEOUT_SECONDS` | `5` — таймаут HTTP-запроса |
| `NOTIFICATIONS_AUTH_CONTACTS_RETRY_SECONDS` | `60` — задержка повторной подготовки при ошибке Auth |
| `NOTIFICATIONS_AUTH_CONTACTS_BATCH_SIZE` | `100` — максимум ID в одном запросе; согласовать с `AUTH_NOTIFICATION_CONTACTS_BATCH_SIZE` |

Ошибка соединения/ответа Auth повторяет подготовку, не расходуя SMTP-попытку.
Отсутствие пользователя или email — окончательный пропуск. Уже подготовленное письмо
повторяется без нового запроса контактов. Регистрация требует `tz`; его отсутствие у
старого профиля означает окончательный пропуск дневной рассылки, а не периодическую проверку.

## Очистка завершённых писем

`notifications-maintenance` — отдельный процесс обслуживания базы. Он завершает старые
дневные задания без корректного `tz`, включая задания с будущим сроком, и удаляет
содержимое завершённых писем после срока хранения. Действующие владельцы заданий и
содержимое незавершённых SMTP-повторов не затрагиваются. Статусы, идентификаторы и
история попыток сохраняются. В Compose worker запускает maintenance как зависимость.

| Переменная | Значение примера |
| --- | --- |
| `NOTIFICATIONS_DELIVERY_PAYLOAD_RETENTION_SECONDS` | `86400` — сутки после завершения, эксплуатационный пример |
| `NOTIFICATIONS_MAINTENANCE_BATCH_SIZE` | `100` — размер обрабатываемой пачки |
| `NOTIFICATIONS_MAINTENANCE_POLL_SECONDS` | `60` — пауза между проходами |

Параметры проверяет отдельная `MaintenanceSettings`; также требуется `NOTIFICATIONS_DATABASE_URL`.
Однократный проход: `python -m notifications.maintenance --once`; без `--once` процесс
работает постоянно. Очистка `deliveries.payload` не удаляет сообщения из SMTP/Mailpit,
старую историю Kafka, резервные копии или произвольный текст заявок кампаний.

## Kafka consumer

Топик — именованный поток Kafka, разделённый на независимо читаемые партиции.
Offset — позиция сообщения в партиции. Проекция — локальные данные Notifications,
полученные из событий. Группа consumer — процессы, совместно читающие её события.

Топики: `auth.users.v1`, `ugc.reviews.v1`, `movies.films.v1`. Для изолированных проверок
есть `--auth-topic`, `--likes-topic`, `--films-topic`. Все экземпляры одной проекции
должны использовать одну группу. Offset хранится в PostgreSQL вместе с результатом
обработки, а не подтверждается отдельной транзакцией в Kafka.

## Расписание и окно отправки

**Точка отсчёта** — первая граница периода в UTC. Следующие границы получаются
прибавлением интервала; например, семь суток от понедельника 09:00 дают каждый
следующий понедельник 09:00. Дата в прошлом сохраняет устойчивое расписание,
дата в будущем откладывает первый выпуск до неё.

| Переменная `NOTIFICATIONS_…` | Начальное значение | Назначение |
| --- | --- | --- |
| `LIKES_INTERVAL_SECONDS` | 86400 в `.env.example`, обязательна | Период дайджеста лайков |
| `FILMS_INTERVAL_SECONDS` | 604800 в `.env.example`, обязательна | Период новинок |
| `FILMS_PER_DIGEST` | 20 | Максимум фильмов в новом выпуске; положительное целое. Сохраняется вместе с выпуском. Worker использует текущую настройку только для старых неподготовленных заданий без сохранённого лимита. Выбираются самые свежие по `catalog_published_at`, остальные не переносятся |
| `LIKES_SCHEDULE_ANCHOR_UTC` | `1970-01-01T00:00:00Z` | Точка отсчёта лайков |
| `FILMS_SCHEDULE_ANCHOR_UTC` | `1970-01-01T00:00:00Z` | Точка отсчёта новинок |
| `SEND_WINDOW_START` | `10:00` | Включённое начало отправки по местному времени получателя |
| `SEND_WINDOW_END` | `20:00` | Исключённый конец отправки по местному времени получателя |

Пример `.env`: лайки ежедневно в 09:30 UTC, новинки по понедельникам в 09:00 UTC,
отправка несрочных писем с 08:30 до 18:45 по времени получателя:

```dotenv
NOTIFICATIONS_LIKES_INTERVAL_SECONDS=86400
NOTIFICATIONS_LIKES_SCHEDULE_ANCHOR_UTC=1970-01-01T09:30:00Z
NOTIFICATIONS_FILMS_INTERVAL_SECONDS=604800
NOTIFICATIONS_FILMS_SCHEDULE_ANCHOR_UTC=1970-01-05T09:00:00Z
NOTIFICATIONS_SEND_WINDOW_START=08:30
NOTIFICATIONS_SEND_WINDOW_END=18:45
```

Точки требуют явно указанного UTC (`Z` или `+00:00`). Окно принимает только `HH:MM`,
начало должно быть раньше конца; ночное окно через полночь не поддерживается.
Переходы часового пояса учитываются: пропущенное время заменяется ближайшим реальным
моментом внутри окна; если окно целиком пропущено, отправка переносится на следующий день.
Повторяющийся при переводе часов час также может быть использован.
`transactional` дневным окном не ограничен.

После изменения расписания пересоздайте scheduler. После изменения окна пересоздайте
scheduler, Campaign API и все три группы worker: они должны работать с одинаковыми
границами. Compose передаёт их из корневого `.env`; CLI-дублирования этих настроек нет.
Уже созданные выпуски сохраняются. При смене точки или периода scheduler выбирает
последнюю наступившую границу нового расписания, поэтому может сразу создать выпуск.
Чтобы начать только с будущей даты, задайте будущую точку отсчёта.

Сохранённые сроки заданий автоматически не пересчитываются: расширение окна не
ускоряет уже отложенные задания. При получении задания worker проверяет новое окно
перед SMTP и при необходимости откладывает его дальше. Это правило действует и для повторов.

## SMTP: Mailpit и внешний провайдер

Mailpit — локальный SMTP-сервер из Compose: принимает письма для просмотра в браузере,
без пересылки наружу. SMTP — протокол передачи писем почтовому серверу.
STARTTLS — включение шифрования уже установленного соединения. Подключение выполняет
[`delivery/smtp.py`](../src/notifications/delivery/smtp.py): адрес/порт из Settings,
соединение, STARTTLS при включённом флаге, авторизация при заданных логине и пароле,
затем передача отправителя, получателя и письма. Успех означает подтверждение приёма сервером.

Для внешнего SMTP-провайдера задайте в корневом `.env` его `NOTIFICATIONS_SMTP_HOST`,
`NOTIFICATIONS_SMTP_PORT`, разрешённый `NOTIFICATIONS_SMTP_FROM` и
`NOTIFICATIONS_SMTP_STARTTLS=true` для STARTTLS (обычно порт 587).
Если нужна авторизация, выполните `cp infra/notifications/smtp.env.example infra/notifications/smtp.env`
и заполните **оба** поля `NOTIFICATIONS_SMTP_USERNAME` и `NOTIFICATIONS_SMTP_PASSWORD`.
Файл `smtp.env` намеренно не хранится в Git и явно исключён через `.gitignore`;
Compose читает его только при наличии. После изменения настроек пересоздайте worker-контейнеры.
Для Mailpit оставьте настройки из `.env.example` и не копируйте файл с логином и паролем.

## Параметры и масштабирование worker

`WorkerSettings` проверяет env и CLI до открытия PostgreSQL, Redis и RabbitMQ.
Явные CLI-аргументы имеют приоритет над env. У остальных процессов worker-параметры
не обязательны. Пароль SMTP хранится в типе `SecretStr`, скрывающем значение при обычном выводе
и в тексте ошибок валидации.

**Lease** — срок владения заданием одним worker. **Восстановление** — поиск
незавершённых заданий, которые снова можно обработать после истечения этого срока.
**Namespace** — префикс имён RabbitMQ для изоляции тестовых очередей и exchange;
exchange — узел RabbitMQ, направляющий сообщения в очереди.

| Переменная с префиксом `NOTIFICATIONS_` | Умолчание | Назначение |
| --- | --- | --- |
| `LEASE_SECONDS` | 120 | Срок владения заданием |
| `SMTP_TIMEOUT` | 30 | Ограничение времени SMTP-транзакции |
| `SHUTDOWN_TIMEOUT` | 45 | Ожидание активных обработок при остановке |
| `POLL_SECONDS` | 1 | Пауза цикла восстановления |
| `PREFETCH` | 10 | Число неподтверждённых сообщений RabbitMQ |
| `NAMESPACE` | Пустая строка | Изоляция тестовой топологии RabbitMQ |

`concurrency` — число параллельных обработок, `attempts` — предел SMTP-попыток,
`prefetch` — число полученных без подтверждения сообщений; все три значения —
положительные целые. Интервалы — положительные конечные числа.
Lease должен превышать таймаут SMTP. Worker читает и восстанавливает
только свой класс отправки. В production `NAMESPACE` пустой; publisher и worker
изолированной проверки должны использовать одинаковый `--namespace`.

Compose запускает `notifications-worker-transactional`, `notifications-worker-service`, `notifications-worker-bulk`. Их можно независимо масштабировать, например `docker compose up -d --scale notifications-worker-bulk=3 notifications-worker-bulk`. Число параллельных отправок группы равно числу экземпляров × concurrency, но общий лимит SMTP не растёт. Все группы используют одинаковые логин и пароль SMTP, идентификатор аккаунта `account_id` и настройки лимитера.

## Общий лимитер SMTP

### Параметры

Token bucket — запас разрешений, который пополняется с заданной скоростью.
Лимитер атомарно списывает одно разрешение общего аккаунта и одно разрешение класса;
неиспользованная доля между классами не передаётся.

Все перечисленные настройки обязательны, префикс — `NOTIFICATIONS_LIMITER_`:

| Настройка | Значение |
| --- | --- |
| `REDIS_URL` | Адрес Redis с постоянным состоянием лимитера |
| `ACCOUNT_ID` | Несекретное имя одной учётной записи SMTP-провайдера |
| `TOTAL_RATE`, `TOTAL_CAPACITY` | Общая скорость пополнения и максимальный запас |
| `TRANSACTIONAL_RATE`, `TRANSACTIONAL_CAPACITY` | Доля срочных писем |
| `SERVICE_RATE`, `SERVICE_CAPACITY` | Доля служебных дайджестов |
| `BULK_RATE`, `BULK_CAPACITY` | Доля массовых писем |
| `UNAVAILABLE_RETRY_SECONDS` | Пауза проверки при недоступном состоянии лимитера |
| `REDIS_TIMEOUT_SECONDS` | Таймаут обращения к Redis |

Rate измеряется в разрешениях в секунду, capacity — максимальный запас.
Суммы rate и capacity классов не превышают общие значения.

### Сохранность состояния Redis

Корневой `.env.example` содержит **демонстрационные** лимиты, допустимый кратковременный всплеск отправок, паузу перед пополнением
разрешений, число параллельных обработок и размеры пачек. До запуска согласовать лимиты и безопасную паузу с провайдером. AOF — журнал операций Redis на диске. Лимитер требует постоянный том данных, `appendonly yes`, `appendfsync always`, `no-appendfsync-on-rewrite no` и `maxmemory-policy noeviction`; состояние хранится в Redis hash — записи с именованными полями,
без срока автоматического удаления (TTL). Те же требования обязательны для внешнего адреса `NOTIFICATIONS_LIMITER_REDIS_URL`. Операция `fsync` сохраняет данные на диске. Redis подтверждает запись после неё; это увеличивает задержку каждого списания, но не позволяет повторно потратить подтверждённый лимит после рестарта при исправном хранилище, выполняющем fsync. Политика `everysec` для этого лимитера недопустима: она может потерять уже подтверждённое списание.

### Инициализация и восстановление

Обычный запуск worker никогда не создаёт запас. Оператор выполняет `docker compose run --rm notifications-limiter-init` отдельно; команда создаёт отсутствующий hash с нулевым запасом разрешений и начинает пополнение только после явной паузы. Повтор с совместимым исправным hash ничего не меняет. Несовместимый или повреждённый hash не сбрасывается.

Старая резервная копия может содержать уже потраченные разрешения и пройти проверку совпадения конфигурации лимитов
(её сохранённой контрольной суммы — fingerprint). Не подключать её к работающим worker как актуальный запас. При потере подтверждённых списаний остановить все группы аккаунта и выполнить операторское восстановление с нулевым запасом и безопасной паузой по [инструкции восстановления](../../../docs/diagrams/notifications-arch/ROLLOUT.md);
автоматического сброса нет. Переключение на отставшую копию Redis не обеспечивает этот контракт. [Контракт сохранения Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).

## Остановка worker

При сигналах остановки SIGTERM/SIGINT worker прекращает приём сообщений и восстановление
заданий, ждёт активные обработки до `--shutdown-timeout` (по умолчанию 45 секунд), затем отменяет оставшиеся и дожидается освобождения владения заданиями и закрытия ресурсов. Compose даёт 60 секунд (`stop_grace_period`), включая запас на закрытие ресурсов. Если внешний процесс принудительно завершит worker или SMTP прервётся по таймауту, результат остаётся неопределённым и восстанавливается через lease с риском дубликата.

## Поведение при недоступном лимитере

Недоступный Redis, отсутствующий hash или исчерпанная доля откладывают задание через PostgreSQL outbox без SMTP и без новой попытки. Только после сохранения транзакции (`COMMIT`) worker подтверждает обработку сообщения
RabbitMQ. Восстановление Redis и переход со старой очереди описаны в инструкции ниже.

Порядок восстановления Redis и смены конфигурации — в
[ROLLOUT](../../../docs/diagrams/notifications-arch/ROLLOUT.md).
