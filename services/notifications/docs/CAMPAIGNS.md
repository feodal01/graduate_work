# Campaign API

[← README сервиса](../README.md)

## Модель рассылки

**Campaign API** — отдельный HTTP-процесс Notifications для приёма внешних рассылок.
**Профиль** — локальные идентификатор, версия, часовой пояс, активность и флаги подписок пользователя. Контакты worker получает из Auth перед подготовкой письма.
**Задание (`delivery`)** — запись на отправку одного письма одному получателю.

Рассылка (`campaign`) объединяет батчи — порции заявок с постоянными UUID `campaign_id` и `batch_id`. Один получатель может входить в рассылку один раз. API сохраняет весь батч одной транзакцией и возвращает `202` после сохранения всей транзакции в базе (`COMMIT`). Принятые задания отправляются сразу с учётом срока и подписки. Для несрочных и массовых писем действует
**дневное окно** — разрешённые часы по времени получателя, настраиваемые через
`NOTIFICATIONS_SEND_WINDOW_START` / `NOTIFICATIONS_SEND_WINDOW_END`
(по умолчанию с 10:00 включительно до 20:00 исключительно); закрытие загрузки не является условием отправки.

## Запуск и доступ

Для доставки используются:

| Компонент | Назначение |
| --- | --- |
| Outbox | Таблица исходящих заданий в PostgreSQL Notifications |
| Publisher | Процесс, передающий готовые задания из outbox в брокер очередей RabbitMQ |
| Worker | Процесс, который читает очередь, готовит письмо и передаёт его почтовому SMTP-серверу |
| Класс отправки | Выбор очереди и группы worker: `transactional` для срочных, `service` для несрочных, `bulk` для массовых писем |
| Лимитер | Общий ограничитель скорости в Redis, выдающий worker разрешение перед каждой SMTP-попыткой |

Docker Compose запускает эти процессы в отдельных контейнерах. Команда включения
Campaign API из корня репозитория (использует корневой `.env`):

```sh
docker compose --profile notifications-campaigns up -d notifications-campaign-api
```

Для отправки также нужны publisher, группа worker соответствующего класса и
инициализированный лимитер. Эти процессы описаны в [README](../README.md#архитектура-и-процессы).

| Обязательная настройка | Назначение |
| --- | --- |
| `NOTIFICATIONS_PROCESS=campaign-api` | Выбор отдельного HTTP-процесса |
| `NOTIFICATIONS_DATABASE_URL` | Общая PostgreSQL Notifications |
| `NOTIFICATIONS_CAMPAIGN_API_KEY` | Непустой сервисный ключ; без него API не запускается |

Pydantic Settings читает и проверяет переменные окружения. Ключ хранится как
`SecretStr` — тип, скрывающий секрет при обычном выводе. `X-API-Key` — HTTP-заголовок
для передачи сервисного ключа. Приём батча, закрытие загрузки и чтение статуса, включая точный
повтор батча, требуют `X-API-Key`. Отсутствующий или неверный ключ даёт `401 unauthorized`.
Для отзыва замените ключ и перезапустите все экземпляры Campaign API; ранее принятые
задания продолжают работу. Ключ хранится только на backend, не передаётся браузеру;
подключение backend должно быть защищено TLS.

Сервис слушает порт 8000 внутри Compose, не публикует host port и не подключён к nginx. Обычный `notifications.main:create_app` возвращает 404 для этих маршрутов. Сервисный ключ не заменяет вход и проверку прав менеджера в вызывающем backend; JWT — подписанный токен доступа пользователя — нужен только существующему API подписок.

## Шаблоны и содержимое

**Шаблон** — файл оформления письма; **реестр** связывает его идентификатор с каналом,
классом отправки и необходимой подпиской. Начальный внешний шаблон `personal_offer`
использует канал `email`, класс `bulk` (очередь `email.bulk`) и флаг `marketing` —
разрешение рекламных предложений. Внутренние шаблоны приветствия `welcome`, дайджеста лайков `likes` и новинок `new_films` не принимаются внешним API. Реестр фиксирует класс и нужную подписку при приёме; изменение реестра не меняет уже сохранённые задания. Тема (`subject`) и основной текст (`text`) сохраняются точно, включая пробелы. HTML-шаблон получает `subject`, `text`, имя (`first_name`) и фамилию (`last_name`) из ответа Auth. Входные `subject` и `text` — обычный текст: HTML экранируется, выражения языка шаблонов Jinja не исполняются; в `text` сохраняются переносы. Worker сохраняет тело, тему, адрес и идентификатор письма Message-ID перед SMTP; повторы используют тот же снимок.

Чтобы прекратить новые заявки по шаблону, установить `external=False`. Запись реестра и HTML-файл сохранять до завершения принятых заданий: до первой подготовки worker читает текущий файл, версии шаблонов отдельно не хранятся. Удалять их можно после завершения всех заданий этого шаблона. Подтверждение точного повтора батча не требует подготовки письма по шаблону.

## Совместимость схемы при откате

Миграция — изменение схемы базы. Откат миграции `004_campaigns` → `003_delivery_send_class` удаляет историю рассылок, включая кампании только с пропущенными получателями. Старые задания внутренних уведомлений сохраняются; наличие заданий внешних кампаний
блокирует откат схемы (downgrade). Для отката приложения сохранять текущую схему (revision 005 или более новую) и данные без downgrade, следуя [ROLLOUT](../../../docs/diagrams/notifications-arch/ROLLOUT.md).

## Формат и ограничения запроса

`campaign_id` передаётся в URL. Тело нового батча:

| Поле | Значение |
| --- | --- |
| `batch_id` | Стабильный UUID батча |
| `created_by_user_id` | UUID автора кампании, полученный backend из проверенной сессии |
| `items` | Список писем одному или нескольким получателям |
| `items[].user_id` | UUID получателя из локального профиля Auth |
| `items[].template_id` | Разрешённый внешний шаблон; сейчас `personal_offer` |
| `items[].type` | `email` |
| `items[].subject` | Готовая тема |
| `items[].text` | Готовый основной текст |
| `items[].available_at` | Необязательное время с часовым поясом, раньше которого нельзя отправлять |

| Ограничение | Значение |
| --- | --- |
| Число `items` | От 1 до `NOTIFICATIONS_CAMPAIGN_BATCH_SIZE`, по умолчанию 100 |
| `template_id` | До 64 символов |
| `subject` | До 200 символов |
| `text` | До 20000 символов |
| Всё HTTP-тело | До 1048576 байт, включая поток без Content-Length |

Пустые и состоящие только из пробелов строки запрещены. Тема — однострочная,
без управляющих символов. В subject/text запрещены NUL и непарные суррогатные
кодовые точки Unicode. Неизвестные поля, повтор `user_id` внутри батча,
каналы `sms`/`push` и время без часового пояса отклоняются.

Для `available_at` отсутствие и `null` равнозначны: обработка допускается после приёма.
Исходное значение неизменно; фактический срок может сдвигаться из-за дневного окна,
повтора после ошибки или лимита. Время сохраняется в UTC.

## Пример приёма, закрытия и статуса

`expected_batches` — ожидаемое число принятых уникальных батчей; передаётся при
закрытии загрузки. Закрытие прекращает приём новых батчей, но не останавливает отправку.

Пример для вызывающего процесса **в сети Compose**; указанный `user_id` должен уже существовать в локальной базе Notifications:

```sh
CAMPAIGN_URL=http://notifications-campaign-api:8000/api/v1/notifications/campaigns/6e965dc2-ae71-4a5c-81c1-22a1f1eab61c
curl -i -X POST "$CAMPAIGN_URL/batches" -H "X-API-Key: $NOTIFICATIONS_CAMPAIGN_API_KEY" -H 'Content-Type: application/json' -d '{
  "batch_id": "969585d5-ef65-41b2-ad79-10d7ce29e1a0",
  "created_by_user_id": "89d56b31-7784-4a33-9d87-032a0d3643be",
  "items": [{
    "user_id": "782bfc9a-7cdb-4743-a9b0-5e559e27b422",
    "template_id": "personal_offer",
    "type": "email",
    "subject": "Ваша подборка",
    "text": "Рекомендуем посмотреть фильм «Прибытие»."
  }]
}'
curl -i -X POST "$CAMPAIGN_URL/close" -H "X-API-Key: $NOTIFICATIONS_CAMPAIGN_API_KEY" -H 'Content-Type: application/json' -d '{"expected_batches":1}'
curl -sS "$CAMPAIGN_URL" -H "X-API-Key: $NOTIFICATIONS_CAMPAIGN_API_KEY"
```

## Повторы и закрытие загрузки

Ответ приёма: `202 {"campaign_id":"…","batch_id":"…","status":"accepted","item_count":1}`. Закрытие: `200 {"campaign_id":"…","intake_status":"closed"}`. Точный повтор батча подтверждается даже после закрытия, изменения подписки, запрета или удаления шаблона из реестра, без новых заданий и пересчёта сохранённого времени. Допуск шаблона, его входная схема и канал проверяются только для нового батча. Перестановка элементов меняет содержимое батча; повтор с изменённым содержимым даёт конфликт. Закрытие с тем же числом батчей также безопасно повторять. `expected_batches` — положительное целое число до 2147483647.

Описание HTTP-тела в этом разделе является контрактом для клиента: обработчик читает тело запроса по частям с ограничением размера и не публикует
его схему в OpenAPI (машиночитаемом описании API). Автоматическая генерация тела клиента
по этому описанию не поддерживается.

## Автор кампании и исторические данные

`created_by_user_id` — UUID автора, обязательный для новой кампании. Он входит в сравнение батча, сохраняется первым успешным батчем и не меняется. Автор не обязан существовать в локальной таблице получателей. Другой автор того же батча даёт `batch_content_conflict`, нового батча — `campaign_author_conflict`. Close и GET не требуют автора.

Миграция сохраняет историческим кампаниям автора `null`, не пересчитывает сохранённые контрольные суммы содержимого батчей. Их старый батч можно точно повторить без автора, но с ключом; новые батчи в такую кампанию отклоняются `campaign_author_conflict`. Закрытие и чтение статуса доступны. Для продолжения отправок создаётся новая кампания с известным автором; повторно включать уже принятых адресатов не следует.

## Ошибки API

Ошибка имеет поля `error_code` и `detail`; ошибки схемы дополнительно содержат `errors` с путём поля (`loc`), типом ошибки (`type`) и сообщением (`msg`) без сырого входа, в том числе путь `items[index].available_at` при невозможности вычислить срок доставки; отсутствующие профили — `user_ids`. Коды:

| HTTP | error_code | Значение |
| --- | --- | --- |
| 401 | `unauthorized` | Нет действующего сервисного ключа |
| 422 | `validation_error` | Невалидная схема, канал или шаблон |
| 413 | `request_too_large` | Тело запроса превышает лимит |
| 404 | `campaign_not_found` | Рассылка не найдена |
| 409 | `profile_not_ready` | Нет локального профиля; весь батч откатан, можно повторить позже |
| 409 | `batch_content_conflict` | Тот же batch_id с другим содержимым |
| 409 | `campaign_author_conflict` | Другой автор нового батча либо историческая кампания без автора |
| 409 | `recipient_conflict` | Получатель уже есть в другом батче рассылки |
| 409 | `campaign_closed` | Новый батч после закрытия |
| 409 | `batch_count_mismatch` | expected_batches не совпадает с числом сохранённых батчей |

## Статус и результаты отправки

Результаты по адресатам:

| Поле | Значение |
| --- | --- |
| `total` | Все получатели, включая пропущенных |
| `sent` | Письма, принятые SMTP-сервером |
| `failed` | Окончательные ошибки после прекращения повторов |
| `skipped` | Пропуски по профилю, подписке, отсутствию email или корректного часового пояса |
| `pending` | Все незавершённые задания, включая ожидание и повторы |
| `accepted_batches` | Число принятых батчей |
| `intake_status` | Приём новых батчей: `open` или `closed` |
| `status` | Общий результат кампании |
| `skipped_reasons`, `failed_reasons` | Число пропусков и ошибок по каждой причине |

Статус содержит `campaign_id`, `created_by_user_id` (UUID или `null` для истории), `intake_status`, `status`, `accepted_batches`, `total`, `sent`, `failed`, `skipped`, `pending`, `skipped_reasons`, `failed_reasons`. Все счётчики читаются по одному снимку PostgreSQL: `total = sent + failed + skipped + pending`. Пропущенные получатели входят в `total`; причины — `profile_deleted`, `subscription_disabled`, `invalid_timezone`, `no_email`, `contact_unavailable`. API проверяет локальный допуск; `no_email` и `contact_unavailable` появляются позднее при подготовке через Auth. Ошибка HTTP Auth не считается отсутствием контакта и повторяет подготовку. Окончательные ошибки — `smtp_permanent`, `attempts_exhausted`, `smtp_uncertain`. Последняя означает неопределённый результат: письмо могло быть принято SMTP, несмотря на отсутствие подтверждения.

Пока загрузка открыта или есть `pending`, общий статус `in_progress`. После закрытия и завершения заданий: `completed`, если отправлены все; `partially_completed`, если отправлена часть; `failed`, если отправленных нет и есть ошибки; иначе `skipped`. Например, завершённая смешанная рассылка возвращает:

```json
{
  "campaign_id": "6e965dc2-ae71-4a5c-81c1-22a1f1eab61c",
  "created_by_user_id": "89d56b31-7784-4a33-9d87-032a0d3643be",
  "intake_status": "closed",
  "status": "partially_completed",
  "accepted_batches": 2,
  "total": 6,
  "sent": 3,
  "failed": 0,
  "skipped": 3,
  "pending": 0,
  "skipped_reasons": {"profile_deleted": 1, "subscription_disabled": 1, "no_email": 1},
  "failed_reasons": {}
}
```
