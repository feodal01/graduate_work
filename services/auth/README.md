# Auth service

FastAPI-сервис пользовательской аутентификации для онлайн-кинотеатра.
Реализует регистрацию, вход по паролю и через Яндекс ID, одноразовую ротацию refresh-токенов, изменение
логина или пароля, историю входов, выход с отзывом access-токена, RBAC и
централизованную проверку доступа к фильмам.

API-слой принимает и проверяет HTTP-запросы, сервисный слой выполняет
сценарии аутентификации и авторизации, а репозитории работают с PostgreSQL.
Redis хранит refresh-сессии, отозванные access-токены, снимки эффективных
прав RBAC и состояние Token Bucket. PostgreSQL остаётся источником истины для
пользователей и ролей.

## Запуск в едином проекте

Единый проект запускается из корня репозитория. Корневой Compose применяет миграции и запускает `auth-bootstrap` до запуска API:

```bash
cp .env.example .env
docker compose up -d --build
```

| Ресурс | Внешний URL |
| --- | --- |
| Swagger UI | `http://localhost/auth/docs` |
| OpenAPI JSON | `http://localhost/auth/openapi.json` |
| Health | `http://localhost/auth/health` |
| Jaeger UI | `http://127.0.0.1:16686/` |
| Вход через Яндекс | `http://localhost/api/v1/auth/social/yandex/login?tz=Europe/Moscow` |

Корневой Compose публикует только gateway. Внутренний порт `8000` сервиса Auth не доступен с хоста.

Nginx добавляет `X-Request-Id` ко всем запросам. Auth отклоняет прямой запрос без этого заголовка с HTTP `400`.

`auth-bootstrap` создаёт начального суперпользователя или повышает существующего пользователя с тем же логином. Локальные значения заданы в корневом `.env`:

- логин: `admin`;
- пароль: `Cinema-Admin-2026!`.

Эти данные использует форма входа Django Admin.

## Локальная разработка

Для локальной разработки нужны Python 3.14, uv, PostgreSQL 16 и Redis 7. Выполните команды из `services/auth`:

```bash
cp .env.example .env
openssl rand -hex 32
```

Запишите независимые случайные значения в `JWT_SECRET` и `SERVICE_API_KEY` внутри `.env`. Задайте пароль PostgreSQL. Оба секрета должны содержать не менее 32 символов. Затем установите зависимости:

```bash
uv sync --group dev
```

Подготовьте PostgreSQL и Redis, которые доступны с хоста. Затем примените миграции и запустите Auth:

```bash
uv run alembic upgrade head
uv run --env-file .env python src/bootstrap.py
uv run uvicorn main:app --app-dir src --reload --port 8000
```

Команда `bootstrap.py` получает `AUTH_ADMIN_LOGIN`, `AUTH_ADMIN_PASSWORD` и `AUTH_ADMIN_TZ` из окружения. Параметр `--env-file .env` в примере передаёт эти значения из `services/auth/.env`; перед запуском замените пароль администратора. Интерактивная команда `uv run python src/cli.py --login Root --tz Europe/Moscow` остаётся доступной для создания другого суперпользователя.

Для локальной трассировки запустите Jaeger с OTLP/HTTP на порте `4318`. Шаблон `.env.example` включает `TRACING_ENABLED=true` и отправляет трассы на `http://127.0.0.1:4318/v1/traces`. Для запуска без Jaeger задайте `TRACING_ENABLED=false`.

Шаблон оставляет `YANDEX_OAUTH_ENABLED=false`. Реальный браузерный вход использует Nginx gateway, который добавляет обязательный `X-Request-Id`. Для отдельного развёртывания Auth нужен такой же ingress. Зарегистрируйте его точный callback в Yandex OAuth и задайте этот адрес в `YANDEX_OAUTH_REDIRECT_URI`.

## API

Все методы имеют префикс `/api/v1/auth`.
Каждый HTTP-запрос, включая healthcheck и OpenAPI, должен содержать непустой заголовок `X-Request-Id`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/signup` | Создать пользователя |
| `POST` | `/login` | Получить access/refresh пару |
| `POST` | `/refresh` | Одноразово обменять refresh на новую пару |
| `GET` | `/profile` | Получить профиль текущего пользователя |
| `PATCH` | `/profile` | Задать `new_login`, `new_password` или оба поля |
| `GET` | `/login-history` | Получить собственную историю входов |
| `POST` | `/logout` | Отозвать текущие access и refresh |
| `GET` | `/roles` | Получить роли |
| `POST` | `/roles` | Создать роль и назначить permissions |
| `PATCH` | `/roles/{role_id}` | Изменить роль |
| `DELETE` | `/roles/{role_id}` | Удалить роль |
| `POST` | `/users/{user_id}/roles` | Назначить роль пользователю |
| `DELETE` | `/users/{user_id}/roles/{role_id}` | Отобрать роль |
| `POST` | `/permissions/check` | Проверить доступ к фильму |
| `GET` | `/social/{provider_name}/login` | Начать вход через зарегистрированного OAuth-провайдера; сейчас зарегистрирован `yandex` |
| `GET` | `/social/{provider_name}/callback` | Проверить callback провайдера и вернуть пару JWT Auth |

Методы `GET /profile`, `PATCH /profile`, `/login-history` и `/logout` требуют заголовок
`Authorization: Bearer <access_token>`.

Управление ролями также требует bearer-токен пользователя с соответствующим
permission или суперпользователя. Начальная миграция RBAC создаёт:

- `admin` с `roles:manage` и `user_roles:manage`;
- `subscriber` с `films.early_access:read`.

Дополнительного суперпользователя можно создать после миграций. Пароль вводится через `getpass` и не попадает в историю команд:

```bash
uv run python src/cli.py --login Root --tz Europe/Moscow
```

### Вход через Яндекс ID

Auth работает как OAuth 2.0 клиент. Он использует Authorization Code, PKCE S256 и права `login:info login:email`. OpenID Connect, `id_token` и `openid` не используются.

#### Настройка

Задайте параметры в корневом `.env`:

```dotenv
AUTH_YANDEX_OAUTH_ENABLED=true
AUTH_YANDEX_OAUTH_CLIENT_ID=<client-id>
AUTH_YANDEX_OAUTH_CLIENT_SECRET=<client-secret>
AUTH_YANDEX_OAUTH_REDIRECT_URI=http://localhost/api/v1/auth/social/yandex/callback
```

Client secret хранится только в `.env`. Redirect URI должен посимвольно совпадать с адресом в приложении Yandex OAuth.

#### Ручная проверка

1. Создайте в Yandex OAuth приложение для авторизации пользователей с платформой «Веб-сервисы».
2. Добавьте Redirect URI `http://localhost/api/v1/auth/social/yandex/callback` и права `login:info`, `login:email`.
3. Заполните параметры выше и пересоберите `auth`.
4. Откройте `http://localhost/api/v1/auth/social/yandex/login?tz=Europe/Moscow`.
5. После callback скопируйте `access_token` из JSON и запросите профиль:

```bash
curl http://localhost/api/v1/auth/profile \
  -H 'X-Request-Id: yandex-profile-check' \
  -H 'Authorization: Bearer <access_token>'
```

#### Сценарии учётной записи

- **Первый вход через Яндекс.** Auth создаёт локального пользователя и запись `social_accounts`. Пользователь не получает роли, права суперпользователя и локальный пароль.
- **Повторный вход через тот же аккаунт Яндекса.** Auth использует существующего пользователя и сохраняет его UUID.
- **Регистрация после входа через Яндекс.** `POST /signup` с таким же логином возвращает HTTP `409`. Чтобы добавить пароль этому пользователю, передайте `new_password` в `PATCH /profile`.
- **Вход через Яндекс после обычной регистрации.** Auth не связывает аккаунты по совпадению email. Auth создаёт отдельного пользователя с техническим логином.
- **Вход по паролю.** Пока социальный пользователь не задал пароль, `POST /login` возвращает HTTP `401`.

#### Данные OAuth

Одноразовые `state` и PKCE verifier хранятся в `auth-redis` 600 секунд. Auth не хранит OAuth-токены Яндекса. Callback возвращает текущий `TokenPairResponse`.

Полный контракт и sequence diagrams находятся в [описании входа через Яндекс](../../docs/yandex-social-authentication.design.md).

### Проверка доступа к фильму

`POST /permissions/check` принимает доверенный атрибут фильма:

```json
{
  "resource": "film",
  "action": "read",
  "attributes": {"creation_date": "2025-08-15"}
}
```

Внутренний вызывающий сервис обязан передать `X-Service-Key`. Bearer-токен
зрителя опционален: фильмы без ограничения доступны анонимно. Фильм младше
трёх календарных лет требует `films.early_access:read`; ровно три года и
старше — публичный. Отсутствующая `creation_date` требует право
`films.early_access:read`. Будущая дата также требует это право. Ответ имеет
вид `{"allowed": true|false}`.

Факты фильма передаются в типизированном `FilmAccessContext`. Независимые
правила `FilmAccessRule` возвращают требуемые permissions, а
`FilmAccessPolicy` объединяет их по AND: пользователь должен иметь каждое
permission, потребованное сработавшими правилами. Сейчас подключено только
`RecentFilmAccessRule` с правилом трёх лет.

Auth принимает решение, но не выдаёт фильм и не читает Elasticsearch. Movies
API передаёт дату из документа Elasticsearch и применяет полученное решение.

### Отзыв сессий после смены пароля

После смены пароля Auth отклоняет все токены, которые сервис выдал раньше.
Проверка использует Redis и не выполняет запрос в PostgreSQL для каждого
токена.

#### Основные термины

| Термин | Значение |
| --- | --- |
| Версия сессий | Случайный UUID. В коде и в JWT поле называется `session_epoch`. |
| Токен доступа | Короткоживущий JWT для обращения к защищённым маршрутам. |
| Токен обновления | Долгоживущий JWT для получения новой пары токенов. |
| Блокировка смены пароля | Временный ключ Redis. Пока ключ существует, Auth не выдаёт новые токены и отклоняет токены пользователя. |
| Список отозванных токенов доступа | Ключи Redis для токенов доступа, которые пользователь завершил через `POST /logout`. |

Auth хранит текущую версию сессий пользователя в Redis. Auth также записывает
эту версию в каждый токен доступа и токен обновления. Поле `session_epoch`
обязательно. Токен без этого поля считается недействительным. Поэтому токены,
которые выпустила предыдущая версия Auth без `session_epoch`, перестают
работать после обновления сервиса.

#### Ключи Redis

| Ключ | Назначение | Когда удаляется |
| --- | --- | --- |
| `{auth-session:<user_id>}:epoch` | Хранит текущую версию сессий | Не удаляется автоматически |
| `{auth-session:<user_id>}:changing` | Хранит идентификатор операции смены пароля | После завершения операции или через 120 секунд |
| `{auth-session:<user_id>}:refresh:<jti>` | Подтверждает, что токен обновления действует | При обновлении, выходе или окончании срока действия токена |
| `{auth-session:<user_id>}:revoked-access:<jti>` | Помечает токен доступа как отозванный | После окончания срока действия токена |

`jti` — уникальный идентификатор токена. Фигурные скобки направляют все ключи
одного пользователя в один слот Redis Cluster. Это позволяет скриптам Lua и
транзакции выхода изменять связанные ключи атомарно.

#### Вход в систему

Локальный вход проходит в следующем порядке:

1. Auth получает идентификатор пользователя из PostgreSQL.
2. Auth получает текущую версию сессий из Redis.
3. Auth читает пользователя и проверяет хеш пароля.
4. Auth записывает успешный вход в `login_history`.
5. Auth создаёт токен доступа и токен обновления с одной версией сессий.
6. Redis сохраняет токен обновления, если версия не изменилась и блокировка
   смены пароля отсутствует.

Если смена пароля начинается между шагами 2 и 6, Redis не сохраняет токен
обновления. Auth возвращает HTTP `503` и не отдаёт пару токенов клиенту.
Вход через Яндекс ID использует такую же проверку перед выдачей токенов.

#### Проверка токенов

Auth принимает токен доступа только при выполнении всех условий:

1. Подпись, тип и срок действия токена верны.
2. Версия сессий в токене совпадает с версией в Redis.
3. Блокировка смены пароля отсутствует.
4. Идентификатор токена отсутствует в списке отозванных токенов доступа.

Для токена обновления действуют первые три условия. Redis также проверяет
существование текущего токена обновления. Затем Redis одной операцией удаляет
старый токен и сохраняет новый. Повтор той же внутренней операции с тем же
новым `jti` считается успешным. Повторное использование старого токена с
другим новым `jti` отклоняется.

Несовпадение версии отзывает токен, даже если его ключ ещё хранится в Redis.
Такой ключ остаётся недействительным и удаляется после окончания срока
действия. Проверка токенов не читает PostgreSQL.

#### Смена пароля

`PATCH /profile` выполняет следующие действия:

1. Auth проверяет новый пароль и вычисляет его хеш.
2. Redis сравнивает версию из токена доступа с текущей версией пользователя.
3. Redis атомарно устанавливает блокировку и меняет версию с V0 на V1.
4. Auth сохраняет новый хеш пароля в PostgreSQL.
5. После успешной записи Redis одной атомарной операцией меняет версию с V1
   на V2 и снимает блокировку.

Версия V1 сразу отзывает все ранее выданные токены. Версия V2 отзывает токены,
которые могли быть выданы с V1 после неожиданного истечения блокировки.
После успешной смены пароля клиент удаляет старую пару токенов и выполняет
новый вход.

| Этап | Версия | Блокировка | Состояние токенов |
| --- | --- | --- | --- |
| До смены пароля | V0 | Нет | Токены с V0 действуют |
| Запись пароля | V1 | Есть | Токены с V0 отозваны, новые сессии запрещены |
| Успешное завершение | V2 | Нет | Токены с V0 и V1 отозваны |
| Откат PostgreSQL | V1 | Нет | Токены с V0 остаются отозванными |

Смена логина не меняет версию сессий.

#### Параллельная смена пароля

Два запроса могут начать работу с версией V0. Первый запрос атомарно меняет её
на V1. Второй запрос сравнивает V0 с V1 и получает HTTP `401`. Второй запрос
не изменяет PostgreSQL. Увеличение времени блокировки не заменяет эту проверку,
потому что блокировка ограничивает длительность операции, а версия определяет
актуальность токена.

#### Ограничение времени операции

Блокировка должна существовать дольше, чем PostgreSQL может выполнять
операцию. Auth использует следующие значения по умолчанию:

| Настройка | Значение |
| --- | ---: |
| Ожидание соединения с PostgreSQL | 5 секунд |
| Ожидание соединения из пула | 10 секунд |
| Ограничение одной команды PostgreSQL | 15 секунд |
| Ограничение одного SQL-запроса | 15 секунд |
| Время жизни блокировки | 120 секунд |

Расчётное окно PostgreSQL равно `10 + 5 + 2 × 15 = 45` секундам. Auth добавляет
запас 30 секунд. Поэтому минимальное время жизни блокировки равно 75 секундам.
При меньшем значении Auth не запускается. Значение 120 секунд не означает,
что запрос ждёт две минуты. Оно задаёт только предельный срок блокировки.

Имена настроек находятся в [`.env.example`](.env.example):
`POSTGRES_CONNECT_TIMEOUT_SECONDS`, `POSTGRES_POOL_TIMEOUT_SECONDS`,
`POSTGRES_COMMAND_TIMEOUT_SECONDS`, `POSTGRES_STATEMENT_TIMEOUT_MS` и
`SESSION_PASSWORD_CHANGE_MARKER_TTL_SECONDS`.

#### Ошибки

| Ситуация | Результат |
| --- | --- |
| Redis недоступен до изменения версии | Auth возвращает HTTP `503`. PostgreSQL не изменяется. |
| Версия в токене устарела | Auth возвращает HTTP `401`. PostgreSQL не изменяется. |
| Блокировка уже установлена при совпадающей версии | Auth возвращает HTTP `503`. PostgreSQL не изменяется. |
| PostgreSQL откатывает изменение | Auth снимает блокировку по возможности. Версия V1 остаётся текущей, поэтому старые токены не работают. |
| PostgreSQL сохранил пароль, но Redis не подтвердил завершение | Auth возвращает HTTP `503`. Клиент не должен автоматически повторять запрос. |

Ошибка Redis при снятии блокировки не подменяет исходную ошибку PostgreSQL.
Если Redis недоступен при обычной проверке токена, Auth возвращает HTTP `503`.

#### Выход из системы

`POST /logout` завершает только текущую сессию. Redis удаляет переданный токен
обновления, если токен действителен и принадлежит тому же пользователю. Redis
помещает текущий токен доступа в список отозванных токенов доступа до конца
его срока действия. Версия сессий не меняется. Сессии на других устройствах
продолжают работать. Отдельного маршрута для выхода со всех устройств нет.

Последовательность показана в
[исходнике PlantUML](../../docs/diagrams/auth/sequence-authentication-as-is.puml)
и на [готовой схеме PNG](../../docs/diagrams/auth/sequence-authentication-as-is.png).

## Партиционирование истории входов

PostgreSQL хранит `login_history` в 16 фиксированных hash-секциях по `user_id`.
PostgreSQL вычисляет секцию как `hash(user_id) % 16`. Все входы одного
пользователя попадают в одну секцию. Число секций не растёт вместе с числом
пользователей.

Таблица использует составной первичный ключ `(user_id, id)` и индекс
`(user_id, logged_at DESC)`. Эта схема соответствует запросу
`GET /login-history`: запрос выбирает одного пользователя и сортирует входы от
новых к старым. PostgreSQL исключает остальные 15 секций из плана запроса.

Таблица `users` не секционируется. Она растёт медленнее истории входов. Для неё
также нужна глобальная уникальность `login`, а связи с ролями и социальными
аккаунтами используют UUID пользователя.

Другие ключи секционирования не подходят текущим запросам:

- `RANGE (logged_at)` требует фильтра по времени. Текущий запрос такого фильтра
  не содержит. Auth также не удаляет историю по сроку хранения.
- Страна и регион отсутствуют в нормализованной модели. Значение по IP может
  измениться, а распределение пользователей будет неравномерным.
- Тип устройства не хранится отдельно. Сырой `User-Agent` нестабилен и не
  используется при чтении истории.
- Возрастное ограничение относится к доступу к контенту. Оно не является
  свойством входа и отсутствует в `login_history`.
- `LIST (user_id)` создаёт отдельную секцию для каждого пользователя. При
  миллионах пользователей такая схема создаёт миллионы секций и требует DDL
  при каждой регистрации.

Корневой Compose применяет миграцию до запуска Auth. Миграция выполняет замену
таблицы в одной транзакции:

1. Блокирует исходную `login_history` от чтения и записи.
2. Создаёт новую таблицу, 16 секций и составной индекс.
3. Копирует все строки и проверяет их количество.
4. Присваивает новой таблице имя `login_history` и удаляет старую таблицу.

Ошибка на любом этапе откатывает транзакцию. Откат миграции выполняет обратную
замену. Он останавливается, если одинаковый `id` принадлежит разным
пользователям, потому что исходная таблица требует глобально уникальный `id`.

Для ручного обновления работающей среды сначала остановите Auth, затем выполните
`uv run alembic upgrade head`.

### Как работает RBAC-кэш

PostgreSQL — единственный источник истины для RBAC. В нём хранятся сами роли,
permissions и назначения ролей пользователям. Redis не хранит отдельный
справочник ролей: он сохраняет только производный результат уже выполненной
проверки прав, чтобы не собирать его заново при каждом запросе.

Основные термины:

- **роль** — именованная группа permissions в PostgreSQL;
- **назначение роли** — связь пользователя с ролью в PostgreSQL;
- **эффективные права** — объединение permissions всех ролей пользователя;
- **снимок пользователя** — вычисленные эффективные права и флаг
  `is_superuser`, сохранённые в Redis;
- **ревизия ролей** — общий UUID, обозначающий текущую версию ролевых правил;
  это не кэш ролей;
- **marker мутации** — временный Redis-ключ, запрещающий доверять снимкам,
  пока связанная SQL-операция ещё не завершена.

| Хранилище | Что хранится |
| --- | --- |
| PostgreSQL | `users`, `roles`, `permissions`, `role_permissions`, `user_roles`; исходные данные и связи RBAC |
| Redis | Снимки эффективных прав пользователей, общая ревизия ролей и временные marker-ключи |

Redis-часть механизма использует четыре вида ключей:

| Ключ | Назначение |
| --- | --- |
| `{authz}:roles-revision` | Текущая UUID-ревизия ролевых правил |
| `{authz}:roles-changing` | Глобальный marker изменения permissions или удаления роли |
| `{authz}:user-changing:<user_id>` | Marker изменения прав одного пользователя |
| `{authz}:user:<user_id>` | JSON-снимок пользователя: `is_superuser`, permissions и ревизия, при которой они были вычислены |

Снимок живёт `AUTHORIZATION_CACHE_TTL_SECONDS` секунд — по умолчанию 300.
Истечение TTL является дополнительной страховкой, но обычная инвалидация
происходит сразу после изменения прав.

#### Проверка permission

1. `AuthorizationService` просит у `RedisAuthorizationCache` снимок
   пользователя.
2. Redis одним `MGET` возвращает текущую ревизию, глобальный marker, marker
   пользователя и его снимок. Порядок этих четырёх значений сразу переводится
   в именованную структуру `_RedisAuthorizationState`.
3. Активный marker, отсутствующий снимок, повреждённый JSON или несовпадение
   ревизии снимка с текущей ревизией означают cache miss.
4. При cache hit сервис использует `is_superuser` и permissions из снимка и не
   обращается к PostgreSQL.
5. При miss сервис читает пользователя и его эффективные права из PostgreSQL,
   формирует новый снимок и пытается записать его в Redis.
6. Lua-скрипт принимает снимок, только если ревизия с начала запроса не
   изменилась и ни один marker не появился. Поэтому медленный запрос не может
   вернуть в кэш права, которые уже успели устареть.

При первом чтении отсутствующая общая ревизия создаётся через `SET NX`, после
чего `MGET` повторяется. Атомарные операции выполняются зарегистрированными
через `redis-py` Lua-скриптами (`EVALSHA` с автозагрузкой).

#### Изменение прав одного пользователя

Назначение или отзыв роли, а также повышение существующего пользователя до
суперпользователя затрагивают только одного пользователя:

1. Redis через `SET NX` создаёт `{authz}:user-changing:<user_id>` с уникальным
   token владельца и защитным TTL.
2. В PostgreSQL выполняется SQL-операция.
3. Lua-скрипт проверяет token, удаляет старый снимок пользователя и marker.
4. Следующая проверка прав получает miss и строит снимок заново из PostgreSQL.

#### Изменение ролевых правил

Изменение permissions существующей роли или удаление роли может повлиять на
множество пользователей:

1. Redis создаёт глобальный `{authz}:roles-changing`.
2. В PostgreSQL изменяется или удаляется роль.
3. После успешной SQL-операции Lua-скрипт записывает новый UUID в
   `{authz}:roles-revision` и удаляет marker.
4. Физически старые снимки остаются в Redis до TTL, но их прежняя ревизия уже
   не совпадает с текущей. Поэтому они сразу считаются cache miss.

Так один короткий ключ инвалидирует любое количество пользовательских снимков
без поиска и массового удаления. Создание ещё никому не назначенной роли и
изменение только её имени не меняют эффективные права, поэтому ревизия в этих
случаях сохраняется.

#### Если Redis недоступен

Проверка прав продолжает работать: сервис читает пользователя и permissions
непосредственно из PostgreSQL и не пытается заполнить кэш. Операция, которая
должна инвалидировать существующие снимки, ведёт себя строже: без marker-а
нельзя гарантировать немедленную инвалидацию, поэтому SQL-операция не
начинается, а API отвечает `503`.

Транзиентные ошибки PostgreSQL-чтений и идемпотентных Redis-операций
повторяются с exponential backoff в границах `BACKOFF_MAX_TRIES` и
`BACKOFF_MAX_TIME`. SQL-записи и health checks не повторяются.

## Ограничение запросов

Nginx ограничивает внешний маршрут `/api/v1/auth/*` по IP. Скорость равна `20` запросам в секунду. Burst равен `20`. Nginx отклоняет лишний запрос без задержки и возвращает HTTP `429` с `Retry-After: 1`.

Auth применяет Token Bucket после проверки HTTP-схемы и обязательных учётных данных. Один запрос расходует токен только одной политики:

| Политика | Маршруты | Identity | Rate | Capacity |
| --- | --- | --- | ---: | ---: |
| `login` | `POST /login` | Валидированный регистрозависимый login | 5 за 60 секунд | 5 |
| `signup` | `POST /signup` | Валидированный регистрозависимый login | 3 за 60 секунд | 3 |
| `refresh` | `POST /refresh` | UUID пользователя из проверенного refresh JWT | 10 за 60 секунд | 5 |
| `user` | `GET|PATCH /profile`, `GET /login-history`, `POST /logout` | UUID текущего пользователя | 60 за 60 секунд | 10 |
| `admin` | Получение и изменение ролей и назначений | UUID текущего администратора | 30 за 60 секунд | 5 |
| `service` | `POST /permissions/check` | Проверенный сервис `movies-api` | 600 за 60 секунд | 50 |

Для `POST /refresh` порядок обработки принципиален:

1. Auth проверяет подпись, срок действия и `type=refresh`, затем извлекает `user_id` из JWT. Невалидный JWT получает HTTP `401` до обращения к limiter.
2. Token Bucket использует `user_id` как identity. Все refresh-токены, последовательно выданные одному пользователю, расходуют один bucket; сам JWT ключом limiter не является.
3. Если bucket разрешает запрос, Auth атомарно заменяет старый `jti` новым в Redis и возвращает новую пару токенов. Повторное использование уже заменённого refresh-токена получает HTTP `401`.

Внешний лимит Nginx остаётся отдельным: он применяется ко всему `/api/v1/auth/*` по IP до передачи запроса в Auth.

Один зарегистрированный Lua-скрипт использует время Redis, пополняет bucket и расходует токен атомарно. Ключ имеет вид `rate-limit:<policy>:<sha256(identity)>`. Redis не хранит исходный login, UUID, JWT или сервисный ключ. Неактивный bucket удаляется по TTL.

Auth возвращает HTTP `429`, `{"detail":"Too many requests"}` и положительный `Retry-After`, если bucket пуст. Healthcheck, Swagger UI и OpenAPI не используют Token Bucket. Ошибка соединения или timeout Redis включает fail-open без backoff. Ошибка Lua не включает fail-open.

`RATE_LIMIT_ENABLED` включает механизм. Переменные `RATE_LIMIT_<POLICY>_{RATE,WINDOW_SECONDS,CAPACITY}` задают шесть политик. При отклонении или fail-open Auth записывает policy и `request_id` в лог и текущий span. Identity и Redis key не записываются.

## Трассировка

OpenTelemetry создаёт серверный спан для каждого запроса Auth. Новая корневая трасса записывается с долей `TRACING_SAMPLE_RATE`, по умолчанию `0.05`. Если запрос содержит W3C-заголовок `traceparent`, Auth наследует решение родительской трассы.

Серверный спан содержит атрибут `http.request_id`. `BatchSpanProcessor` отправляет выбранные спаны на `TRACING_OTLP_ENDPOINT` по OTLP/HTTP. Экспорт выполняется вне обработки HTTP-запроса. Поэтому недоступность Jaeger не меняет ответ Auth и не блокирует запуск сервиса.

## Проверка

Полный набор тестов использует PostgreSQL и Redis по адресам из `services/auth/.env`:

```bash
uv lock --check
uv run ruff check src tests
uv run alembic upgrade head --sql
TRACING_ENABLED=false uv run pytest -q
TRACING_ENABLED=false uv run pytest --cov=src --cov-report=term-missing
uv run python -m compileall -q src tests
```

Repository-тесты выполняются на PostgreSQL во временных схемах. Redis-тесты
проверяют настоящий Redis 7, включая session epoch, marker смены пароля,
Token Bucket, TTL, Lua-ротацию токенов, снимки RBAC, маркеры мутаций и смену
ревизии ролей.

Функциональные тесты поднимают отдельные Auth, PostgreSQL и Redis, обращаются к
API по HTTP и после прогона удаляют контейнеры вместе с временными данными:

```bash
./functional_tests/run.sh
```

Полный pytest можно выполнить в той же изолированной сети без публикации портов PostgreSQL и Redis:

```bash
cd functional_tests
docker compose --env-file functional.env -f docker-compose.yaml --profile test run --rm --build auth-tests
docker compose --env-file functional.env -f docker-compose.yaml --profile test down -v --remove-orphans
```

Описание сценариев и запуск отдельного теста приведены в

Полезные команды выполняются из корня репозитория:

```bash
docker compose down
```

## Границы текущей версии

Индивидуальные политики фильмов, биллинг, удаление пользователей,
email-подтверждение и выход со всех устройств не реализованы.
Auth не выдаёт фильмы. Movies API использует метод `/permissions/check` перед
выдачей полной карточки. Документ фильма содержит `creation_date`. Метод
принимает эту дату как доверенный атрибут для проверки доступа.

Новый пользователь обязан явно передать корректный часовой пояс IANA: `tz` в `POST /signup`, `?tz=Europe/Moscow` при начале OAuth, `--tz Europe/Moscow` для CLI или `AUTH_ADMIN_TZ` для bootstrap. В `PATCH /profile` поле можно опустить, но нельзя передать `null`, пустую строку или неизвестную зону. Существующие профили с `tz = null` доступны для чтения; повторный OAuth-вход и bootstrap не заменяют пояс существующего пользователя.

### Внутренняя проверка access-токенов

`POST /api/v1/internal/introspect` проверяет текущее состояние access-токена.
Вызывающий сервис передаёт `X-Service-Key`, `X-Request-Id` и JSON `{"token": "<access JWT>"}`.
Auth использует `AuthenticationService.authenticate_access()`: проверяет JWT,
отзыв по `jti`, актуальность `session_epoch` и маркер изменения состояния сессий.
Ответ — `{"active": true, "sub": "<user UUID>"}` либо `{"active": false}`; оба имеют
HTTP `200` и `Cache-Control: no-store`. Ошибка сервисного ключа даёт `401`, недоступность
хранилища сессий — `503`. Notifications проверяет токен на каждом GET/PATCH подписок
и преобразует `active: false` в пользовательский `401`. Это внутренний JSON-контракт.
Действует лимит `service`, но отдельный счётчик с суффиксом `:token-introspection`:
запросы подписок не расходуют квоту проверки доступа к фильмам и выдачи контактов.

### Внутренний API контактов уведомлений

`POST /api/v1/internal/notification-contacts` доступен напрямую в сети сервисов.
Публичный nginx gateway не маршрутизирует `/api/v1/internal/` и возвращает 404.
Запрос требует `X-Request-Id` и `X-Service-Key` с существующим сервисным ключом;
пользовательский JWT не требуется. Перед чтением контактов проверяются ключ и
существующий лимит запросов `service`.

Тело запроса: `{"user_ids": ["UUID"]}`. Пустой список, повторяющиеся UUID и
превышение `AUTH_NOTIFICATION_CONTACTS_BATCH_SIZE` отклоняются с HTTP 422.
Настройка задаётся через Pydantic Settings, по умолчанию 100, минимум 1.

Ответ: `{"items": [...]}` в порядке запрошенных UUID. Для существующего
пользователя элемент содержит `user_id`, `status: "active"` и nullable поля
`email`, `first_name`, `last_name`, `locale`. Для отсутствующего или физически
удалённого пользователя возвращаются только `user_id` и
`status: "unavailable"`. Отсутствие email у активного профиля обозначается
`null`; недоступность БД Auth возвращает HTTP 503 для всего запроса.

Запрос выполняет одну SQL-выборку только нужных колонок; пароль, токены и другие
поля профиля не читаются и не выдаются. Тело ответа не логируется. Wire-контракт
включён в OpenAPI Auth (`/auth/openapi.json`).

События Auth для Notifications передают только `event_id`, `event_type`, `user_id`, `user_version` и `tz`; `user.deleted` не содержит `tz`. Адрес, имя, фамилия и язык остаются в Auth. Фактическое изменение этих контактных полей увеличивает `user_version`, но новое событие создаётся только при смене `tz`. Поэтому пропуски версий в Notifications допустимы. Bootstrap передаёт текущую версию и пояс через `user.profile_updated`, сохраняя маркеры загрузки; существующие события outbox остаются неизменными.
