# Отзыв сессий при смене пароля через Redis epoch

## Цель

После успешной смены пароля все ранее выданные access- и refresh-токены
пользователя должны перестать работать. Для отзыва не нужно перечислять и
удалять каждый `refresh:*` ключ.

## Инварианты

- Каждый новый access- и refresh-JWT содержит обязательный подписанный claim
  `session_epoch` типа UUID.
- Токен принимается только тогда, когда его `session_epoch` совпадает с текущим
  epoch пользователя в Redis, marker изменения отсутствует, а access-JTI не
  находится в denylist.
- Отсутствующий epoch, активный marker и несовпадающий epoch обрабатываются
  fail-closed: access отклоняется как отозванный, refresh — как неверный.
- Смена только логина не меняет epoch и не отзывает сессии.
- Смена пароля сначала меняет epoch и блокирует выпуск сессий, затем обновляет
  PostgreSQL и при успехе ещё раз меняет epoch перед снятием marker.
- Ошибка PostgreSQL не возвращает старый epoch: сессии остаются отозванными, а
  старый пароль продолжает действовать.
- Ошибка Redis до установки marker не позволяет начать изменение пароля.

## Redis keyspace

Все ключи одного пользователя используют общий Redis Cluster hash tag:

```text
{auth-session:<user_id>}:epoch
{auth-session:<user_id>}:changing
{auth-session:<user_id>}:refresh:<refresh_jti>
{auth-session:<user_id>}:revoked-access:<access_jti>
```

Epoch — случайный UUID без TTL. Marker содержит случайный UUID владельца и
живёт 30 секунд. Валидация и хеширование нового пароля выполняются до установки
marker; внутри защищённой секции остаётся только короткое обновление PostgreSQL.

## Выпуск сессии

Обычный вход использует защищённый порядок чтения:

1. Найти UUID пользователя по логину, не загружая password hash.
2. Прочитать или создать Redis epoch при отсутствии marker.
3. Загрузить пользователя по UUID и проверить актуальные логин и password hash.
4. Выпустить пару JWT с прочитанным epoch.
5. Lua-скриптом сохранить refresh только при том же epoch и отсутствии marker.

Два чтения PostgreSQL нужны, чтобы вход со старым паролем не смог получить уже
новый epoch во время конкурентной смены пароля. Социальный вход уже подтверждён
внешним провайдером, поэтому получает текущий epoch непосредственно перед
выпуском пары и использует ту же условную запись refresh.

## Проверка токенов

Access проверяется одним зарегистрированным Lua-скриптом: epoch должен
совпадать, marker должен отсутствовать, denylist-ключ JTI не должен
существовать.

Refresh-ротация также выполняется одним Lua-скриптом. Скрипт проверяет epoch и
marker, принадлежность старого refresh пользователю и только после этого
атомарно заменяет старый JTI новым. Если смена пароля выиграла гонку, ротация не
выполняется. Если ротация была первой, последующая смена epoch всё равно делает
новую пару недействительной.

## Смена пароля

Операция повторяет marker-паттерн RBAC-кэша, но с более строгой семантикой:

1. Begin Lua устанавливает marker через `SET NX EX` и одновременно записывает
   новый случайный epoch.
2. Пока marker существует, выпуск и ротация сессий запрещены.
3. Сервис обновляет password hash в PostgreSQL.
4. Finish Lua при успехе PostgreSQL всегда публикует финальный epoch, но удаляет
   marker только при совпадении UUID владельца. Вторая смена epoch отзывает
   сессию, которая могла появиться, если marker истёк во время медленного
   UPDATE; marker более новой операции остаётся на месте.
5. При ошибке PostgreSQL finish только снимает marker: промежуточный epoch
   остаётся и прежние токены не восстанавливаются.
6. Если процесс завершился аварийно, marker истекает, но новый epoch остаётся;
   старые токены не возвращаются к жизни.

При недоступном Redis Auth возвращает `503`. При несовпадении epoch старый access
получает существующий ответ `401 Token revoked`, старый refresh —
`401 Invalid refresh token`.

## Совместимость и выкладка

`session_epoch` становится обязательным claim. JWT, выпущенные старой версией
Auth, после выкладки перестанут проходить строгий decode. Это намеренный разовый
logout всех существующих сессий.

Старые Redis-ключи `refresh:<jti>` и `revoked-access:<jti>` не сканируются и не
удаляются во время выкладки. Они недостижимы для нового keyspace и естественно
исчезают по своему TTL.

## Не входит в изменение

- отдельный endpoint «выйти со всех устройств»;
- список устройств и управление отдельными сессиями;
- сохранение текущего устройства после смены пароля;
- Redis/PostgreSQL distributed transaction;
- фоновая очистка старого Redis keyspace;
- изменение TTL access- и refresh-токенов.

## Проверка

Тесты должны доказать строгий JWT-контракт, атомарность Redis-скриптов,
fail-closed поведение, конкурентную ротацию, отзыв двух пользовательских сессий,
неизменность сессий при смене только логина, поддержку социального входа и
полный HTTP-сценарий с PostgreSQL и Redis.
