# Документация механизма RBAC-кэша

## Цель

Дать разработчику общую модель RBAC-кэша до чтения деталей реализации.
Документация должна устранять ошибочное впечатление, что Redis хранит
отдельный кэш справочника ролей.

Изменяются только README, PlantUML-диаграммы и обзорные комментарии/docstring.
Поведение сервиса, публичные интерфейсы, Redis-ключи и SQL-модель не меняются.

## Модель хранения данных

README и диаграммы явно разделят владельцев данных:

- PostgreSQL является источником истины и хранит пользователей, флаг
  суперпользователя, роли, permissions, связи ролей с permissions и назначения
  ролей пользователям;
- Redis не хранит справочник ролей;
- Redis хранит итоговый снимок прав каждого ранее проверенного пользователя;
- Redis хранит одну общую UUID-ревизию ролевых правил;
- Redis хранит временные marker-ключи пользовательских и глобальных мутаций.

## Термины

Документация вводит термины до описания алгоритма:

- **роль** — именованная группа permissions в PostgreSQL;
- **назначение роли** — связь пользователя с ролью в PostgreSQL;
- **эффективные права** — объединение permissions всех ролей пользователя;
- **снимок пользователя** — вычисленные эффективные права и
  `is_superuser`, сохранённые в Redis вместе с ревизией;
- **ревизия ролей** — UUID-версия определений ролей, а не кэш ролей;
- **marker мутации** — временная блокировка доверия к снимкам на время SQL-
  изменения.

## README

В `services/auth/README.md` появится самостоятельный раздел
`Как работает RBAC-кэш` со следующей структурой:

1. Зачем нужен кэш и почему PostgreSQL остаётся источником истины.
2. Таблица «что и где хранится» для PostgreSQL и Redis.
3. Таблица Redis-ключей:
   - `{authz}:roles-revision`;
   - `{authz}:roles-changing`;
   - `{authz}:user-changing:<user_id>`;
   - `{authz}:user:<user_id>`.
4. Пошаговая проверка прав: `MGET`, marker, hit, miss, чтение PostgreSQL,
   условная запись снимка.
5. Локальная инвалидация при назначении, отзыве роли и повышении до
   суперпользователя.
6. Глобальная инвалидация при изменении permissions роли и удалении роли.
7. Объяснение смены UUID-ревизии без массового удаления снимков.
8. Поведение при недоступности Redis.

Существующий плотный технический текст будет заменён этой структурой, чтобы не
дублировать одно и то же объяснение дважды.

## Sequence diagram

`services/auth/c4/sequence-roles.puml` получит отдельный первый сценарий
`Проверка прав через RBAC-кэш`.

Сценарий покажет:

1. `AuthorizationService` запрашивает снимок через фасад кэша.
2. Один `MGET` читает ревизию, глобальный marker, marker пользователя и JSON-
   снимок.
3. При marker, отсутствии снимка или несовпадении ревизии результат считается
   cache miss.
4. При cache hit сервис использует permissions снимка без PostgreSQL.
5. При miss сервис читает пользователя и эффективные permissions в PostgreSQL.
6. Lua условно сохраняет новый снимок только при той же ревизии и отсутствии
   marker-ключей.
7. Ошибка чтения Redis приводит к чтению PostgreSQL без заполнения кэша.

Сценарии изменения ролей и назначений сохранятся, но их подписи будут
использовать те же термины: локальная инвалидация снимка и глобальная смена
ревизии.

## C4 diagrams

### Container level

`services/auth/c4/c4-container.puml` явно покажет:

- PostgreSQL как источник истины для RBAC;
- Redis как производный cache-aside слой;
- отсутствие в Redis справочника ролей;
- направление чтения при cache miss и направление инвалидации после мутаций.

### Component level

`services/auth/c4/c4-component.puml` разделит текущий общий компонент `db` на:

- PostgreSQL repositories;
- `RedisAuthorizationCache` как фасад;
- `RedisAuthorizationSnapshotStore`;
- user mutation и role mutation components.

Связи покажут, что `AuthorizationService` читает роли через repositories,
использует фасад кэша для снимков и оборачивает SQL-мутации в соответствующий
mutation context.

## Обзорные комментарии модулей

В начало следующих файлов будут добавлены русские module docstring:

- `src/db/cache/authorization.py` — публичный фасад и граница ошибок;
- `src/db/cache/authorization_snapshot.py` — формат снимка, четыре ключа одного
  `MGET` и условная запись;
- `src/db/cache/authorization_mutations.py` — отличие локальной и глобальной
  инвалидации;
- `src/services/authorization.py` — cache-aside поток и PostgreSQL как источник
  истины.

Docstring должны быть самодостаточными, но короче README. Они объясняют роль
файла и направляют чтение к его основной части, не повторяя каждую строку кода.

### Стиль объяснения в Python-файлах

Каждый обзорный docstring строится в одном порядке:

1. Кратко определить все объекты, которые будут использованы дальше.
2. После определений отдельно и по шагам описать каждый процесс файла.
3. Не объединять изменение одного пользователя и изменение общих ролевых
   правил в один абзац.

В русском объяснении используются русские термины:

- «права» вместо `permissions`;
- «данные найдены в кэше» вместо `cache hit`;
- «данных в кэше нет или им нельзя доверять» вместо `cache miss`;
- «маркер блокировки» вместо `marker`;
- «идентификатор владельца» вместо `token`;
- «контекст изменения» вместо `mutation context`.

Точные имена классов, методов, полей, Redis-команд и ключей можно указывать в
обратных кавычках, но только после русского определения. Необъяснённые
английские термины в docstring и поясняющих комментариях не используются.

## Проверка

После изменений выполняются:

- `plantuml -checkonly c4/*.puml`;
- полный `pytest` сервиса, подтверждающий отсутствие поведенческих изменений;
- `compileall` для изменённых Python-файлов;
- Pyright и Pylint для файлов с обновлёнными docstring;
- `git diff --check`;
- ручная сверка терминов README, sequence и C4.
