# Читаемость RBAC-кэша

## Цель

Снизить когнитивную нагрузку при чтении механизма RBAC-кэша, не меняя его
поведение, Redis-ключи и правила инвалидации.

Код должен явно показывать:

- какие значения возвращает один `MGET`;
- почему кэшированный снимок можно или нельзя использовать;
- зачем вместе со снимком возвращается ревизия ролей;
- почему запись снимка выполняется только для ожидаемой ревизии;
- как пользовательские и ролевые мутации защищают кэш от устаревших данных.

## Переименования

Публичные операции фасада будут называться по предмету операции:

- `get` -> `read_snapshot`;
- `set` -> `store_snapshot`.

Результат чтения `AuthorizationCacheLookup` станет
`AuthorizationSnapshotReadResult`. Его поля:

- `cached_snapshot` — готовый снимок либо `None`, если нужно прочитать права из
  PostgreSQL;
- `roles_revision_at_read` — ревизия ролей, наблюдавшаяся при чтении Redis.
  Она передаётся при последующей записи, чтобы Lua-скрипт не сохранил уже
  устаревший снимок.

Pydantic-модель `_AuthorizationCacheEnvelope` станет
`_StoredAuthorizationSnapshot`: название будет прямо говорить, что это JSON
снимка в Redis, а не произвольная оболочка кэша.

## Результат MGET

Позиционный результат Redis не будет использоваться за пределами одного места.
Сразу после `MGET` четыре значения будут распакованы и помещены в
`_RedisAuthorizationState`:

- `roles_revision`;
- `roles_mutation_marker`;
- `user_mutation_marker`;
- `snapshot_payload`.

Так контракт порядка Redis-ключей останется виден рядом с распаковкой, а
остальной код будет обращаться только к именованным полям. Индексных обращений
`result[0]`—`result[3]` в логике чтения не останется.

## Поток чтения

`read_snapshot` будет читаться сверху вниз как последовательность проверок:

1. Получить именованное состояние Redis.
2. Убедиться, что глобальная ревизия ролей существует.
3. При активной пользовательской или ролевой мутации вернуть промах кэша.
4. При отсутствии JSON-снимка вернуть промах кэша.
5. Провалидировать JSON через `_StoredAuthorizationSnapshot`.
6. Сравнить ревизию сохранённого снимка с текущей глобальной ревизией. При
   несовпадении считать снимок устаревшим.
7. Вернуть валидный снимок.

Короткие русские комментарии объяснят причины неочевидных проверок. Очевидный
синтаксис Python и Redis комментироваться построчно не будет.

## Остальной механизм

Русские обзорные комментарии и docstring будут добавлены в:

- фасад `RedisAuthorizationCache`;
- хранилище снимков и описание Redis keyspace;
- пользовательскую и ролевую мутации;
- cache-aside поток в `AuthorizationService`.

Комментарии объяснят назначение снимка, ревизии, marker-ключей, `yield`, TTL
маркера, условного удаления маркера и глобальной инвалидации через смену
ревизии.

## Неизменяемое поведение

Рефакторинг не меняет:

- Redis-ключи и формат сохранённого JSON;
- TTL снимков и маркеров;
- атомарность Lua-скриптов;
- fallback чтения в PostgreSQL;
- запрет SQL-мутации, если marker не удалось получить;
- локальную инвалидацию при изменении ролей пользователя;
- глобальную инвалидацию при изменении состава прав роли.

## Проверка

Существующие тесты RBAC-кэша и сервиса должны пройти после последовательного
обновления публичных имён, тестовых fake-объектов и всех вызовов. Дополнительно
проверяются отсутствие старых имён, отсутствие индексных обращений к результату
`MGET`, `compileall`, Pyright, Pylint и `git diff --check`.
