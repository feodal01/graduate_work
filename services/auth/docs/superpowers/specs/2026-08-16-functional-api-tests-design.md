# Изолированные функциональные тесты Auth API

## Задача

Добавить запускаемые тесты, которые обращаются к Auth API по настоящему HTTP
и используют реальные PostgreSQL и Redis. Тесты не должны зависеть от уже
запущенного локального сервиса и не должны оставлять пользователей, роли или
ключи Redis после завершения.

## Основные сущности

- **функциональный контур** — отдельные контейнеры Auth API, PostgreSQL и Redis,
  созданные только на время тестов;
- **функциональный тест** — pytest-сценарий, который отправляет HTTP-запросы в
  запущенный контейнер Auth API без подмены зависимостей;
- **`functional.env`** — неизменяемые тестовые настройки контура. Значения в
  нём предназначены только для одноразовых локальных контейнеров;
- **`run.sh`** — единая команда, которая создаёт контур, запускает pytest и
  удаляет контур независимо от результата тестов.

Все файлы функционального контура располагаются в отдельной папке
`services/auth/functional_tests`.

## Как запускаются тесты

1. `run.sh` загружает тестовые настройки из `functional.env`.
2. Docker Compose создаёт отдельный проект с PostgreSQL, Redis и Auth API.
3. PostgreSQL и Redis хранят данные во временных файловых системах контейнеров,
   поэтому основной локальный Compose не используется.
4. Контейнер Auth API применяет Alembic-миграции, создаёт тестового
   суперпользователя и запускает Uvicorn.
5. После успешного health check `run.sh` запускает pytest. Тесты обращаются к
   опубликованному HTTP-порту контейнера.
6. После pytest `run.sh` всегда выполняет `docker compose down -v`. Контейнеры,
   сеть и все тестовые данные удаляются даже при падении теста.

## Проверяемые процессы

### Аутентификация пользователя

Функциональный тест последовательно проверяет регистрацию, конфликт повторного
логина, вход, историю входов, изменение профиля, ротацию refresh-токена, запрет
повторного использования старого refresh-токена и logout. После logout старые
access- и refresh-токены должны возвращать HTTP `401`.

### Проверка доступа к фильму

Отдельный тест проверяет обязательность `X-Service-Key`, публичный доступ к
старому фильму, запрет анонимного доступа к новому фильму и HTTP `422` при
отсутствующей дате создания.

### Управление ролями

Тестовый суперпользователь входит через публичный API, создаёт роль, изменяет
её, назначает обычному пользователю и проверяет открывшийся доступ к новому
фильму. Затем роль отзывается, доступ снова запрещается, а роль удаляется.

Для пользователей и ролей применяются уникальные имена, поэтому повторный
запуск не зависит от результатов предыдущего. Полная изоляция дополнительно
обеспечивается удалением функционального контура.

## Структура файлов

- `functional_tests/docker-compose.yaml` — изолированный стек;
- `functional_tests/functional.env` — только тестовые настройки;
- `functional_tests/conftest.py` — HTTP-клиент и чтение обязательных настроек;
- `functional_tests/test_auth_api.py` — пользовательский жизненный цикл;
- `functional_tests/test_permissions_api.py` — политика фильмов и RBAC;
- `functional_tests/run.sh` — полный запуск и гарантированная очистка;
- `functional_tests/README.md` — назначение и команды запуска.

Основной `services/auth/README.md` содержит короткую ссылку на команду запуска.

## Локальный `.env`

В существующий `services/auth/.env` добавляются случайно сгенерированные
`JWT_SECRET` и `SERVICE_API_KEY`. Этот файл не коммитится. Функциональный
контур не читает эти значения и использует собственные тестовые настройки из
`functional.env`.

## Границы изменений

Бизнес-логика, публичные маршруты и схема основной базы данных не меняются.
Функциональные тесты не заменяют существующие unit- и integration-тесты, а
добавляют проверку сборки контейнера и полного пути HTTP → сервис → хранилища.
