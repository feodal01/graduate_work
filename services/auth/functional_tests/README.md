# Функциональные тесты Auth

Функциональные тесты обращаются к сервису по настоящему HTTP и проверяют его
работу вместе с PostgreSQL и Redis. Они не подменяют зависимости и не используют
данные основного Docker Compose.

В каталоге находятся:

- `docker-compose.yaml` — отдельный стек из Auth, PostgreSQL и Redis;
- `functional.env` — несекретные настройки только этого тестового стека;
- `run.sh` — единая команда запуска и очистки окружения;
- `test_auth_api.py` — жизненный цикл пользователя и токенов;
- `test_permissions_api.py` — политика доступа к фильмам и управление ролями.

## Запуск

Из каталога `services/auth` выполните:

```bash
./functional_tests/run.sh
```

Команда последовательно:

1. Собирает образ сервиса.
2. Запускает временные PostgreSQL и Redis.
3. Применяет миграции и создаёт тестового суперпользователя.
4. Ждёт готовности сервиса.
5. Запускает тесты по HTTP.
6. Останавливает контейнеры и удаляет временные данные даже при ошибке теста.

Можно запустить отдельный файл или отдельный тест:

```bash
./functional_tests/run.sh functional_tests/test_auth_api.py
./functional_tests/run.sh functional_tests/test_permissions_api.py::test_film_policy_for_anonymous_user
```

Если нужный образ Auth уже собран, пересборку можно пропустить:

```bash
AUTH_FUNCTIONAL_SKIP_BUILD=1 ./functional_tests/run.sh
```

Этот режим не загружает образы из реестра. Обычный запуск с пересборкой остаётся
основным способом проверки текущих зависимостей и Dockerfile.

## Что проверяется

Сценарий аутентификации создаёт нового пользователя, проверяет конфликт логина,
вход, историю входов и изменение логина с паролем. После смены пароля старые
access и refresh, а также старый пароль отклоняются: новый `session_epoch` в
Redis отзывает все устройства, включая текущее. Сценарий заново входит с новым
паролем и продолжает проверять одноразовую ротацию refresh, выход и отказ для
отозванных токенов. Клиентское приложение после успешной смены пароля также
должно удалить старую пару и перейти к login.

Begin смены пароля делает Redis CAS по `session_epoch` access-токена: запрос,
который был аутентифицирован до завершившейся смены пароля, получает `401` и не
записывает новый hash. Таймауты PostgreSQL ограничивают commit/rollback раньше
120-секундного marker TTL; неверное соотношение отклоняется при старте Auth.
Проверка access и refresh по-прежнему не обращается к PostgreSQL.

JWT старой версии без обязательного `session_epoch` после выкладки больше не
принимаются. Если Redis недоступен, проверка токенов и смена пароля работают
fail-closed, а не продолжаются с устаревшим состоянием.

Сценарии авторизации сначала проверяют служебный ключ, известную и отсутствующую
дату создания фильма и правило трёх лет для анонимного пользователя. Затем суперпользователь
создаёт роль, назначает её обычному пользователю и отзывает. Повторная проверка
доступа сразу после отзыва подтверждает, что старый снимок прав в Redis больше не
используется.

`functional.env` содержит только фиксированные тестовые значения. Не используйте
их для локального или рабочего экземпляра сервиса.
