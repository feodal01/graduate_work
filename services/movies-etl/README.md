# Movies ETL

Movies ETL читает фильмы из PostgreSQL и обновляет рабочий индекс Elasticsearch.
SQLite хранит очередь ETL. PostgreSQL хранит реестр публикаций
`notifications_source.source_state`; этот реестр необходимо сохранять при переиндексации.

## Публикация карточки

`film_version` — версия данных для Notifications: название, описание, дата создания,
рейтинг и жанры с идентификаторами и названиями. Перестановка жанров версию не меняет.
`index_revision` — отдельная версия всего документа, включая актёров, режиссёров и
сценаристов. Она передаётся как внешняя версия Elasticsearch и не входит в `_source`.

1. Воркер определяет затронутые фильмы.
2. `prepare_publication(film_id, now)` блокирует подготовку одного фильма в PostgreSQL
   и повторно читает его актуальные данные. Старый снимок из очереди не используется.
3. Реестр сохраняет снимок, хеши, обе версии и даты одной транзакцией.
4. После завершения транзакции воркер отправляет снимок в Elasticsearch.
   Повторный или запоздавший запрос не перезаписывает более свежую ревизию.

`catalog_published_at` — время первой подготовки к публикации, UTC. Оно сохраняется
при сетевой ошибке, повторе и переиндексации. `catalog_updated_at` меняется только
вместе с `film_version`; при первой публикации обе даты равны. При обратном ходе часов
время следующей версии увеличивается минимум на микросекунду. Это операционные даты,
а не `creation_date` и не гарантия мгновенной видимости в поиске. Детектор должен читать
только рабочий Elasticsearch после появления документа в поиске.

При запуске ETL применяются повторяемые SQL-миграции из `catalog_events/migrations`.
Для новых миграций сохраняйте идемпотентность; подготовку миграций сериализует PostgreSQL.
Миграция Admin `0003_catalog_relation_changes` обновляет `film_work.modified` при
добавлении, изменении и удалении связи жанра, чтобы producer обнаружил изменение.

## Первый переход со старого индекса

Старый индекс использует внутренние версии Elasticsearch. Нельзя продолжать запись
нового ETL в него: числовые версии могут совпасть с новыми внешними ревизиями.
Подготовьте новый индекс, сохранив старый для проверки и отката. Описанные действия —
операторская процедура; сервис не переключает индекс и не удаляет исходные данные.

1. Остановите и дождитесь завершения старых ETL-запросов. Детектор и рассылка новинок
   должны оставаться выключенными до завершения первоначальной загрузки.
2. Установите `index.blocks.write=true` на исходном рабочем индексе и выполните его
   `_refresh`, чтобы все подтверждённые документы были видны поиску. Оставьте исходный
   индекс заблокированным до конца переноса. Укажите конкретное имя индекса, не alias.
3. Выберите постоянный UUID `load_id` и новое, ещё не существующее имя целевого индекса.
   С подключением к той же PostgreSQL, что использует ETL, выполните:

   ```bash
   uv run python -m postgres_to_es.catalog_events.legacy \
     --source-index movies-old \
     --target-index movies-publication-v1 \
     --load-id 11111111-1111-4111-8111-111111111111
   ```

   Используйте свой UUID вместо примера. После сбоя повторите с **теми же** аргументами.
   Снимок берётся только из старого рабочего Elasticsearch. Неиндексированные фильмы
   PostgreSQL не попадут в старый каталог. Новая карточка сохраняется сначала в реестре,
   затем в новом индексе. Дата первой попытки сохраняется при повторе.
4. Проверьте `captured_at` и `completed_at` в `notifications_source.legacy_catalog_loads`,
   количество и карточки в целевом индексе. `started_at` — неизменная исходная граница;
   `captured_at` обозначает полноту сохранённого снимка; `completed_at` — завершение
   записи и `_refresh` нового индекса.
5. Первоначальная загрузка Notifications (Task9) должна использовать исходный `load_id`,
   `started_at` и сохранённые карточки из `legacy_catalog_membership`, ключ
   `(load_id, film_id)`. Она создаёт состояние известных фильмов и переносит карточки без
   писем. Первоначальная загрузка Task9 выполняется отдельно от обычного детектора.
6. Согласованно настройте Movies API, ETL (`ELASTICSEARCH_INDEX`) и детектор на один новый
   рабочий индекс либо общий alias. Только после первоначальной загрузки и переключения
   возобновите обычные записи и детектор. Старый индекс сохраните. Изменения исходной
   PostgreSQL после снимка будут обработаны обычным ETL как новые версии.

При обычной последующей переиндексации сохраняйте PostgreSQL-реестр и направляйте
подготовленные ETL-документы в новый индекс: версии и даты останутся прежними.

## Запуск

Для локального процесса задайте `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`,
`SQL_HOST`, `SQL_PORT`, `ELASTICSEARCH_URL`, `ELASTICSEARCH_INDEX` и путь
`STATE_DATABASE_FILE_PATH`. Не используйте рабочий старый индекс до описанного переноса.

```bash
uv sync --group test
uv run python -m postgres_to_es
```

Docker-образ копирует SQL-миграции вместе с `postgres_to_es`. Настройка корневого Compose
и автоматическое переключение старого индекса не входят в эту миграцию.

## Проверка

Из корня репозитория:

```bash
uv run --directory services/movies-etl --group test pytest -m 'not integration' -q
docker compose -p notifications-integration -f tests/notifications/compose.yaml up -d --wait
MOVIES_PUBLICATION_INTEGRATION=1 uv run --directory services/movies-etl --group test pytest -q
uv run --directory services/movies-etl --group lint ruff check postgres_to_es tests
uv run --directory services/movies-etl --group lint mypy
```

Интеграционные тесты обнаруживают динамические порты отдельного Compose-проекта,
создают UUID-базы и индексы, затем удаляют только свои данные. Выбранный интеграционный
тест без подготовленного окружения завершается ошибкой; для автономной проверки
используйте явное исключение `-m 'not integration'`.


## События рабочего каталога

Детектор — отдельный процесс, который читает рабочий Elasticsearch и сохраняет новые
версии в PostgreSQL вместе с событиями. Relay — отдельный процесс, который отправляет
сохранённые события в Kafka и отмечает их после подтверждения брокера. HTTP не запускается.

```bash
uv run python -m postgres_to_es.catalog_events migrate
uv run python -m postgres_to_es.catalog_events detect
uv run python -m postgres_to_es.catalog_events relay
```

Для детектора обязательны `CATALOG_SCAN_INTERVAL_SECONDS`, `CATALOG_OVERLAP_SECONDS` и
`CATALOG_RECONCILE_INTERVAL_SECONDS`: период опроса, повторно проверяемое окно и период
полной сверки в секундах. Продуктовых значений по умолчанию нет. Размер страницы
`CATALOG_BATCH_SIZE` по умолчанию 500. Процесс не запускает чтение, пока в
`notifications_source.detector_state` не заполнены `bootstrap_load_id`, `baseline_at`
и `bootstrap_completed_at`. Их заполняет первоначальная загрузка; `baseline_at` означает
начало исходного снимка, а не время завершения загрузки. Не выставляйте готовность вручную
для каталога, который ещё не перенесён.

Детектор фиксирует верхнюю границу прохода. Между страницами сохраняет известные версии,
события и позицию одной транзакцией. При рестарте перечитывает незавершённое окно с начала:
PIT Elasticsearch действует только в рамках текущего прохода. Уже известные версии не
создают повторных событий. Полная сверка находит поздно видимые ID и более новые версии,
в том числе за пределами окна. Ошибка или неполный ответ ES не продвигает позицию страницы.

Relay требует `KAFKA_BOOTSTRAP_SERVERS`; `KAFKA_MOVIES_TOPIC` по умолчанию `movies.films.v1`.
Топик должен быть создан инфраструктурой заранее. Технические настройки:
`CATALOG_RELAY_BATCH_SIZE=500`, `CATALOG_RELAY_PAUSE_SECONDS=1` (после пустой пачки/ошибки),
`CATALOG_RELAY_DELIVERY_TIMEOUT_SECONDS=30`. После полной пачки relay сразу читает следующую.
Сбой после подтверждения Kafka, но до записи PostgreSQL допускает повтор с тем же
`event_id`, payload и ключом `film_id`. Каждому процессу нужна собственная PG-сессия;
её advisory lock исключает одновременных детекторов или relay в одной базе.

## Первоначальная загрузка карточек

Bootstrap — перенос исторических карточек без объявления новинок. Capture сохраняет
неизменяемый снимок; enqueue создаёт события `film.updated` из этого снимка пачками.
Версии и даты при переносе не увеличиваются. Обычный детектор включается только после
завершения всех пачек. Все команды выполняются из `services/movies-etl` с теми же
обязательными настройками PostgreSQL/Elasticsearch, что и ETL; Kafka для них не требуется.

1. На время capture выделите окно обслуживания. Не переключайте alias, не заменяйте индекс
   и не меняйте его блокировки до завершения операции и всех повторов. Остановите запуск
   новых заданий ETL, чтобы не расходовать попытки на ожидаемые ответы ES `403`.
   Capture сам ставит блокировку записи через `PUT /<index>/_block/write`: этот API ждёт
   завершения активных записей на всех шардах. Если до первого запуска индекс уже
   заблокирован внешним процессом, capture откажет: повторный add-block в ES 8.6.2
   не подтверждает ожидание записей. Владелец внешней блокировки должен при остановленном
   ETL снять её и повторить capture с тем же ID, чтобы bootstrap сам установил
   подтверждённую блокировку. Затем capture выполняет `_refresh` и сохраняет
   страницы в PostgreSQL. Нужны разрешения ES на чтение, блокировку индекса, изменение
   settings и refresh (при включённой безопасности — `read` и `manage` на рабочем индексе).
   PostgreSQL-пользователь должен иметь права на миграции и запись `notifications_source`.
2. Для каталога с уже подготовленными метаданными используйте постоянный текстовый ID:

   ```bash
   uv run python -m postgres_to_es.catalog_events bootstrap capture --load-id initial-films-v1
   uv run python -m postgres_to_es.catalog_events bootstrap status --load-id initial-films-v1
   ```

   После переноса старого индекса через `catalog_events.legacy` укажите **тот же UUID**
   `load_id`, что использовался там, а `ELASTICSEARCH_INDEX` направьте на новый целевой индекс.
   Bootstrap определяет этот перенос по `_meta.legacy_load_id` и берёт исходные
   `legacy_catalog_membership` и `started_at`. Уже появившиеся в новом индексе фильмы
   не становятся историческими; более свежие версии не подменяют замороженные карточки.
3. При сбое повторите capture с тем же ID. Частичный снимок перечитывается с начала при
   сохраняющейся блокировке; исходная граница времени и сохранённые карточки не меняются.
   На ошибке блокировка остаётся, чтобы можно было безопасно продолжить. Не снимайте её
   вручную и не удаляйте строки загрузки. Изменение UUID индекса или потеря блокировки
   приводят к отказу продолжать. Исключение: если подтверждение первой собственной
   блокировки потеряно и ни одной карточки ещё не сохранено, capture кратко снимает
   собственную блокировку и ставит её заново с ожиданием всех записей. Снимок начинается
   только после подтверждения; исходная временная граница остаётся прежней. При наличии
   хотя бы одной карточки такой повтор запрещён. Внешнее временное снятие и установка блокировки
   не отслеживаются: непрерывность окна обслуживания обеспечивает оператор.
4. После полного capture снимается только блокировка, которой владеет bootstrap.
   Существовавшая до первого запуска внешняя блокировка сохраняется; оператор снимает её
   по своему регламенту. `captured_at` подтверждает полноту снимка, `released_at` — завершение
   обработки блокировки. Запись ETL после этого можно возобновить, пока enqueue продолжается.
   Если сеть оборвалась при снятии блокировки, повторите capture до появления `released_at`.
5. Выполняйте enqueue до ненулевого `completed_at` в JSON-ответе:

   ```bash
   uv run python -m postgres_to_es.catalog_events bootstrap enqueue \
     --load-id initial-films-v1 --limit 500
   uv run python -m postgres_to_es.catalog_events bootstrap status --load-id initial-films-v1
   ```

   Одна команда enqueue выполняет одну транзакцию на пачку. Без `--limit` используется
   `CATALOG_BATCH_SIZE` (по умолчанию 500). JSON содержит `captured_count`, `enqueued_count`,
   исходную `start_boundary` и даты этапов. Даже пустой каталог требует capture и enqueue.
6. После `completed_at` запускайте detector. Его первая полная сверка найдёт новые фильмы
   и версии, появившиеся во время переноса. Relay можно запускать раньше: исторические
   `film.updated` не создают объявления новинок. Bootstrap, detector и relay используют
   существующую модель повторяемой доставки с дедупликацией событий у получателя.

В одной базе допустима одна первоначальная загрузка: новый ID после её начала отвергается.
Повтор завершённого capture/enqueue не изменяет границу, watermark или снимок. Таблицы
`catalog_bootstrap_loads` и `catalog_bootstrap_members` сохраняйте вместе с `known_films`
и реестром публикаций. Поле `enqueued_at` — постоянная отметка, независимая от очистки
outbox: после удаления отправленных событий повторный запуск не создаёт их заново.
SQL-миграция `004_catalog_bootstrap.sql` добавляется к существующим `001–003`.
