# Нотификации: требования и целевой дизайн

Решение реализует пункты 2 и 3 [задания](../task.md) с уточнениями из [considerations.md](../considerations.md). Сервис принимает события, создаёт массовые и персональные уведомления и доставляет email. Основа решения — RabbitMQ и два типа воркеров: организующий и доставляющий. Этот документ описывает целевое поведение; существующий код его пока не реализует. Порядок внедрения и проверки приведён в [плане реализации](notifications.plan.md).

## Общий механизм: с этой схемы начинать ревью

Три сценария используют один путь обработки. Сначала источник передаёт заявку по HTTP. API сохраняет её в PostgreSQL, а отдельный процесс relay публикует готовую заявку в RabbitMQ. Организующий воркер создаёт доставки по получателям; relay публикует их в очередь доставки. Доставляющий воркер получает контакт из Auth, проверяет настройки и отправляет письмо через SMTP.

![Общий механизм: мгновенные, отложенные и персонализированные уведомления](diagrams/notifications/00-overview-sequence-to-be.png)

[Открыть изображение целиком](diagrams/notifications/00-overview-sequence-to-be.png) · [Исходник PlantUML](diagrams/notifications/00-overview-sequence-to-be.puml)

На обзорной схеме API, PostgreSQL и relay объединены в одну колонку для чтения общего процесса. Это три отдельных компонента: API принимает HTTP, БД хранит состояние, relay подключается к RabbitMQ. Стрелки воркеров к этой колонке с подписью PostgreSQL означают работу с собственной БД, а не дополнительные HTTP-вызовы. Детали транзакций, подтверждений и восстановления показаны ниже в локальных схемах.

| Сценарий | Когда начинается обработка | Что делают воркеры | Подробности |
| --- | --- | --- | --- |
| Мгновенное уведомление | Сразу после приёма события, например регистрации | Organiser создаёт одну доставку; sender формирует приветствие | [01: источник](diagrams/notifications/01-auth-source-sequence-to-be.png), [02: приём](diagrams/notifications/02-ingress-sequence-to-be.png), [05: отправка](diagrams/notifications/05-sender-sequence-to-be.png) |
| Отложенное уведомление | Кампания ждёт `send_at` в БД; регулярный выпуск создаёт генератор при наступлении периода | После наступления времени выполняется обычная организация и доставка | [11: разовая отсрочка](diagrams/notifications/11-delayed-sequence-to-be.png), [07: регулярный выпуск](diagrams/notifications/07-scheduler-sequence-to-be.png) |
| Персонализированная рассылка | Сразу либо после `send_at` | Organiser определяет аудиторию; sender подставляет имя каждого получателя в общий шаблон | [04: аудитория и доставки](diagrams/notifications/04-organiser-sequence-to-be.png), [05: персонализация](diagrams/notifications/05-sender-sequence-to-be.png) |

Мгновенность и отсрочка определяют **когда** отправлять, персонализация — **как сформировать содержимое**. Поэтому персонализированная рассылка также может быть отложенной. В первой версии персонализация означает обращение по имени при общих данных кампании; индивидуальные рекомендации фильмов сюда не входят. Регулярный выпуск формирует одну подборку для всей аудитории, а не письмо на каждое изменение каталога.

## Термины

**Событие** — факт или запрос на уведомление с постоянным `event_id`. **Рассылка** (`campaign`) — общий шаблон, содержимое и аудитория. **Доставка** (`delivery`) — одно уведомление одному пользователю по одному каналу. **Попытка** (`attempt`) — отдельный цикл обработки доставки; он может завершиться до обращения к SMTP. Одна доставка может иметь несколько попыток.

**Организующий воркер** определяет получателей и создаёт доставки порциями. **Доставляющий воркер** получает контакт, проверяет разрешение на отправку, формирует письмо и обращается к почтовому серверу. **Relay** — процесс передачи сохранённых исходящих записей в HTTP API или брокер. **Генератор** создаёт периодические события.

**Outbox** — таблица исходящих записей в той же базе, где выполняется бизнес-изменение. Изменение и запись outbox коммитятся одной транзакцией. Relay передаёт запись повторно, пока получатель не подтвердит устойчивое принятие. **Идемпотентность** означает, что повторная обработка одного идентификатора не создаёт новую логическую работу.

**Publisher confirm** — подтверждение публикации брокером. **Consumer ack** — подтверждение обработки потребителем. **DLX** — обменник RabbitMQ для перенаправления отклонённых сообщений; **DLQ** — очередь, в которой такие сообщения сохраняются. **Quorum queue** — постоянная очередь с механизмом репликации; один её участник в учебном Compose не даёт отказоустойчивости при потере узла.

**Lane** — класс задач: `instant` для мгновенных, `bulk` для массовых. **Lease** — временный захват задания одним процессом; **token** отличает владельца захвата. **Generation** — номер поколения задания, который меняется при продолжении или повторной попытке. **SMTP** — протокол передачи email почтовому серверу. Формирование письма из шаблона и данных называется рендерингом.

**Вне реализации:** админка рассылок, WebSocket, сокращатель ссылок, SMS/push, API произвольного HTML, пользовательский список уведомлений, CRUD шаблонов, пользовательские повторяющиеся расписания. Разовая отсрочка сервисной кампании через `send_at` входит в реализацию. Контракт массовой кампании позволяет будущей админке использовать существующий API. Источники лайков, серии сериалов и напоминания о закладках также не входят в первую версию.

Генератор одного фиксированного расписания включён как часть подсистемы, чтобы проверить требования к периодическим событиям. Общие изменения Auth необходимы для пунктов 2–3. Существующая Kafka, UGC, ClickHouse и сервисы каталога сохраняют свои роли.

## Исходное состояние репозитория

Auth хранит пользователей в PostgreSQL. `services/auth/src/models/entity.py`, класс `User`, содержит имя и фамилию, но не основной email. `SignupRequest` в `services/auth/src/schemas/authentication.py` также не принимает email. Email внешней учётной записи хранится отдельно в `SocialAccount`.

`SQLAlchemyUserRepository.create` в `services/auth/src/repositories/users.py` сам коммитит пользователя. `SQLAlchemySocialAccountRepository._try_create` в `services/auth/src/repositories/social_accounts.py` также коммитит создание. Следовательно, запись исходящего события должна попасть именно в эти транзакции. Общую переделку всех транзакций Auth выполнять не требуется.

`require_internal_service` в `services/auth/src/dependencies.py` возвращает `movies-api` после проверки общего ключа. Для новых внутренних методов нужен отдельный ключ и идентичность нотификаций; существующий путь Movies API должен сохранить поведение.

Movies API уже предоставляет `GET /api/v1/films?sort=-imdb_rating&page_number=1&page_size=10`. Это список по рейтингу, а не новинки. Каталог не предоставляет проверенного контракта даты публикации. Поэтому первая периодическая рассылка называется **«Подборка фильмов недели»** и содержит десять фильмов по рейтингу на момент формирования. Она не обещает новизну или персональные рекомендации.

UGC хранит закладки и голоса в MongoDB. У закладки нет состояния последнего посещения списка. Наличие Kafka в проекте не означает, что UGC публикует надёжные события голосования. Эти сценарии требуют отдельного дизайна.

## Гарантии и ограничения

### Модель отказов

Обязательные проверки покрывают остановку и перезапуск любого процесса или контейнера, обрыв сети, потерю HTTP-ответа/confirm и временную недоступность PostgreSQL, Auth, RabbitMQ и SMTP при сохранности постоянных томов. После восстановления обработка продолжается.

Учебный Compose содержит один PostgreSQL нотификаций и один RabbitMQ. Потеря диска, удаление томов, повреждение данных, потеря всего узла и непрерывная доступность при таких отказах не покрываются этой конфигурацией. Требование урока «любое уведомление получено при любом падении» интерпретируется в указанной модели отказов. Для более широкой гарантии нужны резервное копирование с проверкой восстановления и отдельный проект репликации существующих баз и брокера. Перед приёмкой эту границу нужно согласовать с наставником.

### Сохранность и повторная обработка

HTTP 202 означает, что запись и обязанность дальнейшей обработки сохранены в PostgreSQL. Он не означает, что RabbitMQ или SMTP уже доступны. Повтор одного ключа с тем же содержимым возвращает прежний идентификатор; тот же ключ с другим содержимым возвращает 409. При недоступной базе API отвечает 503 и ничего не обещает. Источник сохраняет событие у себя до получения устойчивого ответа.

Одна логическая доставка существует один раз. RabbitMQ может доставлять её идентификатор повторно. Outbox, захваты и проверки состояния устраняют повторное создание работы и большинство повторных отправок, но не обеспечивают однократный внешний эффект SMTP.

Если SMTP принял письмо, а процесс упал до коммита результата, исход становится неопределённым. Приоритет первой версии — не терять отправку: после таймаута такой результат повторяется, поэтому возможно повторное письмо. Один `Message-ID` не считается гарантией подавления дублей. Более сильную гарантию можно заявлять только с провайдером, который поддерживает проверенную идемпотентность по `delivery_id` и выяснение результата.

`accepted_by_smtp` означает принятие SMTP, а не получение человеком или попадание во входящие. Подтверждения фактической доставки и возвраты писем не реализуются. В тестовом стенде Mailpit принимает и показывает письмо; реальная отправка требует отдельной конфигурации SMTP. Отсутствующий email, отказ пользователя и просроченность — учитываемые исходы, а не потерянные сообщения.

### Задержка и нагрузка

Мгновенные задачи имеют отдельные очереди организации/доставки, отдельный relay и выделенный sender. Пакет массовой рассылки — 100 получателей. Проверочный профиль: снимок 5 000 пользователей, 100 мгновенных событий за 60 с, SMTP-заглушка с общей ёмкостью 50 принятий/с; из них минимум 10/с зарезервированы мгновенной доставке. Все мгновенные письма должны быть приняты не позднее 180 с от `occurred_at`. Это целевой критерий, а не уже измеренный результат.

Время простоя внешних зависимостей в предел 180 с не включается. Возраст мгновенной очереди, ожидание outbox и лимиты SMTP наблюдаются отдельно. Бесконечная входная нагрузка не покрывается обещанием. При 50 000 незавершённых bulk-доставок или 500 незавершённых bulk-кампаний новые сервисные кампании получают 429 с `Retry-After`. Развёртывание уже принятых bulk-кампаний при заполненном бюджете ожидает освобождения места. Отдельный предел — 5 000 незавершённых instant-событий; событие сверх предела остаётся в outbox источника до повторного приёма. Эти проверки атомарны, повтор уже принятого ключа не расходует бюджет. Instant ёмкость не может быть занята bulk-очередью.

Общая SMTP-квота хранится в PostgreSQL, в `smtp_rate_windows`: максимум 50 начатых отправок за UTC-секунду, из них bulk не более 40. Все экземпляры sender атомарно получают разрешение в одной строке окна; SQL-транзакция завершается до SMTP. Значения конфигурируются под фактического провайдера. Недостаток квоты переносит задачу на следующее окно и не расходует счётчик ошибок SMTP. Настройки и срок проверяются после ожидания квоты. Это ограничение темпа, а не обещание производительности SMTP.

### Актуальность и отключение

Welcome актуален семь суток после регистрации. Выпуск недели актуален 72 часа от запланированного времени периода; сервисная кампания — не более 72 часов от `send_at`, а без него — от первого принятия. Если клиент указал меньший срок, используется он. Автоматическое продление срока не допускается. До истечения срока ошибка контакта допускает ручной повтор; после срока результат `expired`.

Перед каждой попыткой sender читает настройки. Общий выключатель блокирует и приветствия, и массовые письма. Изменение влияет на задания, которые ещё не переданы SMTP. После чтения настроек и начала SMTP существует небольшое окно гонки; уже отправленное письмо отозвать нельзя. Пропущенная по настройкам доставка не оживает автоматически после включения; повтор требует новой кампании.

Отсутствие имени даёт нейтральное обращение. В массовом режиме `generic` имя не подставляется: содержимое одинаковое, но конверт SMTP отдельный для каждого пользователя. В режиме `personalised` допускается обращение по имени. Никаких BCC-рассылок одним письмом на всю аудиторию.

## Целевой состав

Один новый пакет `services/notifications` и один Docker-образ запускаются разными командами. API принимает события, кампании и настройки. Organiser создаёт доставки. Sender формирует и отправляет письмо. Relay публикует outbox и возобновляет задачи с истёкшим захватом. Scheduler формирует один еженедельный выпуск. Это два типа **бизнес-воркеров**, а не ограничение на число процессов инфраструктурной обработки.

Новые Compose-сервисы: `notifications-db`, `rabbitmq`, `notifications-migrate`, `notifications-api`, `notifications-organiser-instant`, `notifications-organiser-bulk`, `notifications-sender-instant`, `notifications-sender-bulk`, `notifications-relay-instant`, `notifications-relay-bulk`, `notifications-scheduler`, `auth-notifications-relay`. Mailpit запускается только в профиле `notifications-test`. Relay Auth также обслуживает исходящие записи Auth; брокерные relay нотификаций работают с разделёнными классами задач.

PostgreSQL хранит бизнес-состояние. RabbitMQ переносит идентификаторы работы и класс очереди. Контакты и текст писем в сообщения брокера не попадают. Существующие Auth и Movies API используются через HTTP; прямого доступа воркеров к чужим базам нет. Исключение — исходящий outbox внутри Auth, которым управляет сам Auth.

Внутренние маршруты недоступны через публичный gateway. Поле идентификатора пользователя из тела preferences не принимается: используется проверенный `sub` токена.

Общие ответы: 401 — отсутствующие/неверные учётные данные; 403 — сервисный ключ не имеет доступа к операции; 422 — схема или версия неизвестна; 503 — недоступно обязательное хранилище. Внутренние маршруты имеют ограничение размера тела 64 КиБ, явная аудитория — до 100 UUID. `GET` состояния доставок — техническая диагностика, не личный список уведомлений.

API readiness намеренно не зависит от RabbitMQ: при его простое API сохраняет работу в outbox. Swagger и OpenAPI отключены: дополнительных неописанных HTTP-маршрутов нет. Для relay и воркеров отдельные process-health команды проверяют рабочий цикл, БД и AMQP; внешние `GET` маршруты им не добавляются. Mailpit/SMTP не определяет готовность приёма события.

### Конверты и права источников

Событие содержит `event_id: UUID`, `schema_version: 1`, `event_type`, `occurred_at` с часовым поясом, `user_id` для welcome, `payload` и `expires_at`. `source` вычисляется по ключу, а не принимается на доверии. `user.registered` разрешён только Auth. Для него шаблон `welcome/v1`, категория `welcome`, канал `email`, режим `personalised` определяются сервером. `digest.weekly` разрешён только scheduler и содержит `schedule_id`, границы периода и готовую общую подборку.

Кампания содержит `campaign_id: UUID`, `schema_version: 1`, `audience: all | user_ids`, `user_ids` при адресной аудитории, `template_id`, `template_version`, `category: newsletter`, `render_mode: generic | personalised`, `payload`, необязательный `send_at`, `expires_at`. Реестр разрешает `announcement/v1` и `weekly_digest/v1`. HTML и имя канала произвольного вида не принимаются. Прямая персональная кампания содержит один UUID; большая массовая — `all`. Разрешённые поля `announcement/v1`: `subject`, `text`, необязательная ссылка на фильм по его UUID. Ссылки строятся сервером из доверенного базового адреса и UUID, текст экранируется.

`send_at` — самое раннее время начала обработки разовой кампании. Поле можно не передавать или передать `null`: обработка начинается сразу. Ненулевое значение должно содержать часовой пояс и при первом принятии быть в будущем; сохраняется UTC. Для нового запроса требуется `send_at < expires_at <= send_at + 72 часа`; без отсрочки — `accepted_at < expires_at <= accepted_at + 72 часа`. Нарушение даёт 422. Сначала проверяется уже принятый ключ: повтор прежнего запроса возвращает 202 и после наступления времени. В хеше отсутствие `send_at` и `null` равнозначны; вычисленный `accepted_at` не подставляется в хеш. Изменение `send_at` с прежним ключом даёт 409. Перенос и отмена принятой кампании отдельным API в первую версию не входят.

Хеш нормализованного конверта включает бизнес-поля и исключает HTTP request-id. Уникальность события — `(source, event_id)`; кампании — `(source, campaign_id)`. Повтор с другим хешем даёт 409. Входные UUID — ключи источника. Внутренние ID событий и кампаний хранятся отдельно и вычисляются UUIDv5 из фиксированного namespace, источника, вида запроса и входного UUID; одинаковый UUID разных источников не сталкивается. Ответ включает исходный ключ и внутренний `job_id`; снимок Auth и доставки используют внутренний ID кампании. План не вводит автоматического удаления записей дедупликации; повтор через длительное время также не создаёт новую работу.

Принятие события атомарно создаёт `notification_events`, связанную `campaigns` и organise outbox: welcome имеет аудиторию из одного user_id, digest — all. Прямой запрос кампании создаёт `campaigns` и organise outbox без синтетического входного события. Для UUIDv5 используется namespace `76b3f290-574a-4f8a-9b0e-1cd103d2e6ad` и строка `source:kind:external_uuid`, где kind различает event, event_campaign и direct_campaign. Идентичность не зависит от версии шаблона или времени обработки.

В RabbitMQ передаётся только `{schema_version: 1, job_id, job_type, lane, generation}`. Истинное состояние и содержимое читаются из PostgreSQL. `generation` увеличивается при создании повторной задачи; устаревший конверт подтверждается без внешнего эффекта. Неизвестные и повреждённые конверты перенаправляются в DLQ.

### Auth: контакт и аудитория

Email добавляется в `User`, `SignupRequest`, `UserResponse` и `ProfileUpdateRequest`. Он необязателен для сохранения совместимости с существующими клиентами. `PATCH /api/v1/auth/profile` получает возможность менять только email и удалять его явным `null`; отсутствие поля означает «не менять». Email не становится логином, не используется для связывания аккаунтов и не обязан быть уникальным. Старые записи остаются с `null`; адрес из login автоматически не извлекается.

При первом OAuth-создании адрес копируется из профиля провайдера, если он существует, и событие создаётся в той же транзакции. Повторный вход не создаёт welcome и не перезаписывает основной email, изменённый пользователем. Связывание OAuth по email по-прежнему запрещено. Проверка владения email не входит в учебную первую версию; реальный SMTP включается только после проверки тестовой конфигурации и выбранных получателей.

Новые внутренние методы Auth получают роль `notifications` с двумя отдельными ключами и идентичностями `notifications-instant` и `notifications-bulk`. Instant имеет бюджет 600 запросов/мин и burst 20, bulk — 1 200/мин и burst 50; они не расходуют лимит Movies API или друг друга. Снимки аудитории доступны только bulk. Bulk sender собирает до десяти ID одним lookup; ожидание набора пакета не превышает 100 мс. Instant lookup не ждёт пакет. Эти пределы действуют для оговорённого проверочного профиля. Контракты:

| Метод и путь | Назначение и поведение | Вид и диаграмма |
| --- | --- | --- |
| `POST /internal/v1/recipients/lookup` | До 100 UUID; возвращает запись для каждого: `found`, `email`, `first_name`, `last_name`; 200, 422, 429, 503 | TO-BE, [03](diagrams/notifications/03-auth-recipients-sequence-to-be.png) |
| `POST /internal/v1/audiences` | `audience_id=campaign_id`; атомарно фиксирует ID всех закоммиченных пользователей в снимке одной SQL-операцией; повтор возвращает тот же снимок | TO-BE, [03](diagrams/notifications/03-auth-recipients-sequence-to-be.png) |
| `GET /internal/v1/audiences/{audience_id}/members?after=&limit=100` | Возвращает `user_ids`, `next_cursor`, `complete`; порядок по сохранённому UUID, максимум 100; 404 для неизвестного снимка, 422 для неверного курсора | TO-BE, [03](diagrams/notifications/03-auth-recipients-sequence-to-be.png) |

Снимок создаётся **при первой успешной операции Auth**, а не во время HTTP-приёма кампании. Позже зарегистрированные пользователи в него не входят. Сохраняется только ID, без контактов. Курсор — Base64URL от последнего UUID, без padding; пустой/отсутствующий after начинает обход. Следующая порция выбирает ID строго больше предыдущего в порядке UUID. Один снимок может использовать до 10 000 пользователей в учебном стенде; превышение лимита — явная блокировка кампании, а не частичная рассылка. Больше пользователей требует отдельной проверки и асинхронного построения снимков. Снимок пока не удаляется автоматически. Явные `user_ids` фиксируются в самой кампании и снимка Auth не требуют.

Изменённые интеграционные маршруты Auth: `POST /api/v1/auth/signup` и `GET /api/v1/auth/social/{provider_name}/callback` — TO-BE, [01](diagrams/notifications/01-auth-source-sequence-to-be.png); `PATCH /api/v1/auth/profile` — TO-BE, [03](diagrams/notifications/03-auth-recipients-sequence-to-be.png). Схема 01 показывает только новое сохранение и передачу события, а не повторяет существующую реализацию регистрации и OAuth. Остальные существующие маршруты Auth не меняются и не входят в описание нового сервиса. Нотификации проверяют access JWT локально, как текущий UGC: отзыв токена не действует немедленно до его истечения. Этот существующий предел нужно указать в README; контракты sessions/denylist Auth не меняются.

## Модель данных и транзакции

Таблицы нотификаций: `notification_events`, `campaigns`, `deliveries`, `delivery_attempts`, `notification_preferences`, `schedule_runs`, `outbox`, `operation_requests`, `smtp_rate_windows`, `admission_budgets`. Идентификаторы — UUID, время — UTC с часовым поясом. Колонки для поиска состояния/времени имеют индексы; JSON содержимое валидируется схемой до записи. `admission_budgets` атомарно ограничивает число активных событий, кампаний и доставок; завершение или парковка освобождает соответствующее место. `smtp_rate_windows` содержит окно, общий счётчик и счётчик bulk, без персональных данных.

`notification_events` хранит источник, ключ, хеш, тип, содержимое, срок и ссылку на кампанию. `campaigns` хранит неизменяемые шаблон/версию/содержимое, аудиторию, lane, `accepted_at`, неизменяемый `send_at`, срок, статус, курсор и состояние захвата. `deliveries` хранит кампанию, user_id, канал, generation, срок, статус, `next_attempt_at`, lease token и счётчики. Уникальный ключ — `(campaign_id, user_id, channel)`.

`delivery_attempts` хранит начало/конец, фазу `preparing | smtp_started | finished`, исход, код ошибки, lease token и номер попытки; контакт и тело письма в историю не записываются. Фаза smtp_started устойчиво записывается до сетевой отправки. `notification_preferences` хранит user_id, общий выключатель и категории. При отсутствии записи значения: `enabled=true`, `welcome=true`, `newsletter=true`. Ручная массовая рассылка также подчиняется `newsletter`.

`schedule_runs` имеет уникальный `(schedule_id, period_start)`, статус подготовки, сохранённую подборку и постоянный event_id. `outbox` содержит адрес назначения, lane, job/event ID, generation, `available_at` (время следующей допустимой публикации), захват и подтверждение передачи. Уникальный ключ передачи — `(destination, job_id, generation)`. `operation_requests` обеспечивает идемпотентность ручного повтора по `(delivery_id, retry_request_id)` и хранит итог ответа.

Auth дополнительно хранит `notification_source_outbox`, `notification_audiences`, `notification_audience_members`. Изменения User и source outbox коммитятся вместе внутри существующих операций создания. Снимок и все его участники коммитятся вместе. Взаимных внешних ключей между базами нет.

Организатор захватывает кампанию короткой транзакцией с lease 60 с и уникальным token; HTTP-запросы выполняются вне открытой транзакции. Lease продлевается каждые 15 с. Таймаут обычного HTTP — 5 с, создания снимка — 10 с, SMTP — 15 с, ожидания confirm — 5 с; health-проверки — 2 с. Для порции organiser коммитит доставки, outbox, курсор и продолжение одной транзакцией. Смена владельца проверяется token и generation. Повтор порции безопасен благодаря уникальности; нет отдельного коммита курсора без заданий. Ack исходной Rabbit-задачи происходит после сохранённого продолжения или завершения кампании.

Sender аналогично захватывает доставку и создаёт попытку короткой транзакцией. Он не держит блокировку PostgreSQL во время Auth/SMTP. Захват продлевается при работе, ограниченные таймауты клиента короче lease. Запись результата допускается только владельцу актуального token. Истёкшая попытка preparing безопасно возобновляется; smtp_started без устойчивого результата становится `uncertain` и затем повторяется согласно политике. Падение между записью smtp_started и вызовом SMTP также считается неопределённостью. Это не устраняет описанную гонку внешней отправки.

Состояния доставки: `pending`, `sending`, `retry_wait`, `uncertain`, `accepted_by_smtp`, `suppressed`, `expired`, `blocked`. `suppressed` означает пользовательский отказ; `expired` — истёкший срок; `blocked` — отсутствие контакта, ошибка шаблона, постоянная ошибка SMTP или исчерпание автоматических попыток. Причина хранится отдельно. `blocked` не объявляется доставкой; оператор может исправить причину и повторить до истечения срока. Терминальные `accepted_by_smtp`, `suppressed`, `expired` автоматически не повторяются.

Кампания с будущим `send_at` переходит `scheduled → pending → expanding → expanded`; немедленная начинается с `pending`. `scheduled` означает ожидание времени в БД и учитывается в пределе 500 активных bulk-кампаний; ошибки аудитории дают `blocked`; истёкшая до развёртывания — `expired`. `expanded` означает создание всех заданий, а не завершение отправки. Диагностика считает отдельно принятые, пропущенные, просроченные и заблокированные доставки.

## RabbitMQ и повторные попытки

Базовый образ для проекта — `rabbitmq:4.2-management`. При этапе инфраструктуры фиксируется конкретный digest этой линии, проверяется наличие нужных свойств очередей и создаётся lock-запись в Compose-комментарии. PostgreSQL — линия 16. Воспроизводимые версии Python-зависимостей фиксируются в `uv.lock`. Проект не использует новые свойства RabbitMQ, отсутствующие в проверенной линии.

Обменники `notifications.organise`, `notifications.deliver`, `notifications.dead` — durable direct. Рабочие quorum queues: `notifications.organise.instant`, `notifications.organise.bulk`, `notifications.deliver.instant`, `notifications.deliver.bulk`; dead queues имеют суффикс `.dead` для каждого направления/lane. Binding и routing key совпадают с lane. Dead очереди не имеют обратного DLX, чтобы исключить цикл.

Для рабочих очередей политика включает `dead-letter-exchange`, отдельный `dead-letter-routing-key`, `dead-letter-strategy=at-least-once`, `overflow=reject-publish`, `delivery-limit=20`; feature flags и сочетание свойств проверяются на зафиксированном образе. Нельзя считать ordinary DLX безопасным или автоматически объединять несовместимые политики. Ограничение числа сообщений не должно выталкивать старые записи. Сообщения публикуются persistent, с `mandatory`, confirm и обработкой return/nack/timeout. Любая неопределённость оставляет outbox для повтора.

Ожидаемая бизнес-ошибка сначала сохраняется в БД. Перенаправление в dead queue сохраняется в outbox, после чего рабочее сообщение подтверждается. Неизвестный конверт отклоняется `requeue=false` и проходит безопасный DLX. Эти два пути имеют разные причины, но одинаково сохраняют данные для диагностики. При недоступной dead queue исходная quorum queue удерживает работу; БД дополнительно содержит проблему.

Отложенные повторы хранятся в PostgreSQL как `next_attempt_at`, а не в TTL-очередях и не в цикле немедленных `nack/requeue`. Проверенные ошибки соединения, HTTP 429/503 и SMTP 4xx повторяются после 10 с, 60 с, 5 мин, 30 мин и 2 ч с небольшим случайным сдвигом; `Retry-After` Auth учитывается как минимальная задержка. После пяти автоматических повторов доставка остаётся `blocked`, видна оператору и допускает ручной повтор. Источник Auth и relay продолжают повторять передачу с ограниченным backoff до устойчивого принятия; их данные не отбрасываются из-за счётчика попыток.

Ошибки схемы, неизвестный шаблон и SMTP 5xx автоматически не повторяются. Недоступность БД не превращается в успешный ack: потребитель прекращает приём, восстанавливает соединение и получает неподтверждённое сообщение снова. Обычное исключение программы сохраняется как ошибка обработки, если БД доступна; повторяется ограниченно, затем паркуется.

Relay каждые 5 с выбирает готовые записи и публикует их с отдельным захватом. Каждые 30 с он также проверяет незавершённые кампании и истёкшие доставки. Если передача подтверждена, но задача не захвачена за 60 с, relay повторно публикует **ту же generation** через прежнюю запись outbox. Иначе ожидание в очереди могло бы бесконечно инвалидировать конверты. Новая generation создаётся при продолжении порции, реальной повторной попытке или восстановлении истёкшего lease. Рабочие lease не трогает; копия задания с активным владельцем подтверждается без нового внешнего эффекта. PostgreSQL остаётся источником обязанностей; статус «опубликовано» не равен «выполнено». Ручной повтор доставки из DLQ сверяется с БД и идёт через технический API; напрямую возвращать старый конверт в рабочую очередь нельзя. Заблокированная кампания возобновляется командой `python -m notifications retry-campaign --campaign-id UUID --operation-id UUID`, с теми же проверками срока, идемпотентности и атомарной записью продолжения.

## Процессы и sequence-диаграммы

Во всех изображениях **TO-BE** означает целевое поведение. Обзорная схема 00 выше связывает весь путь; ниже каждый процесс показан отдельно. Внешние сервисы представлены чёрными ящиками; их внутренние операции вынесены в собственные диаграммы. Исходник `.puml` лежит рядом с PNG под тем же именем.

### 1. Сохранение и передача события регистрации Auth

Auth сохраняет нового пользователя и событие одной транзакцией. Новый процесс передачи периодически читает непереданные события из своей БД и отправляет их по HTTP в Notifications API. Пометка «взято этим процессом» нужна, чтобы два экземпляра одновременно не обрабатывали одну запись; при падении временная пометка истекает. Именно это ранее называлось «захватить исходящую запись».

Существующие проверки остаются в схемах самого Auth: [регистрация и вход](diagrams/auth/sequence-authentication-as-is.png), [OAuth callback](diagrams/auth/auth-yandex-callback-sequence-as-is.png). Здесь показано только дополнение для нотификаций. Соединение с RabbitMQ появляется на следующем участке, внутри нотификаций, — в схеме 02. Изменение email через профиль показано отдельно в схеме 03.

![Auth: сохранение и передача события регистрации](diagrams/notifications/01-auth-source-sequence-to-be.png)

### 2. Приём события и сервисной кампании

API проверяет права источника и схему, сравнивает ключ/хеш, затем коммитит данные и outbox. В HTTP-пути нет поиска аудитории и SMTP.

![Устойчивый приём](diagrams/notifications/02-ingress-sequence-to-be.png)

### 3. Данные получателей и снимок аудитории Auth

Пользователь может обновить email через существующий профиль Auth. Организатор получает стабильный снимок ID. Sender получает актуальный контакт по ID; в сохранённую аудиторию контакт не включается.

![Auth: аудитория и контакты](diagrams/notifications/03-auth-recipients-sequence-to-be.png)

### 4. Развёртывание кампании в доставки

Курсор, новая порция доставок и следующее задание сохраняются вместе. Перезапуск продолжает кампанию, а повторный конверт не создаёт дубликаты.

![Организующий воркер](diagrams/notifications/04-organiser-sequence-to-be.png)

### 5. Персонализация и доставка

Sender получает контакт из Auth, проверяет срок и настройки перед отправкой, рендерит фиксированную версию шаблона. Результат SMTP сохраняется до ack. Отдельная ветвь показывает неопределённый результат.

![Доставляющий воркер](diagrams/notifications/05-sender-sequence-to-be.png)

### 6. Публикация, повторы и очередь ошибок

Relay не забывает неподтверждённую передачу. Ожидаемые ошибки и повреждённые конверты имеют устойчивые пути парковки; после восстановления используется тот же логический ID.

![Повторы и DLX](diagrams/notifications/06-retry-and-dlx-sequence-to-be.png)

### 7. Еженедельный выпуск и восстановление генератора

Расписание: пятница 12:00 `Europe/Moscow`. Генератор каждые 60 с определяет последний наступивший выпуск. Он сохраняет подборку один раз и передаёт событие через свой HTTP-outbox. Незавершённый актуальный выпуск возобновляется; старые пропущенные периоды отмечаются `skipped_stale`, без отправки серии старых писем. Пустой каталог даёт `skipped_empty`; недоступный каталог — повтор подготовки до срока выпуска.

При первом включении расписания начальный период — последний наступивший; выпуски за время до внедрения не создаются. После этого пропущенные периоды определяются по сохранённой истории. Каждому выпуску соответствует дата и время запуска; окно актуальности — 72 часа от этой точки. Расписание и часовой пояс первой версии не меняются через API.

![Генератор выпуска](diagrams/notifications/07-scheduler-sequence-to-be.png)

### 8. Настройки пользователя

GET возвращает явные значения по умолчанию. PATCH меняет только настройки владельца access JWT. Sender учитывает выключатель перед каждой попыткой.

![Настройки](diagrams/notifications/08-preferences-sequence-to-be.png)

### 9. Диагностика и ручной повтор

Оператор получает состояние без текста и контактов. Повтор создаёт новую generation и outbox одной транзакцией и не позволяет заново отправить успешную доставку.

![Операторский повтор](diagrams/notifications/09-operations-sequence-to-be.png)

### 10. Проверка процесса и готовности

Проверка процесса не вызывает внешние сервисы. Готовность API требует БД и реестра шаблонов, но допускает недоступность брокера благодаря outbox.

![Проверки состояния](diagrams/notifications/10-health-sequence-to-be.png)

### 11. Разовая отложенная кампания

API сохраняет кампанию со статусом `scheduled` и organise outbox с `available_at=send_at` в одной транзакции. Relay проверяет готовые записи каждые 5 с: до этого момента сообщения в RabbitMQ нет. При наступлении времени relay переводит кампанию в `pending` и публикует её через обычный механизм подтверждений. Для этого не нужен новый тип воркера, отдельный таймер на каждую кампанию или плагин задержек RabbitMQ.

После перезапуска ещё не наступившая кампания продолжает ждать. Если время наступило и срок не истёк, она публикуется с прежним ID; если срок истёк — получает `expired` без отправки. Reconciliation не публикует задание раньше `send_at`; organiser проверяет эту границу повторно. Преждевременный конверт приводит к сохранению ожидания до `send_at` и ack после COMMIT, без создания доставок. Ручной повтор также не обходит время и срок. Источник времени для проверок — PostgreSQL UTC.

`send_at` — нижняя граница, а не гарантия доставки в точную секунду; после неё возможны ожидание очереди и повторы. Предел 180 с относится к instant, а отложенные сервисные кампании идут по bulk. Для `all` снимок создаётся при первой успешной операции Auth после наступления `send_at`; указанные явно ID фиксируются при приёме. Контакты и настройки читаются при отправке. `generic` и `personalised` поддерживают одинаковую отсрочку. Генератор регулярного выпуска из схемы 07 сам создаёт событие при наступлении периода и не требует `send_at` в событийном контракте.

![Отложенная кампания: ожидание и публикация](diagrams/notifications/11-delayed-sequence-to-be.png)

## Единые шаблоны и безопасность

Файлы `welcome/v1`, `announcement/v1`, `weekly_digest/v1` содержат тему, plain text и HTML. Реестр фиксирует разрешённые поля и режимы. Jinja2 формирует HTML с экранированием; отсутствие обязательной переменной даёт ошибку шаблона, а не пустое письмо. Уже использованная версия не меняется: новое содержимое получает новую версию, а образ во время обновления сохраняет старые версии до завершения их заданий. Принимающая версия API и все sender используют один реестр из образа.

API пользователя проверяет подпись JWT, алгоритм HS256, обязательные `sub/jti/type/iat/exp`, `type=access` и срок. Внутренние права задаются по ключам `auth`, `scheduler`, `campaign-client`, `operator`; клиент не может объявить себя другим источником. В Auth существующий ключ Movies API сохраняется, новый ключ нотификаций проверяется отдельно. Публичный gateway блокирует `/internal/` и `/health/` до общих прокси-правил; снаружи доступны только preferences. SMTP и Management UI публикуются только на localhost для учебного стенда.

Секреты хранятся в переменных окружения; примеры содержат только фиктивные значения. Логи содержат event/campaign/delivery/request ID, lane, код ошибки и задержку; email, ФИО, JWT, сервисные ключи и тело письма не логируются. Готовый текст существует только в памяти sender и на стороне SMTP. Содержимое рассылки в БД доступно только сервису и не отдаётся техническим статусным API.

## Наблюдение и приёмка

Структурированные логи новых процессов передаются существующим механизмом Logstash; ошибки — через действующую конфигурацию Sentry. При выключенном внешнем сборщике обработка не прекращается. Обязательные показатели: возраст oldest pending instant/outbox, число pending/retry/blocked/uncertain, длительность Auth/SMTP, количество дублей конвертов, прогресс кампании и генератора. Команда `inspect` выводит агрегаты без контактов; отдельная система мониторинга не обязательна.

Приёмка включает: письмо регистрации; одинаковую кампанию; персональную кампанию; выпуск недели; настройку/отключение; повтор event ID и конфликт хеша; восстановление Auth/API/organiser/sender/relay/scheduler; недоступную DLQ; потерянный confirm; обрыв после SMTP; параллельные организаторы; задержку instant на фоне bulk. Проверяются реальные PostgreSQL и RabbitMQ, а SMTP принимает Mailpit. Детальная последовательность, имена тестов и команды находятся в плане.

## Основания для решений

Правила подтверждений и безопасного перенаправления проверены по текущей официальной документации: [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms), [DLX safety](https://www.rabbitmq.com/docs/dlx#safety), [quorum queues](https://www.rabbitmq.com/docs/quorum-queues#activating-at-least-once-dead-lettering). Пределы SMTP описаны в [RFC 5321](https://www.rfc-editor.org/rfc/rfc5321). Конкретные свойства выбранного образа дополнительно проверяются до реализации на этапе инфраструктуры.
