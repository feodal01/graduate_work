# Ограничение количества запросов к Auth

## Область решения

Ограничение работает на двух уровнях.

Nginx ограничивает внешний поток запросов по IP-адресу. Auth применяет точные правила по логину, пользователю или внутреннему сервису. Admin и Movies API обращаются к Auth напрямую, поэтому правила Auth не зависят от прохождения запроса через Nginx.

Rate limiter является компонентом Auth. Он использует существующий `auth-redis`. Отдельный микросервис, отдельный Redis и новая фоновая задача не добавляются.

## Поток запроса

```text
Внешний клиент
    │
    ▼
Nginx: Leaky Bucket по IP
    │
    ▼
Auth: выбор политики и идентификатора
    │
    ▼
Token Bucket в auth-redis
    ├── токен доступен ──► обработчик Auth
    ├── токена нет ──────► HTTP 429
    └── Redis недоступен ─► обработчик Auth и запись ошибки

Admin ────────────► Auth: Token Bucket
Movies API ───────► Auth: Token Bucket
```

## Алгоритмы

Nginx использует встроенный Leaky Bucket. Для зоны Auth задаются `rate=20r/s`, `burst=20` и `nodelay`. Nginx не задерживает лишние запросы. Он возвращает HTTP `429`.

Auth использует Token Bucket с непрерывным пополнением. Политика содержит:

- `rate` — количество токенов за период;
- `window_seconds` — длину периода;
- `capacity` — максимальное количество токенов;
- стоимость одного запроса — один токен.

Redis хранит `tokens` и `last_refill` в Hash. Lua-скрипт получает время через Redis `TIME`, пополняет bucket, списывает токен и вычисляет время до следующего токена. Весь переход состояния выполняется атомарно.

Компонент использует `redis.register_script()`. Он не вызывает сырой `EVAL` для каждого запроса. Ключ получает TTL, достаточный для полного восстановления bucket. Неактивные ключи удаляются автоматически.

## Политики Auth

| Политика | Маршруты | Идентификатор | Rate | Capacity |
| --- | --- | --- | ---: | ---: |
| `login` | `POST /api/v1/auth/login` | Нормализованный login | 5 за 60 секунд | 5 |
| `signup` | `POST /api/v1/auth/signup` | Нормализованный login | 3 за 60 секунд | 3 |
| `refresh` | `POST /api/v1/auth/refresh` | UUID пользователя из проверенного refresh JWT | 10 за 60 секунд | 5 |
| `user` | `GET|PATCH /profile`, `GET /login-history`, `POST /logout` | UUID текущего пользователя | 60 за 60 секунд | 10 |
| `admin` | Получение и изменение ролей и назначений | UUID текущего администратора | 30 за 60 секунд | 5 |
| `service` | `POST /api/v1/auth/permissions/check` | Проверенный сервис `movies-api` | 600 за 60 секунд | 50 |

Auth применяет один Redis bucket к одному запросу. Nginx независимо применяет внешний лимит по IP.

Healthcheck, OpenAPI и Swagger не используют Token Bucket.

## Ключи Redis

Формат ключа:

```text
rate-limit:<policy>:<sha256(identity)>
```

Login перед хешированием проходит существующую нормализацию входных данных: внешние пробелы удаляются, регистр сохраняется. UUID преобразуется в каноническую строку. Refresh JWT не используется как identity. В Redis не сохраняются login, UUID, IP, JWT или сервисный ключ в открытом виде.

Для `permissions/check` Auth сначала проверяет `X-Service-Key`. После успешной проверки он использует стабильный идентификатор `movies-api`. Значение сервисного ключа не используется как Redis key.

## HTTP-контракт

При исчерпании bucket Auth возвращает:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 12
Content-Type: application/json
```

```json
{"detail":"Too many requests"}
```

`Retry-After` содержит целое количество секунд до появления следующего токена. Минимальное значение равно `1`.

Nginx возвращает тот же JSON и `Retry-After: 1` для запроса, который отклонён внешним лимитом.

## Отказ Redis

Rate limiter не выполняет backoff. Одна проверка выполняет не более одного вызова зарегистрированного Lua-скрипта.

Ошибка соединения или timeout Redis включает fail-open:

1. Auth записывает техническую ошибку.
2. Текущий запрос продолжает выполнение.
3. Rate limiter не меняет ответ бизнес-обработчика.

Ошибка самого Lua-скрипта не считается недоступностью Redis. Такая ошибка не скрывается режимом fail-open.

## Обработка HTTP 429 клиентами

Movies API распознаёт HTTP `429` от `permissions/check` как отдельное ограничение. Клиент сохраняет положительный `Retry-After` в `AuthRateLimitedError`. Movies API не удерживает запрос пользователя до окончания этого времени. Он немедленно применяет локальную политику по возрасту фильма.

Admin распознаёт HTTP `429` отдельно от недоступности и ошибки контракта Auth. Вход, защищённая страница и операция управления ролями возвращают понятную страницу HTTP `429` и сохраняют `Retry-After`. Logout всегда очищает локальную Django-сессию.

## Наблюдаемость

Auth записывает отклонение и недоступность хранилища со следующими полями:

- `request_id`;
- `rate_limit.policy`;
- `rate_limit.allowed`;
- `rate_limit.retry_after` для отклонения;
- `rate_limit.store_available=false` для fail-open.

Те же безопасные поля добавляются в текущий OpenTelemetry span. Идентификатор bucket и исходное значение identity не записываются.

Nginx добавляет `$limit_req_status` в access-log. Это поле отличает ограничение gateway от HTTP `429`, полученного от Auth.

## Конфигурация

Локальный `.env` Auth использует префикс `RATE_LIMIT_`. Корневой `.env` использует префикс `AUTH_RATE_LIMIT_`. Docker Compose удаляет часть `AUTH_` при передаче значений контейнеру Auth.

Rate limiting включён по умолчанию в корневом Compose и в локальном `.env.example` Auth. Изолированный функциональный набор Auth отключает механизм и проверяет его отдельными тестами.

## Критерии готовности

- Nginx отклоняет внешний burst и не задерживает его.
- Auth применяет все шесть политик.
- Параллельные запросы не расходуют больше `capacity` токенов.
- Ответ Auth содержит HTTP `429`, JSON и `Retry-After`.
- Токены восстанавливаются по времени Redis.
- Ключи Redis имеют TTL и не содержат исходные идентификаторы.
- Ошибка соединения Redis включает fail-open без повторов.
- Movies API сохраняет причину HTTP `429` и `Retry-After`, затем применяет деградацию без повтора.
- Admin показывает HTTP `429` для входа, защищённых страниц и управления ролями. Logout всегда удаляет локальную Django-сессию.
- Healthcheck, OpenAPI и Swagger не ограничиваются.
- Документация и AS-IS диаграмма соответствуют реализованному потоку.
