### 1.3. Что легко упустить

1. **Вебхуки ЮKassa при локальной работе** — разобраны в 1.4.
2. **Проверка подлинности вебхука.** Уведомления ЮKassa не подписаны. SDK предлагает проверку по IP (`SecurityHelper.is_ip_trusted`), но через туннель IP-адрес будет адресом туннеля. Надёжный способ — не доверять телу уведомления и перезапрашивать объект платежа через API по его `id`.
3. **Пользовательские экраны.** Фронтенда в проекте нет; минимальный набор экранов описан в 2.8.
4. **Окончание подписки** — разобрано в 1.5.
5. **Чеки по 54-ФЗ.** В тестовом магазине не обязательны; в объём не входят.
6. **Секреты.** `shopId` и секретный ключ тестового магазина хранятся только в `.env` и не попадают в репозиторий.

### 1.4. Как узнавать итог оплаты без входящих запросов

**Проблема.** ЮKassa сообщает об итоге платежа или возврата POST-запросом на публичный HTTPS-адрес. Работа идёт на локальной рабочей машине, где туннель может быть запрещён политиками безопасности.

**Проверено с этой машины 28.10.2026:**

| Проверка | Результат | Вывод |
|---|---|---|
| Исходящий HTTPS к `api.yookassa.ru/v3/payments` без ключа | `401` | API ЮKassa доступен; создание платежей, возвратов и запрос статуса работают без входящих соединений |
| Сайт `ngrok.com` | нет ответа за 10 с | ngrok, скорее всего, заблокирован |
| `api.trycloudflare.com` по HTTPS | `405` | Домен доступен, но cloudflared использует собственный протокол до Cloudflare, его проходимость не проверена |
| Установленные `cloudflared`, `ngrok`, `tailscale` | не найдены | Туннель потребует установки ПО на рабочую машину |

**Ключевой принцип.** Вебхук не должен быть источником истины. Обработчик берёт из уведомления только `id` объекта, а статус всегда запрашивает у API ЮKassa (п. 2 в 1.3). Тогда вебхук — лишь сигнал «проверь сейчас». Тот же сигнал можно получить и без него.

**Стратегии:**

| # | Стратегия | Как работает | Нужны входящие соединения | Задержка итога | Оценка |
|---|---|---|---|---|---|
| A | Проверка при возврате пользователя | Страница `return_url` при открытии запрашивает статус платежа у ЮKassa | Нет | Сразу при возврате на сайт | Покрывает основной сценарий |
| B | Фоновая сверка | Процесс раз в интервал запрашивает статус всех незавершённых платежей и возвратов | Нет | До одного интервала | Покрывает закрытую вкладку, возвраты и сбои; нужна в любом случае для надёжности |
| C | Локальная эмуляция вебхука | Тест или скрипт отправляет на локальный обработчик JSON в формате уведомления ЮKassa с реальным `id`; обработчик перезапрашивает статус | Нет | Мгновенно | Проверяет код вебхука в тестах и на демо; итог всё равно берётся из ЮKassa |
| D | Туннель (cloudflared quick tunnel, Tailscale Funnel) | Публичный адрес проксируется на локальный шлюз; адрес указывается в настройках HTTP-уведомлений тестового магазина | Да, через туннель | Секунды | **Отклонено:** туннели на рабочей машине не работают |
| E | Внешний приёмник | Небольшой приёмник на внешнем сервере сохраняет уведомления, локальный биллинг их забирает | Нет | Интервал забора | Лишняя инфраструктура ради одного сигнала; не нужен при A + B |

**Решение (28.10.2026):** A и B — основной механизм; D и E не используются. Вариант C принят: обработчик вебхука реализуется (берёт из уведомления только `id` и вызывает ту же функцию обновления статуса, что A и B) и проверяется тестом, который отправляет уведомление в формате ЮKassa с идентификатором настоящего тестового платежа. Реальная ЮKassa на локальной машине его не вызывает.

- Блокера нет: для A и B нужен только исходящий HTTPS к ЮKassa, и он работает.
- Возвраты не имеют страницы возврата пользователя, поэтому итог возврата узнаётся только через B.
- На защите: «система не зависит от доставки вебхука; итог мы узнаём сами при возврате пользователя и фоновой сверкой».

### 1.5. Окончание подписки: срок на лету вместо периодического процесса

**Идея.** Биллинг хранит начало и конец оплаченного периода, и статус подписки вычисляется на лету: `активна`, если `сейчас < конец периода`. Периодический процесс для статуса в биллинге не нужен.

**Ограничение.** Доступ к новинкам проверяет не биллинг, а Auth: movies-api вызывает `permissions/check`, а Auth смотрит роли пользователя. Если роль выдана без срока, доступ останется и после конца периода. Значит, срок должен знать тот, кто проверяет доступ.

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| 1. Срок действия роли в Auth | Биллинг выдаёт роль с `expires_at`; Auth игнорирует истёкшие роли при расчёте прав; кэш прав живёт не дольше, чем до ближайшего истечения | Срок проверяется на лету; периодический процесс не нужен; доступ не зависит от доступности биллинга | Изменения Auth: колонка `expires_at` в `user_roles`, миграция, учёт срока в кэше прав |
| 2. Периодический отзыв роли | Биллинг раз в интервал отзывает роли у истёкших подписок | Auth меняется меньше | Доступ остаётся до следующего запуска; ещё один процесс; при сбое процесса доступ не отзывается |
| 3. Auth спрашивает биллинг | При каждой проверке прав Auth обращается к биллингу | Единый источник истины | Биллинг попадает в путь каждого просмотра фильма; при его сбое пропадает доступ у всех — противоречит НФТ-R7 |

**Решение (28.10.2026) — вариант 1.** Он реализует вашу идею последовательно: срок хранится и в биллинге (для статуса и истории), и в Auth (для проверки доступа). Возврат по-прежнему отзывает роль немедленно.

**Письмо об окончании подписки (решение 28.10.2026).** Фонового процесса нет, поэтому письмо планируется заранее, а при возврате отменяется.

1. При активации подписки биллинг передаёт письмо в Campaign API с `available_at`, равным концу оплаченного периода. Отдельная кампания на подписку; её `campaign_id` выводится из идентификатора подписки.
2. До наступления срока письмо лежит в outbox Notifications, publisher его не публикует.
3. При успешном возврате биллинг вызывает новый эндпоинт отмены кампании в Campaign API. Незавершённые доставки кампании переходят в конечный статус `cancelled` с причиной `cancelled_by_sender`.

Что уже есть в Notifications (проверено по коду): статус доставки `cancelled` предусмотрен схемой; worker перед подготовкой и отправкой перечитывает доставку под блокировкой строки и пропускает доставки в конечном статусе; статистика кампании учитывает `cancelled` как пропуск.

Что нужно добавить: эндпоинт `POST /api/v1/notifications/campaigns/{campaign_id}/cancel` с сервисным ключом; новая причина `cancelled_by_sender` в ограничении `terminal_reason` (миграция). Отмена идемпотентна. Доставку, уже переданную на SMTP (статус `sending`), отменить нельзя.

**Принятый риск.** Если возврат совпадёт с моментом отправки письма об окончании, письмо может уйти. Риск принимаем без дополнительной защиты: возврат в последние секунды оплаченного периода не ожидается как штатный сценарий администратора и больше похож на мошенничество.

### 1.6. Где хранятся подписка, доступ и история

**Что сейчас есть в Auth (проверено по коду и миграции `20260815_0002_rbac.py`):**

| Таблица | Содержимое |
|---|---|
| `permissions` | Коды прав: `roles:manage`, `user_roles:manage`, `films.early_access:read` |
| `roles` | Роли `admin` и `subscriber` |
| `role_permissions` | `subscriber` → `films.early_access:read`; `admin` → `roles:manage`, `user_roles:manage` |
| `user_roles` | Пары «пользователь — роль» без сроков и без истории: строка есть — роль есть |

«Галка» доступа к новинкам — это строка `(user_id, subscriber)` в `user_roles`. Роль `subscriber` уже создана миграцией, создавать её не нужно. Права пользователя Auth кэширует в Redis (`AUTHORIZATION_CACHE_TTL_SECONDS`, по умолчанию 300 с). При выдаче и отзыве роли через сервис авторизации кэш пользователя сбрасывается.

**Разделение ответственности:**

- **Auth хранит только текущий доступ** — «можно ли сейчас смотреть новинки». Истории в Auth нет и не появляется.
- **Биллинг хранит всю историю** — каждую подписку, платёж и возврат отдельной записью. Записи не удаляются и не перезаписываются.

**Изменение Auth.** В `user_roles` добавляется необязательная колонка `expires_at`:

- `NULL` — роль бессрочная; так остаются все существующие роли, включая `admin`;
- дата — роль действует до этой даты; после неё Auth считает, что роли нет;
- выдача подписки — запись строки `(user_id, subscriber, expires_at = конец периода)`; если строка уже есть от прошлой подписки, обновляется только `expires_at`;
- возврат — удаление строки, доступ закрывается сразу;
- истечение срока не меняет данные, поэтому кэш прав не должен жить дольше, чем до ближайшего `expires_at` пользователя; иначе доступ сохранится до 5 минут после окончания.

Ролью `subscriber` управляет только биллинг. Ручное назначение этой роли через существующий API администратора в сценарии не входит.

**Что хранит биллинг (предварительно; схема уточняется на шаге 5):**

| Сущность | Что в ней | Сколько записей |
|---|---|---|
| Подписка | Пользователь, тариф, начало и конец периода, платёж, которым оплачена. После создания не меняется | Одна на каждый оплаченный период |
| Платёж | Сумма, итоговый статус («оплачен» или «не оплачен»), идентификатор в ЮKassa, ключ идемпотентности. Итоговый статус не меняется, в том числе при возврате | Одна на каждую попытку оплаты, включая неуспешные |
| Возврат | Платёж, сумма, статус, идентификатор в ЮKassa, администратор и причина | Не больше одного на платёж |
| Журнал событий | Каждый переход статуса платежа, подписки и возврата: когда и по какой причине (возврат пользователя, сверка, вебхук, администратор) | Много на каждую операцию |

Статус подписки не хранится, а вычисляется: «Возвращена», если по её платежу есть успешный возврат; «Активна», если сейчас раньше конца периода; иначе «Завершена».

**Принцип: финансовые записи только добавляются.** Ранее записанные факты не перезаписываются и не удаляются.

- Возврат — **компенсирующая запись**: новая запись «Возврат» со ссылкой на платёж. Платёж остаётся «оплачен», подписка сохраняет свой период; то, что деньги вернули, видно по наличию возврата.
- Промежуточные стадии одной операции («ожидает» → «оплачен», «в обработке» → «выполнен») добавляются в журнал событий. Поле текущего статуса в записи операции — производное от журнала и обновляется в той же транзакции. Итоговый статус после установки не меняется.
- Если запись оказалась ошибочной, исправление — тоже новая запись, а не правка старой.
- Удаление строки в Auth при возврате этому принципу не противоречит: Auth хранит текущий доступ, а не историю.

**Пример истории пользователя:**

| Когда | Биллинг | Auth (`user_roles`) |
|---|---|---|
| 5 января оплатил | Подписка №1: 5 января — 5 февраля | `subscriber`, `expires_at` = 5 февраля |
| 5 февраля | Подписка №1 вычисляется как «Завершена» | Строка осталась, но срок прошёл — доступа нет |
| Февраль — без подписки | Новых записей нет | Без изменений |
| 10 марта оплатил снова | Подписка №2: 10 марта — 10 апреля; №1 остаётся в истории | Та же строка, `expires_at` = 10 апреля |
| 15 марта возврат | Добавлены запись возврата и действие администратора; подписка №2 и её платёж не меняются, статус «Возвращена» вычисляется по возврату | Строка удалена |

Перерывы и повторные покупки видны в биллинге. Auth в любой момент знает только ответ на вопрос «есть ли доступ сейчас».

## Шаг 2. Продуктовая часть ТЗ

### 2.1. Проблема и ценность

Сейчас фильмы младше трёх лет требуют право `films.early_access:read`, но получить его можно только вручную через администратора. Монетизации нет.

Биллинг даёт кинотеатру выручку от подписки «Премиум», которая открывает новинки. Пользователь получает доступ сразу после оплаты без участия поддержки. Поддержка видит все платежи и может вернуть деньги из админки.

| Составляющая | Ответ |
|---|---|
| Ценность | Выручка от подписок; самообслуживание вместо ручной выдачи прав |
| Затраты | Один разработчик, 4 недели; тестовый магазин ЮKassa бесплатен |
| Время | MVP к защите в конце четвёртой недели |

### 2.2. Пользователи

| Роль | Что делает |
|---|---|
| Пользователь | Покупает подписку, видит её статус и историю платежей; за возвратом обращается в поддержку |
| Администратор (поддержка) | Ищет пользователя, видит подписки, платежи и возвраты, оформляет возврат, видит журнал действий |
| Внешние системы | ЮKassa проводит платежи и возвраты; Auth выдаёт доступ; Notifications отправляет письма |

### 2.3. Объём работ

**Входит:**

- один тарифный план: «Премиум», 1 месяц, 299 ₽;
- оплата картой через страницу ЮKassa;
- полный возврат последнего платежа по решению администратора с немедленным отзывом доступа;
- выдача доступа со сроком и его отзыв через Auth;
- письма об успешной оплате, ошибке оплаты, возврате и окончании подписки;
- минимальные пользовательские экраны (2.8);
- управление в Django-админке.

**Не входит:**

- автопродление и сохранение карт (рекуррентные платежи);
- несколько тарифов, промокоды, пробный период;
- частичные и пропорциональные возвраты;
- самостоятельный возврат пользователем без участия администратора;
- чеки 54-ФЗ, мультивалютность, другие способы оплаты.

Автопродление — первый кандидат на добавление, если останется время. Модель данных стоит проектировать так, чтобы его можно было добавить без переделки.

### 2.4. Сценарии

**С1. Покупка подписки**

1. Пользователь авторизован и вызывает «Купить подписку».
2. Биллинг создаёт платёж у себя, затем в ЮKassa и возвращает ссылку на оплату.
3. Пользователь вводит тестовую карту на странице ЮKassa.
4. ЮKassa возвращает пользователя на страницу статуса биллинга.
5. Биллинг узнаёт итог: при открытии страницы возврата, из вебхука или при фоновой сверке (1.4). Затем активирует подписку, выдаёт доступ со сроком через Auth и отправляет письмо.
6. Пользователь видит статус «Активна» и смотрит новинки.

Ветки:

- оплата отклонена или отменена: статус «Не оплачено», письмо об ошибке, можно повторить покупку;
- пользователь закрыл страницу ЮKassa: платёж остаётся в ожидании до итога или истечения срока, повторное нажатие не создаёт второе списание (ФТ-7);
- повторное нажатие или двойной запрос: возвращается тот же незавершённый платёж;
- подписка уже активна: покупка отклоняется с понятной ошибкой (продление — вне объёма);
- ЮKassa недоступна при создании платежа: пользователь получает понятную ошибку, деньги не списаны;
- Auth недоступен при выдаче доступа: подписка оплачена, выдача повторяется до успеха; пользователь видит «Оплачено, доступ активируется».

**С2. Возврат**

1. Администратор находит платёж в админке и нажимает «Вернуть».
2. Биллинг создаёт возврат в ЮKassa.
3. По итогу возврата биллинг отзывает доступ через Auth, отменяет запланированное письмо об окончании подписки и отправляет письмо о возврате.

Ветки:

- возврат возможен только для платежа, которым оплачена **текущая активная** подписка;
- платёж завершённой подписки вернуть нельзя — и когда у пользователя уже есть новая активная подписка, и когда активной подписки нет;
- платёж ещё не завершён или уже возвращён: действие недоступно;
- ЮKassa отклонила возврат: администратор видит статус и причину;
- повторное нажатие: второй возврат не создаётся.

**С3. Окончание подписки.** Когда оплаченный период закончился, подписка считается завершённой, а Auth перестаёт учитывать роль. Оба вывода делаются на лету по дате окончания, без фонового процесса. Письмо об окончании, запланированное при активации, уходит в эту дату (1.5).

**С4. Просмотр.** Пользователь видит текущую подписку (статус, дата окончания) и историю платежей.

### 2.5. Нулевые состояния

| Состояние | Что видит пользователь или администратор |
|---|---|
| Пользователь без подписки | Статус «Нет подписки» и кнопка покупки |
| Пользователь без платежей | Пустая история |
| Платёж ожидает итога | Статус «Ожидает подтверждения» и ссылка для продолжения оплаты |
| Подписка оплачена, доступ ещё не выдан | «Оплачено, доступ активируется» |
| В админке нет платежей по фильтру | Пустой список |

### 2.6. Уведомления

Все письма — транзакционные, через Campaign API сервиса уведомлений с новым шаблоном биллинга (1.2).

| Событие | Когда | Содержание |
|---|---|---|
| Оплата прошла | Подписка активирована | Срок действия, что открыто |
| Оплата не прошла | Платёж отменён | Причина, ссылка на повтор |
| Возврат выполнен | Возврат завершён | Сумма, отзыв доступа |
| Подписка закончилась | Дата окончания; планируется при активации, отменяется при возврате (1.5) | Ссылка на покупку |

### 2.7. Служба поддержки: сценарии Django-админки

**Как сейчас устроен вход в админку (проверено по `services/admin/app/users/auth_backend.py`).** Администратор входит логином и паролем Auth. Вход разрешён, только если Auth разрешает пользователю читать список ролей. Каждый вошедший получает в Django полные права. Отдельного права «может делать возвраты» нет, поэтому раздел биллинга доступен всем администраторам.

**Общие правила раздела биллинга:**

- данные подписок, платежей, возвратов и журнала **только для чтения**; ручное изменение статусов и сумм запрещено;
- администратор не меняет существующие записи; единственное его действие — оформление возврата, которое **добавляет** компенсирующую запись (1.6, А4);
- все даты хранятся в UTC.

**Часовые пояса (решение 28.10.2026):**

| Где | Как показываются даты |
|---|---|
| Django-админка | Две колонки: UTC и часовой пояс пользователя, к которому относится запись (из профиля Auth, ФТ-30) |
| Экраны пользователя (2.8) | Часовой пояс пользователя из его профиля Auth |
| Письма | Московское время с пометкой «МСК» |

**Намеренное сокращение объёма.** Письма не учитывают часовой пояс получателя. Текст письма биллинг формирует в фоне без участия пользователя, а внутренний эндпоинт контактов Auth (`/api/v1/internal/notification-contacts`) часовой пояс не возвращает. Учёт часового пояса в письмах — направление развития.

**А1. Найти пользователя и посмотреть его историю**

1. Администратор открывает «Подписки» и ищет по идентификатору пользователя (UUID).
2. Видит все подписки пользователя: период, вычисленный статус («Активна», «Завершена», «Возвращена»), сумму, ссылку на платёж.
3. Из подписки переходит в карточку платежа (А3).

Поиск по логину (решение 28.10.2026). Биллинг хранит только UUID пользователя, поэтому админка сначала спрашивает Auth «какой UUID у пользователя с логином …», а затем ищет подписки по этому UUID. В Auth уже есть метод репозитория `get_id_by_login`, но HTTP-эндпоинта для него нет — нужен внутренний эндпоинт с сервисными учётными данными (ФТ-30). Он же возвращает логин и часовой пояс по списку UUID: так админка показывает логин вместо UUID и время в часовом поясе пользователя. Поиск по email не делаем: email в Auth не уникален, по нему может найтись несколько пользователей.

**А2. Список платежей и поиск проблемных операций**

1. Администратор открывает «Платежи».
2. Фильтрует по статусу (ожидает, оплачен, не оплачен), по признаку «есть возврат» и дате; ищет по нашему номеру платежа или номеру платежа в ЮKassa.
3. Два фильтра для поиска сбоев. В штатной работе оба списка пусты; запись в них означает, что нужна реакция поддержки или разработчика.
   - **«Зависшие операции»** — платежи и возвраты в промежуточном статусе дольше порога (настройка, по умолчанию 10 минут). Отличие от фильтра по статусу «Ожидает»: тот показывает и штатные незавершённые платежи, например пользователя, который прямо сейчас вводит карту. Зависшая операция означает, что фоновая сверка не смогла довести её до итога: ЮKassa недоступна, сверка не работает или ошибка в коде. Помогает кнопка «Проверить в ЮKassa» (А6).
   - **«Не доставлено в Auth или Notifications»** — невыполненные задачи outbox биллинга старше порога (настройка): выдача и отзыв роли в Auth, передача и отмена писем в Campaign API. Auth для этого не опрашивается: при активации подписки в той же транзакции создаётся задача «выдать роль `subscriber` до …», фоновый процесс отправляет её в Auth и после успешного ответа отмечает выполненной (НФТ-R6). Пока Auth недоступен, задача остаётся невыполненной и повторяется. Так находятся оплаченные подписки без выданного доступа и возвраты без отзыва доступа.

**А3. Карточка платежа**

Показывает:

- пользователя, сумму, номер в ЮKassa, текущий статус;
- связанную подписку и её период;
- журнал переходов статусов: время, новый статус, источник (возврат пользователя, сверка, вебхук, администратор);
- задачи outbox по этой операции (выдача и отзыв доступа, письма): статус, число попыток, последняя ошибка;
- возврат, если есть: статус, сумму, автора, причину;
- кнопку «Вернуть», если возврат разрешён правилами С2.

**А4. Оформить возврат**

1. В карточке платежа администратор нажимает «Вернуть».
2. Открывается страница подтверждения: пользователь, сумма, период подписки и последствия — доступ закроется сразу, письмо об окончании отменится, пользователь получит письмо о возврате. Поле «Причина» обязательно.
3. Администратор подтверждает. Биллинг сохраняет возврат и действие в журнале, затем создаёт возврат в ЮKassa.
4. Карточка показывает «Возврат в обработке». Итог приходит фоновой сверкой — не позже интервала сверки, по умолчанию 30 с.
5. После успеха: у возврата статус «Выполнен»; платёж остаётся «оплачен» с отметкой о возврате; подписка вычисляется как «Возвращена»; доступ отозван; письмо о возврате отправлено.

Ветки:

- возврат запрещён правилами С2: кнопки нет, а прямой запрос отклоняется с объяснением;
- двойное нажатие или повторная отправка формы: второй возврат не создаётся, показывается существующий;
- ЮKassa отклонила возврат: статус «Возврат отклонён» с причиной от ЮKassa; доступ и письма не меняются;
- ЮKassa недоступна или не ответила: возврат остаётся «В обработке», сверка узнаёт итог; администратор видит это в карточке и в фильтре «Зависшие операции».

**А5. Журнал действий администраторов**

Список всех возвратов, оформленных администраторами: кто, когда, по какому платежу и с какой причиной. Фильтр по администратору и дате. Записи не редактируются и не удаляются.

**А6. Проверить статус сейчас** (решение 28.10.2026)

В карточке зависшего платежа или возврата кнопка «Проверить в ЮKassa» сразу запрашивает статус, не дожидаясь сверки. Это та же функция обновления статуса, что у стратегий A и B (1.4), поэтому стоит недорого.

### 2.8. Пользовательские экраны

Минимальный набор для живого демо сценария С1. Экраны — серверные HTML-страницы без отдельного фронтенд-приложения; конкретная технология выбирается на шаге 5.

| Экран | Адрес (предварительно) | Что на экране | Переходы |
|---|---|---|---|
| Э1. Вход | `/billing/login` | Email и пароль; вход через существующий API Auth | Успех → Э2 |
| Э2. Моя подписка | `/billing/` | Статус: «Нет подписки», «Ожидает оплаты», «Оплачено, доступ активируется», «Активна до …», «Завершена», «Возвращена». Кнопка «Оформить за 299 ₽» при отсутствии активной подписки. Ссылка «Продолжить оплату» для незавершённого платежа. История платежей | Кнопка → страница оплаты ЮKassa; без входа → Э1 |

| Э3. Результат оплаты | `/billing/payments/{id}` | При открытии биллинг запрашивает статус у ЮKassa (стратегия A в 1.4). «Оплата прошла, доступ открыт до …», «Оплата не прошла» с кнопкой повтора или «Проверяем оплату…» с автообновлением | Ссылка «Моя подписка» → Э2 |

## Шаг 4. Нефункциональные требования (FURPS+)

### R — Reliability

| Код | Требование |
|---|---|
| НФТ-R1 | **Нет двойных списаний.** Не больше одного незавершённого платежа на пользователя (ограничение в БД); запрос в ЮKassa отправляется с `Idempotence-Key`, равным идентификатору нашего платежа; повтор запроса не создаёт новый платёж |
| НФТ-R2 | **Нет двойных возвратов.** Не больше одного возврата на платёж (ограничение в БД) и `Idempotence-Key` при создании возврата |

| НФТ-R4 | Повторная доставка одного и того же уведомления ЮKassa не меняет результат (идемпотентная обработка) |
| НФТ-R5 | Незавершённые платежи и возвраты сверяются с ЮKassa; ни одна операция не остаётся в промежуточном статусе дольше срока сверки |

| НФТ-R8 | Тайм-ауты на все внешние вызовы; ответ ЮKassa «неизвестно» (тайм-аут, 5xx) не считается ни успехом, ни отказом, а решается сверкой |
