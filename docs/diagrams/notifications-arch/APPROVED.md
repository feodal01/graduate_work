# Согласованные решения

## Auth
### Проверка токена в API подписок

**Introspection** — запрос текущего состояния access-токена в Auth.
Перед каждым чтением и изменением подписок Notifications проверяет JWT локально,
затем вызывает внутренний `POST /api/v1/internal/introspect` с сервисной авторизацией.
Auth использует общую проверку подписи, срока действия, отзыва токена, версии состояния
сессий `session_epoch` и незавершённого изменения этого состояния.

Неактивный токен даёт `401` в API подписок. Недоступность проверки, неверный сервисный
ключ или некорректный ответ Auth дают `503`; подписки не меняются. Положительные ответы
не кэшируются. Запрос, начатый после успешного logout, уже не может использовать
отозванный токен. Завершение запросов, проверенных до logout, отдельно не блокируется.

### События Auth

**Outbox** — таблица исходящих событий в базе Auth.

**Relay** — отдельный экземпляр Auth, запущенный в режиме пересылки событий из outbox в Kafka. В этом экземпляре работает только relay; HTTP API не запускается. Экземпляры Auth API и Auth relay используют один проект Auth и общую базу данных Auth. Relay работает постоянно, независимо от обработки HTTP-запросов к Auth API.

Механизм применяется к трём операциям:

- регистрация пользователя — `user.registered`;
- удаление пользователя — `user.deleted`;
- изменение часового пояса пользователя — `user.profile_updated` (также используется для первичной загрузки).

Все три типа событий отправляются в один топик Kafka — `auth.users.v1`.

### Общие поля событий Auth

Каждое событие содержит:

- `event_id` — уникальный идентификатор события; сохраняется в outbox и не меняется при повторной отправке;
- `user_id` — постоянный идентификатор пользователя;
- `user_version` — номер версии данных этого пользователя.

При регистрации `user_version` равен 1. Auth увеличивает его при изменении профиля и при удалении пользователя. Не каждое изменение профиля создаёт событие для Notifications, поэтому пропуски версий допустимы: получатель сравнивает версии через `>`. Версия относится к пользователю, а не к формату сообщения.

### Данные профиля Auth

В профиле могут изменяться:

- `email` — адрес электронной почты;
- `first_name` — имя;
- `last_name` — фамилия;
- `locale` — язык и региональные настройки;
- `tz` — часовой пояс.

Контактные данные `email`, `first_name`, `last_name`, `locale` хранятся в Auth и больше не включаются в новые события для Notifications. `user.registered` и `user.profile_updated` содержат общие поля, `event_type` и актуальный `tz`. Обычный `user.profile_updated` создаётся только при фактическом изменении `tz`; изменение email, имени, фамилии или языка само по себе события не создаёт. `user.deleted` содержит общие поля и `event_type`, без контактов и `tz`.

`tz` обязателен при любом новом создании пользователя: обычная регистрация, регистрация через соцсеть, CLI и создание администратора. Используется корректный именованный часовой пояс IANA. Клиент передаёт его явно; без фронтенда — в API-запросе или параметрах запуска. Auth не определяет пояс по IP и не подставляет UTC. При обновлении профиля `tz` можно не передавать, но нельзя очистить или заменить некорректным значением. В OAuth пояс передаётся в начале входа и сохраняется в состоянии авторизации до создания пользователя.

Существующим пользователям с неизвестным `tz` значение не выдумывается. Первичная загрузка может передать `tz = null` только для таких исторических записей; правила их допуска к рассылкам описаны в разделе «Дневное окно отправки по времени получателя».

### Публикация событий Auth

1. Auth принимает запрос на операцию с пользователем.
2. Для перечисленных операций Auth сохраняет изменение пользователя, его версию и событие в outbox в одной транзакции: сохраняются все изменения либо ни одно. Изменения только контактных полей сохраняются без события для Notifications. У новой записи outbox `published_at = NULL`.
3. Relay читает сохранённые записи с `published_at IS NULL` пачками до 500 записей, не ожидая заполнения пачки.
4. Relay передаёт события Kafka-клиенту отдельными сообщениями с ключом `user_id`, не ожидая подтверждения каждого перед передачей следующего. Клиент объединяет сообщения в сетевые батчи; 500 сообщений не означают 500 сетевых запросов.
5. Relay дожидается результатов отправки и одним обновлением сохраняет `published_at` в базе Auth только для записей, подтверждённых Kafka.

Relay проверяет outbox сразу при запуске и после обработки каждой пачки. Если записей нет или произошла ошибка, повторяет попытку через 1 секунду. Размер пачки и пауза настраиваются.

После сбоя relay снова читает неопубликованные записи. Если Kafka уже приняла событие, но `published_at` не сохранился, relay повторяет отправку с тем же `event_id`.

## Передача событий из UGC в Notifications

Путь события: `UGC API → outbox в MongoDB → UGC relay → Kafka → consumer Notifications → база Notifications`.

**Outbox UGC** — коллекция исходящих событий в MongoDB UGC. **UGC relay** — отдельный экземпляр UGC, работающий только в режиме пересылки; HTTP API в нём не запускается. **Consumer Notifications** — процесс, который читает события из Kafka и сохраняет их результат в базе Notifications.

1. При изменении количества лайков UGC в одной транзакции MongoDB сохраняет изменение голоса, итоговый `likes_count`, увеличенную `likes_version` комментария и событие в outbox с `published_at = NULL`. Повторный запрос, не меняющий голос, нового события не создаёт. Снятие лайка и замена лайка дизлайком также меняют счётчик и создают событие.
2. Событие содержит `event_id`, `review_id`, `user_id` автора комментария, итоговый `likes_count` и `likes_version`. `user_id` обозначает получателя уведомления. Передаётся полное значение счётчика, а не прибавка `+1` или `-1`; `event_id` и содержимое события не меняются при повторной отправке.
3. Relay периодически читает из outbox пачку записей с `published_at IS NULL` и отправляет их отдельными сообщениями в отдельный топик событий UGC в Kafka. Ключ сообщения — `review_id`. Relay видит только записи завершённых транзакций.
4. После подтверждения Kafka relay заполняет `published_at` только у успешно опубликованных записей. Остальные остаются для следующей попытки. Это отметка доставки в Kafka; обработка события в Notifications может произойти позже.
5. Consumer создаёт отсутствующий локальный счётчик либо обновляет существующий только при большей `likes_version`. Обычные события сохраняют `last_sent_likes_count` и `last_notification_sent_at` существующей строки. Повторная или более старая версия не меняет текущий счётчик; начальная точка отсчёта задаётся отдельно при первичной загрузке, описанной в разделе «Уведомления о лайках».
6. Сравнение версии, запись счётчика и следующей позиции чтения для соответствующих топика и партиции в таблице `kafka_offsets` выполняются в одной транзакции базы Notifications. При запуске consumer продолжает чтение с сохранённой в этой таблице позиции.

Сбой до завершения транзакции UGC откатывает и изменение голоса, и событие. После её завершения событие остаётся в outbox до публикации. Если Kafka приняла сообщение, но relay не успел сохранить `published_at`, он отправит его повторно с тем же `event_id`; проверка `likes_version` не даст повторно изменить счётчик. Сбой consumer до `COMMIT` откатывает и счётчик, и позицию чтения — событие будет прочитано снова.

Приём события обновляет данные для будущего дайджеста. Генерацией уведомлений по расписанию и порогу прироста занимается scheduler, описанный в разделе «Уведомления о лайках».

## Movies: новинки и изменения рабочего каталога

Источник данных — рабочий индекс Elasticsearch, из которого Movies API читает фильмы. Каталог периодически читает отдельный процесс обнаружения новинок и изменений на стороне Movies. Фильм становится кандидатом для рассылки только после появления в рабочем каталоге.

Путь события: `Elasticsearch → процесс обнаружения новинок и изменений Movies → outbox → relay → Kafka → consumer Notifications`.

Отдельный relay отправляет события в Kafka и отмечает публикацию после подтверждения Kafka; при повторной отправке сохраняет `event_id` и содержимое события. Notifications получает карточки фильмов из Kafka и сохраняет их локально. Его scheduler собирает рассылку новинок активным пользователям с `new_films = true`, читая собственную базу. Начальная периодичность рассылки — раз в семь суток; расписание приведено в разделе «Начальные настройки дайджестов». Периодичность проверки каталога процессом Movies ещё не выбрана.

ETL добавляет в документ фильма `catalog_published_at` — дату и время его первой публикации в рабочем каталоге, в UTC. Это отдельное поле от `creation_date`. Повторная обработка ETL, изменение карточки и переиндексация сохраняют первоначальное значение `catalog_published_at`.

Также ETL записывает вместе с карточкой `film_version` — возрастающий номер версии передаваемых в Notifications данных — и `catalog_updated_at` — время их изменения в UTC. Изменение названия, описания, даты создания фильма, рейтинга или жанров увеличивает версию и обновляет это время. При первой публикации `catalog_updated_at` равен `catalog_published_at`. Повторная загрузка тех же данных и переиндексация сохраняют версию и время изменения.

Для обнаружения изменений Movies хранит в своей базе `known_films` с уникальным `film_id` и последней обработанной `film_version`, а также прогресс чтения каталога:

1. Процесс читает фильмы по `catalog_updated_at` за очередной период, повторно захватывая часть предыдущего периода. Читает пачками с сортировкой по `catalog_updated_at` и `film_id`.
2. Для неизвестного фильма создаёт `film.published`, для известного с большей `film_version` — `film.updated`. Равную или меньшую версию пропускает. Изменение `known_films`, запись событий в outbox и прогресса чтения выполняются в одной транзакции. Сбой до `COMMIT` откатывает всё; пачка обрабатывается повторно.
3. Реже выполняет полную сверку идентификаторов и версий каталога пачками, чтобы обнаружить новинки и обновления, ставшие видимыми позже повторно проверяемого периода. Размер этого периода и частота полной сверки ещё не выбраны.

Оба события, `film.published` и `film.updated`, содержат полный снимок данных фильма из Elasticsearch на момент обнаружения:

| Поле | Назначение |
| --- | --- |
| `event_id` | Уникальный идентификатор события, сохраняется в outbox |
| `film_id` | Идентификатор фильма из поля `id` документа Elasticsearch |
| `film_version` | Версия передаваемых данных фильма |
| `catalog_published_at` | Время первой публикации в каталоге, UTC |
| `catalog_updated_at` | Время изменения передаваемых данных, UTC |
| `title` | Название фильма |
| `description` | Описание, если есть |
| `creation_date` | Дата создания фильма, если есть; позволяет получить год |
| `imdb_rating` | Рейтинг, если есть |
| `genres` | Список жанров с идентификаторами и названиями |

Notifications хранит карточку по уникальному `film_id` и применяет данные только при большей `film_version`. `film.updated` обновляет карточку или создаёт отсутствующую, но не запускает новую рассылку. Для подготовки письма используется последняя полученная версия карточки; отсутствующие описание, дату или рейтинг в письме не показывает.

`film.published` один раз учитывает фильм как новинку. Отметка этого действия хранится отдельно от версии карточки: если `film.updated` пришёл раньше `film.published`, запоздавшая публикация учитывает новинку, сохраняя более свежие данные. Повторные события не создают повторную новинку.

### Первичная загрузка фильмов

Существующий каталог переносится отдельным одноразовым контейнером на стороне Movies. После переноса контейнер завершается. Старые фильмы загружаются без рассылок; заполнение новых полей у них также не запускает уведомления.

1. Контейнер читает зафиксированный исходный каталог из Elasticsearch пачками.
2. В одной транзакции на пачку добавляет фильмы с текущими `film_version` в `known_films`, записывает в outbox события `film.updated` с полными данными и сохраняет прогресс загрузки.
3. Relay отправляет события в Kafka обычным способом.
4. Notifications создаёт или обновляет карточки; `film.updated` рассылку не запускает. Версии фильмов при переносе не увеличиваются.

Обычный процесс обнаружения запускается после заполнения `known_films`. Состав исходного каталога и граница начала загрузки сохраняются для повторных запусков. Фильмы, появившиеся во время переноса, затем обрабатываются как новинки через `film.published`; отсчёт обнаружения не переносится на момент завершения контейнера.

Контейнер использует постоянный `load_id`, например `initial-films-v1`. Уникальность `(load_id, film_id)` в outbox защищает от повторного добавления: уже обработанные пары пропускаются, загрузка продолжается с сохранённого прогресса. У обычных событий `load_id = NULL`. Как и для Auth, при очистке outbox отметки о перенесённых фильмах нужно сохранять отдельно.

## Notifications
### Локальная копия данных о юзерах в Notifications

Auth остаётся источником контактных данных. Notifications хранит только `user_id`, `user_version`, `tz`, признак удаления и флаги рассылок; email, имя, фамилия и язык в локальном профиле не сохраняются. События Kafka обрабатываются так:

1. При регистрации создаёт профиль получателя с начальными значениями флагов рассылок.
2. При `user.profile_updated` создаёт отсутствующий профиль с данными и `user_version` из события и начальными значениями флагов рассылок либо обновляет существующий профиль, сохраняя его флаги. Приветственное письмо по этому событию не отправляет.
3. При удалении пользователя помечает локальный профиль удалённым, сохраняет перечисленные локальные поля и исключает пользователя из дальнейших отправок (то есть убирает все флаги рассылок)

Флаги рассылок (`true` — включено, `false` — отключено):

- `likes` — уведомления о лайках на комментарии пользователя;
- `new_films` — уведомления о появлении новых фильмов;
- `marketing` — рекламные предложения и подборки фильмов.

Флаги меняются отдельно, по запросу пользователя через Notifications API. Аудитория и время отправки рассчитываются по локальным флагам, активности и `tz`, без обращения к Auth. Локальное состояние обновляется с задержкой доставки и обработки событий.

Для подготовки письма worker получает актуальные `email`, `first_name`, `last_name`, `locale` из внутреннего API Auth по `user_id`. API поддерживает запрос пачки пользователей и требует сервисную авторизацию. Отсутствующий или удалённый пользователь не получает письмо; отсутствие email даёт окончательный пропуск `no_email`. Недоступность Auth означает повтор подготовки того же задания через outbox, без SMTP-попытки; таймаут и пауза задаются настройками. Ответ Auth не сохраняется как ещё одна копия профиля.

Подготовленное письмо всё ещё содержит адрес и персонализированный текст. Они временно сохраняются для повторов с тем же `Message-ID`; повтор SMTP не требует повторного получения контактов. После завершения доставки содержимое очищается по настраиваемому сроку хранения, служебная история результата остаётся. Контакты и содержимое письма не записываются в логи. Переход также требует удалить прежние контактные поля локальных профилей и учесть старые события в outbox/Kafka и ранее подготовленные письма: изменение нового контракта само по себе их не очищает.

Очистка содержимого внешних писем удаляет обе копии: `deliveries.payload` и исходные `campaign_recipients.subject`/`text`. Общий срок задаёт `NOTIFICATIONS_DELIVERY_PAYLOAD_RETENTION_SECONDS`. Для доставки он отсчитывается от `terminal_at`; для получателя, пропущенного при приёме без создания доставки, — от `campaign_batches.accepted_at`, независимо от будущей даты отправки. Идентификаторы, итоговые статусы, причины пропуска и хеши пачек остаются для статистики и проверки точных повторов. Повтор принятой пачки не восстанавливает удалённый текст.

### Идемпотентная обработка событий кафки из Auth в Notifications

Идемпотентность означает, что повторное получение одного события не создаёт повторных изменений или заданий на отправку.

Notifications отсеивает повторы по уникальному `event_id` в таблице `processed_events`. Вставка `event_id`, изменение локальных данных и создание необходимых заданий выполняются на одном соединении в одной транзакции, без промежуточных `COMMIT`. Сбой до `COMMIT` откатывает всё, включая `event_id`; после `COMMIT` сохранены и отметка события, и результат обработки.

Некорректное содержимое события Auth, UGC или Movies приостанавливает только его партицию Kafka. Позиция чтения в PostgreSQL не продвигается, последующие сообщения этой партиции не применяются. Остальные партиции продолжают обрабатываться. Consumer сообщает в ERROR-логе топик, партицию, offset и необходимость ручного исправления, не записывая содержимое события. После исправления причины и перезапуска либо при передаче партиции другому владельцу чтение начинается с сохранённой позиции; неисправленное событие снова приостанавливает свою партицию. Автоматического пропуска события нет.

Notifications применяет состояние профиля или помечает удаление только при `user_version` больше сохранённой версии; сравнение и изменение выполняются атомарно. Сохранённая версия удаления защищает профиль от восстановления запоздавшими событиями.

```Plain text
BEGIN — начало транзакции Notifications bd

    Попытаться добавить event_id в processed_events.

    Если запись добавлена:
        Создать локальный профиль с начальными значениями флагов
        либо обновить/пометить удалённым существующий, сохраняя флаги.
        Применить только новую user_version.

        Если событие требует уведомления:
            Создать запись уведомления.
            Создать запись в outbox Notifications
            для дальнейшей обработки.

    Сохранить позицию чтения Kafka в kafka_offsets.

COMMIT — сохранить все изменения вместе
```

### Уведомления о лайках

UGC хранит отдельные голоса пользователей. Notifications хранит локальные счётчики для уведомлений: одну строку на комментарий, без копирования списка голосов и полного содержимого каждого события.

Структура локального счётчика:

| Поле | Назначение |
| --- | --- |
| `review_id` | Идентификатор комментария, уникальный ключ строки |
| `user_id` | Автор комментария и получатель уведомления; внешний ключ на `user_id` локального профиля в Notifications |
| `likes_count` | Последнее известное количество лайков |
| `likes_version` | Последняя применённая версия счётчика этого комментария |
| `last_sent_likes_count` | Точка отсчёта: число лайков из последнего успешно отправленного уведомления; до первой отправки — исходное число при загрузке, для новых комментариев — `0` |
| `last_notification_sent_at` | Дата и время UTC последней успешной отправки; `NULL` до первой отправки |

`likes_version` увеличивает UGC при каждом изменении счётчика конкретного комментария; это отдельная версия, не связанная с `user_version`. Например: версия 5 — 10 лайков, версия 6 — 11, версия 7 — снова 10. После версии 7 Notifications игнорирует повторные и запоздавшие версии 7 и ниже.

Первичная загрузка счётчиков выполняется одноразовым контейнером на стороне UGC. Он читает зафиксированный исходный снимок комментариев и передаёт счётчики с текущими `likes_version` через outbox → relay → Kafka. Версии не увеличивает. Постоянный `load_id` передаётся в событии как признак начальной загрузки; уникальность `(load_id, review_id)` для записей загрузки защищает от повторного добавления в outbox. Исходный снимок и отметки переноса сохраняются между запусками, в том числе при очистке outbox.

При обработке начальной загрузки Notifications один раз записывает исходное число в `last_sent_likes_count`, если уведомлений ещё не было; `last_notification_sent_at` остаётся `NULL`. Точка отсчёта инициализируется независимо от сравнения `likes_version`: более свежий текущий счётчик не откатывается. Повторное событие отсеивается через `processed_events`; отметка события, инициализация, применение счётчика и позиция в `kafka_offsets` сохраняются одной транзакцией. Повторный запуск не сдвигает точку отсчёта и не скрывает накопленный прирост.

Запись обычных событий UGC в outbox включается до переноса. Scheduler лайков запускается после обработки начальной загрузки в Notifications.

В настройках генерации уведомлений Notifications задаётся `likes_min_delta` — минимальный прирост лайков на комментарий: целое число не меньше 1; начальное значение — `3`. Условие включения комментария в дайджест: `likes_count - last_sent_likes_count >= likes_min_delta`. Прирост считается от точки отсчёта в `last_sent_likes_count`; проверки scheduler её не меняют. Уменьшение или прежнее количество лайков уведомление не вызывает.

Scheduler — отдельный процесс Notifications с доступом к его базе. По расписанию он отбирает комментарии, достигшие порога прироста. Одной транзакцией сохраняет выпуск, его состав и аудиторию; затем создаёт задания получателям пачками. Каждая пачка заданий сохраняется вместе с записями outbox и прогрессом обработки в отдельной транзакции. Подробный порядок приведён в разделе «Выпуски дайджестов: состав, аудитория и создание заданий». Воркер формирует сводное письмо по комментариям пользователя; отправка разрешена только активному профилю с включённым `likes`. Приём события сам по себе письмо не запускает; начальная периодичность дайджеста — раз в сутки.

После успешной отправки для комментариев из письма обновляются `last_notification_sent_at` и `last_sent_likes_count`. Сохраняется число из отправленного письма, а не текущий `likes_count`: за время подготовки и отправки счётчик мог измениться.

Сравнение счётчиков показывает изменение общего количества, а не точное число новых лайков. Если три лайка сняли и три других поставили, итоговое число прежнее — уведомление по такому сравнению не создаётся. События и обновления счётчика всё равно обрабатываются для каждого изменения, но число строк в таблице счётчиков растёт по числу комментариев, а не лайков.

## Первичная загрузка пользователей из Auth в Notifications

Существующие пользователи переносятся в Notifications отдельным одноразовым контейнером. После выполнения переноса контейнер завершает работу.

Процесс: 
1. Контейнер выполняет массовую вставку из таблицы пользователей в outbox, в одной транзакции.
2. Для каждого пользователя создаётся `user.profile_updated`: `user_id`, текущий `tz`, текущая `user_version`, уникальный `event_id`, `event_type` и `published_at = NULL`, без контактных данных. Для исторического пользователя с неизвестным поясом допустим `tz = null`.
3. Relay доставляет события обычным способом.
4. Notifications создаёт отсутствующие профили с начальными флагами рассылок, без приветственных писем.

В outbox Auth `load_id` — необязательная метка загрузки: контейнер использует постоянное значение, например `initial-users-v1`, включая повторные запуски; у обычных событий Auth `load_id = NULL`. Уникальность пары `(load_id, user_id)` действует только для строк с заполненным `load_id`: повторная вставка пропускается, обычные события не ограничиваются.

Пример для пользователя 123:
1. Первый запуск добавляет в outbox событие с load_id = initial-users-v1, user_id = 123.
2. Запускаем контейнер повторно.
3. Он пытается добавить событие с той же парой.
4. Ограничение уникальности в базе не позволяет создать вторую запись — пропускаем её.

Защита от повторного добавления действует, пока записи загрузки сохраняются в outbox. При их очистке отметки о перенесённых пользователях нужно сохранять отдельно.

Если контейнер запущен после того как у нас уже какие-то юзеры есть в Notifications - это безоапсно.

Дополнительные события попадут в Kafka, но существующие данные защищает `user_version`.
У событий загрузки новые `event_id`, поэтому проверка по `event_id` их пропустит. Дальше Notifications:
- Профиля нет — создаёт его с начальными флагами.
- Версия такая же или старее — оставляет профиль и флаги без изменений.
- Версия новее — обновляет данные профиля, сохраняя флаги.
Сохранённая версия удаления также защищает от восстановления пользователя устаревшим событием. Приветственные письма на user.`profile_updated` не отправляются.
Важно: контейнер берёт текущую `user_version` из Auth, не увеличивая её ради загрузки.

## Доставка welcome-письма после регистрации

Путь от регистрации до отправки: `Auth → outbox Auth → Auth relay → Kafka → consumer Notifications → outbox Notifications → notifications-publisher → RabbitMQ → notifications-worker → SMTP`.

В этой цепочке два разных outbox: Auth хранит события для Kafka, Notifications — задания для передачи в RabbitMQ. Consumer Notifications создаёт welcome-задание и запись outbox в одной транзакции с обработкой события регистрации, как описано выше.

Welcome — служебное приветственное письмо. Оно отправляется активному пользователю с email независимо от флагов `likes`, `new_films` и `marketing`. На одного пользователя создаётся не более одного welcome-задания. Повтор события регистрации не создаёт новое задание; запоздалая регистрация после более новой версии профиля также не создаёт письмо. Первичная загрузка пользователей через `user.profile_updated` welcome не запускает.

### Данные для отправки и повторов

Все перечисленные таблицы находятся в PostgreSQL Notifications:

| Таблица | Назначение |
| --- | --- |
| `deliveries` | Задание на отправку конкретного письма: `delivery_id`, получатель, вид письма, статус, подготовленное содержимое, `message_id`, время следующей попытки `next_attempt_at` и время успешной отправки `sent_at` |
| `outbox` | Запись для передачи задания в RabbitMQ: `delivery_id`, время доступности для публикации `available_at` и отметка публикации `published_at` |
| `delivery_attempts` | История попыток отправки: `delivery_id`, номер попытки, время начала и завершения, результат `outcome`, описание ошибки `error` и признак риска дубля `duplicate_risk` |

`available_at` — время, раньше которого publisher не должен публиковать запись в RabbitMQ. Столбец уже предусмотрен в модели outbox; его значение по умолчанию — текущее время базы. При создании первой записи для welcome consumer может не передавать это поле: задание сразу доступно для публикации. Для дайджестов scheduler явно рассчитывает время с учётом дневного окна получателя. При назначении повтора worker также задаёт время явно и учитывает дневное окно для классов `service` и `bulk`.

`next_attempt_at` относится к заданию в `deliveries`, а `available_at` — к его передаче через outbox. При назначении повтора оба поля получают одно выбранное время. Время хранится в UTC.

**Lease** — временное закрепление записи за одним процессом. В базе для него хранятся `lease_token` — идентификатор текущего владельца — и `lease_until` — срок владения. Захват выполняется атомарно; обновление результата проверяет владение. После сбоя процесса запись можно снова захватить по истечении срока. Publisher использует lease записи outbox, worker — lease задания в `deliveries`.

### Publisher: передача из outbox Notifications в RabbitMQ

**`notifications-publisher`** — отдельный постоянно работающий процесс Notifications с доступом к его базе и RabbitMQ.

1. Читает пачку записей outbox с `published_at IS NULL` и `available_at <= текущее время`, доступных для захвата.
2. Получает lease на выбранные записи, чтобы несколько экземпляров publisher не обрабатывали их одновременно.
3. Публикует по сообщению на запись, передавая только `delivery_id`. Локальное состояние получателя и подготовленное содержимое письма остаются в базе Notifications.
4. Дожидается подтверждения публикации от RabbitMQ. Использует `publisher confirms` — подтверждение приёма брокером — и `mandatory` — возврат сообщения, если его не удалось направить в очередь. Возвращённое сообщение не считается опубликованным, даже если брокер подтвердил его приём.
5. Сохраняет `published_at` только у успешно опубликованных записей и освобождает их lease. Остальные записи остаются для следующей попытки.
6. Продолжает обработку следующих пачек. Размер пачки и пауза при отсутствии записей или ошибке настраиваются; конкретные значения ещё не выбраны.

RabbitMQ использует сохраняемые после перезапуска exchange и quorum-очередь; сообщения публикуются как persistent, то есть предназначенные для сохранения брокером.

Если RabbitMQ недоступен, неопубликованные записи остаются в outbox. Если RabbitMQ принял сообщение, но publisher упал до сохранения `published_at`, сообщение будет опубликовано повторно с тем же `delivery_id`. Worker проверяет состояние задания в базе при каждом получении.

`published_at` означает передачу задания в RabbitMQ. Эта отметка не означает подготовку или отправку письма.

### Worker: подготовка и отправка письма

**`notifications-worker`** — отдельный процесс Notifications, который получает задания из RabbitMQ, готовит письма и передаёт их SMTP-серверу. SMTP-сервер — почтовый сервер, принимающий письма для дальнейшей доставки.

**Подтверждение обработки сообщения RabbitMQ (`ack`)** означает, что брокеру больше не нужно доставлять это сообщение worker. Оно отличается от подтверждения публикации, которое получает publisher.

1. Получает `delivery_id` из RabbitMQ, пока не подтверждая обработку сообщения.
2. Читает задание из `deliveries` и атомарно получает lease на его обработку. Повторное сообщение для завершённого задания подтверждает без повторной отправки. Наличие другого действующего владельца не разрешает начать параллельную отправку.
3. Читает актуальное локальное состояние получателя: активность, подписки и `tz`. При удалённом профиле отменяет доставку; для `service` и `bulk` без корректного `tz` окончательно пропускает её.
4. Если письмо ещё не подготовлено, запрашивает контакты в Auth, проверяет наличие активного пользователя и email, подставляет данные в шаблон и сохраняет содержимое письма и `Message-ID` — идентификатор письма. Сетевой запрос выполняется вне транзакции с блокировками строк; перед сохранением заново проверяются локальная активность и подписки. При повторах SMTP использует сохранённые содержимое и идентификатор.
5. Непосредственно перед отправкой снова проверяет, что отправка разрешена. Для welcome проверяет активность профиля и наличие адреса в подготовленном письме; для других видов писем также проверяет соответствующий флаг рассылки. Для классов `service` и `bulk` проверяет дневное окно в актуальном часовом поясе получателя, как описано в разделе «Дневное окно отправки по времени получателя».
6. Фиксирует начало попытки в `delivery_attempts` и передаёт письмо SMTP-серверу.
7. После подтверждения приёма SMTP-сервером одной транзакцией сохраняет успешную попытку, статус задания `sent` и `sent_at`, освобождает lease. Затем отправляет `ack` в RabbitMQ. При отмене или пропуске также сначала сохраняет результат в базе, затем подтверждает сообщение.

`sent` означает, что SMTP-сервер принял письмо. Это не подтверждение попадания во входящие получателя. Если worker упал после сохранения `sent`, но до `ack`, повторное сообщение не приводит к новой отправке.

### Временная ошибка отправки и повтор через outbox

Временная ошибка отправки — например, worker не смог подключиться к временно недоступному SMTP-серверу. В этом случае письмо не передано серверу, и отправку можно повторить позже. Ошибка публикации в RabbitMQ обрабатывается publisher по правилам предыдущего раздела.

Worker выбирает время следующей попытки и одной транзакцией в PostgreSQL Notifications:

1. Сохраняет результат текущей попытки в `delivery_attempts`: `outcome = retry`, описание ошибки в `error` и время завершения.
2. Обновляет существующее задание в `deliveries`: устанавливает статус `retry`, записывает выбранное время в `next_attempt_at` и освобождает lease.
3. Создаёт запись outbox с тем же `delivery_id`, `available_at`, равным выбранному времени, и `published_at = NULL`. Если для задания уже есть неопубликованная запись, обновляет её срок и сбрасывает `lease_token` и `lease_until` в той же транзакции. Старый publisher теряет право изменить эту запись: его запоздалое подтверждение не завершает новый повтор, а обработка ошибки не снимает lease нового владельца. Это правило действует и при неизменном `available_at`.

После успешного `COMMIT` worker подтверждает текущее сообщение RabbitMQ. Если транзакция не сохранилась, подтверждать сообщение нельзя: повтор ещё не обеспечен записью в базе. Новое welcome-задание в `deliveries` не создаётся; повторяется отправка существующего письма.

Пример: ошибка произошла в `12:00`, повтор назначен на `12:01`. Publisher не выбирает новую запись outbox до `12:01`. При следующем опросе после наступления этого времени он публикует тот же `delivery_id`, и worker снова пытается отправить подготовленное письмо. Если publisher был остановлен, запись остаётся в базе и будет обработана после запуска. Минута здесь — пример; интервалы и предел повторов ещё не выбраны.

### Постоянная ошибка и неопределённый результат отправки

При постоянной ошибке worker сохраняет окончательный отказ в `deliveries` и результат попытки в `delivery_attempts`; автоматическая отправка прекращается. Сообщение направляется в **DLQ** — сохраняемую очередь неуспешных сообщений — через настроенный **DLX**, exchange для таких сообщений. Источником состояния задания и восстановления остаётся PostgreSQL Notifications.

Ручной перезапуск окончательно неуспешных заданий и возврат сообщений из DLQ в обработку в текущий объём не входят. Статус `failed` и причины ошибок сохраняются для просмотра; согласованные автоматические повторы до окончательного отказа остаются.

Если соединение оборвалось после передачи письма SMTP-серверу, результат может быть неизвестен. Аналогичная ситуация возникает, если сервер подтвердил приём, но worker упал до сохранения результата в базе. Такую попытку нельзя считать заведомо неуспешной: письмо могло быть принято.

При восстановлении неопределённый результат отмечается в истории попыток как `uncertain` с `duplicate_risk = true`. Повтор проходит через outbox с тем же `delivery_id`, сохранённым содержимым и `Message-ID`. Возможен дубль письма: одинаковый `Message-ID` не гарантирует, что почтовый сервер исключит повтор. Восстановление незавершённого задания после сбоя учитывает истечение его lease; статус `sent` без подтверждённого результата не выставляется.

Фоновый цикл восстановления обрабатывает временные ошибки БД внутри своего цикла и повторяет проверку после настроенной паузы, сохраняя активные SMTP-отправки. При ошибке восстановления, чтения очереди или обработчика, требующей перезапуска, worker сначала прекращает приём новых заданий и дожидается завершения активных обработчиков. Они продолжают сохранять результат и подтверждать сообщения RabbitMQ; ошибка подтверждения одного сообщения не отменяет соседние отправки. Ошибки передаются управляющему циклу после этого ожидания. Принудительная отмена при истечении срока остановки процесса остаётся возможной; незавершённые попытки восстанавливаются как `uncertain`.

## Разделение писем по очередям и ресурсам

### Три очереди и один основной exchange

**Exchange** — узел RabbitMQ, который направляет опубликованные сообщения в очереди. **Routing key** — ключ маршрутизации сообщения. Для обычной доставки писем используется один сохраняемый exchange `notifications.email` типа `direct`: он выбирает очередь по точному совпадению routing key с ключом её привязки.

| Класс отправки | Routing key | Очередь | Назначение |
| --- | --- | --- | --- |
| `transactional` | `transactional` | `email.transactional` | Срочные служебные письма, включая welcome; обработка начинается максимально быстро |
| `service` | `service` | `email.service` | Несрочные уведомления пользователя, включая дайджесты лайков; обрабатываются независимо от массовых кампаний |
| `bulk` | `bulk` | `email.bulk` | Рассылка новинок и массовые рассылки, в том числе с персональным содержимым для каждого получателя; отправляются постепенно с ограничением скорости |

Все три очереди — сохраняемые quorum-очереди. Publisher публикует сообщение с телом, содержащим только `delivery_id`, и соответствующим routing key. Ключ передаётся как параметр публикации. Для существующих заданий соответствие такое: `welcome → transactional`, `likes → service`, `new_films → bulk`. При повторе задание сохраняет свой класс отправки.

Один основной exchange обслуживает все три очереди отправки. Описанные выше DLX и DLQ остаются служебными exchange и очередью для неуспешных сообщений.

### Отложенная отправка

Время отправки задаётся независимо от класса. Уже созданное задание ожидает в PostgreSQL Notifications: publisher выбирает его запись outbox только после наступления `available_at`, затем направляет в соответствующую очередь.

Массовая персональная рассылка, назначенная на завтра, после наступления её времени попадает в `email.bulk`. Срочное служебное письмо с назначенным временем попадает в `email.transactional`. Повтор после ошибки также сохраняет исходный класс, а новое `available_at` задаёт время следующей публикации. Отдельная очередь для ожидания будущего времени не требуется.

### Отдельные группы worker

Для каждой очереди запускается отдельная группа экземпляров `notifications-worker`. Код подготовки и отправки общий; очередь и допустимое число параллельных обработок задаются настройками запуска. Число экземпляров каждой группы можно менять независимо.

Для `email.transactional` выделяются собственные ресурсы обработки, которые не занимаются массовой рассылкой. Большая кампания в `email.bulk` не должна занимать все процессы и места для параллельной отправки срочных писем. Количество worker и параллельных отправок по классам ещё не выбрано.

### Срок отправки срочных писем

Для немедленных писем класса `transactional`, включая welcome, максимальная задержка составляет 3 минуты от сохранения исходного события до подтверждения приёма письма SMTP-сервером, при исправных компонентах и согласованной нагрузке. Для события Auth начало отсчёта — `COMMIT`, сохраняющий регистрацию и её outbox; задержка relay, Kafka, consumer, publisher и worker входит в эти 3 минуты. Для внешней немедленной заявки начало отсчёта — успешное сохранение заявки в Notifications.

Критерий относится к разрешённым отправкам на действующие адреса при доступности необходимых данных профиля. Он не означает доставку во входящие или прочтение письма и не применяется к специально отложенным письмам до наступления их `available_at`. Сбои компонентов обрабатываются по согласованным правилам сохранения и восстановления заданий.

Соблюдение срока проверяется нагрузочным сценарием: на фоне массовой рассылки поступают срочные события, для каждого измеряется полный срок до подтверждения SMTP. При проверке фиксируются входная нагрузка, число worker, лимиты SMTP и их распределение между классами. Наличие отдельных очередей само по себе не считается подтверждением выполнения этого критерия.

### Раздельная выборка publisher из outbox

Publisher выбирает готовые записи отдельно для каждого класса: проверяет `published_at IS NULL`, наступление `available_at` и доступность lease. Наличие большой пачки `bulk` не должно задерживать выборку новых `transactional` до полного завершения массовой рассылки.

В каждом проходе publisher обрабатывает ограниченные пачки классов, начиная с `transactional`, и регулярно переходит к `service` и `bulk`. Он не ожидает полного исчерпания одного класса перед переходом к остальным. Размеры пачек и интервалы настраиваются так, чтобы срочные задания быстро попадали в RabbitMQ, а остальные классы продолжали обрабатываться.

### Общий лимит SMTP и доля для срочных писем

**Лимит SMTP** — разрешённый почтовым провайдером объём отправок за определённое время. Если несколько worker используют одну учётную запись провайдера, они совместно расходуют её лимит. Отдельные очереди и процессы сами по себе этот лимит не разделяют.

Перед каждой SMTP-отправкой, включая повтор, worker должен получить разрешение общего ограничителя скорости. Состояние ограничителя общее для всех экземпляров worker, использующих эту учётную запись. Проверка и расход разрешённого объёма выполняются атомарно, чтобы параллельные worker не использовали одну и ту же доступную ёмкость.

Общий предел провайдера соблюдается совместно всеми тремя классами. Часть пропускной способности выделяется `transactional`; `service` и `bulk` не должны расходовать её целиком. Добавление экземпляров worker не увеличивает разрешённый объём отправок.

Если разрешение пока не получено, письмо ожидает следующей возможности отправки. Ожидание лимита не считается неудачной SMTP-попыткой: обращения к SMTP ещё не было. Задание остаётся восстанавливаемым в базе Notifications.

Для общего ограничителя выбран Redis и алгоритм token bucket, описанные ниже. Классам выделяются фиксированные доли без заимствования неиспользованной ёмкости. Численные лимиты ещё не выбраны.

### Общий ограничитель скорости в Redis

Redis хранит состояние ограничителя, общее для всех worker одной учётной записи SMTP-провайдера. Для каждой такой учётной записи учитываются четыре ограничения: общий лимит и отдельные доли `transactional`, `service`, `bulk`.

**Token bucket** — запас разрешений на отправку, который пополняется с заданной скоростью до установленного максимума. Для каждого ограничения Redis хранит число доступных разрешений и время последнего пополнения. Скорость пополнения определяет длительно допустимую скорость отправки, максимальный запас — допустимый кратковременный всплеск.

Сумма выделенных скоростей классов не превышает общий лимит провайдера. Скорости пополнения и максимальные запасы настраиваются под его правила; накопленные разрешения не должны допускать запрещённый провайдером всплеск отправок. Неиспользованная доля класса не передаётся другим классам: в частности, массовая рассылка не расходует долю срочных писем.

**Lua-скрипт** — небольшой код, выполняемый внутри Redis. Перед каждым обращением к SMTP worker вызывает один такой скрипт, который атомарно:

1. Рассчитывает доступные разрешения с учётом времени пополнения для общего ограничения и ограничения нужного класса.
2. Проверяет, есть ли разрешение в обоих запасах.
3. Если разрешения есть, списывает по одному из обоих запасов и возвращает разрешение на отправку.
4. Если хотя бы один запас недостаточен, не списывает разрешения и возвращает время ожидания до следующей проверки.

Проверка и списание выполняются одним вызовом скрипта. Параллельные worker не могут одновременно потратить одно оставшееся разрешение. После получения разрешения worker выполняет SMTP-отправку; повтор после ошибки также требует нового разрешения.

Если разрешения нет, worker откладывает задание через outbox: одной транзакцией сохраняет время следующей проверки в `deliveries.next_attempt_at`, новую запись outbox с тем же `delivery_id` и соответствующим `available_at`, освобождает lease. Только после успешного сохранения подтверждает текущее сообщение RabbitMQ. При следующем получении задания снова проверяет ограничитель. Ожидание лимита не записывается как неудачная SMTP-попытка и не увеличивает число попыток отправки.

Задания, подготовленные письма, история попыток и outbox остаются в PostgreSQL Notifications. Дополнительная таблица лимитов в PostgreSQL не требуется.

### Недоступность Redis и потеря состояния ограничителя

Если Redis недоступен или worker не может подтвердить получение разрешения, новая SMTP-отправка не начинается. Worker откладывает проверку через outbox, сохраняя задание в PostgreSQL. Пауза между проверками настраивается; обходить ограничитель и отправлять без разрешения нельзя.

Потеря состояния Redis не означает, что лимит SMTP-провайдера снова полностью свободен: часть разрешений могла быть потрачена до сбоя. После такой потери новые отправки возобновляются только после восстановления безопасного состояния ограничителя либо выдерживания паузы, учитывающей ранее использованный лимит. Автоматически выдавать полный запас разрешений из-за отсутствия ключей нельзя. Конкретный порядок восстановления и длительность паузы уточняются по ограничениям провайдера.

## Выпуски дайджестов: состав, аудитория и создание заданий

**Выпуск дайджеста** — сохранённый запуск одного вида рассылки за определённый период. Он содержит выбранные данные, список получателей и прогресс создания заданий. **Снимок выпуска** — зафиксированные в базе состав и аудитория; повторная обработка выпуска использует этот снимок.

**Задание `delivery`** — отправка одного письма одному получателю. Выпуск может содержать много заданий. Для каждого вида дайджеста создаётся не более одного задания на получателя в рамках выпуска.

### Начальные настройки дайджестов

| Настройка | Начальное значение | Значение для пользователя |
| --- | --- | --- |
| `likes_min_delta` / `NOTIFICATIONS_LIKES_MIN_DELTA` | `3` | Комментарий включается в дайджест при приросте не меньше трёх лайков от последней отправленной точки отсчёта |
| `likes_interval_seconds` / `NOTIFICATIONS_LIKES_INTERVAL_SECONDS` | `86400` | Дайджест лайков формируется раз в сутки |
| `films_interval_seconds` / `NOTIFICATIONS_FILMS_INTERVAL_SECONDS` | `604800` | Дайджест новинок формируется раз в семь суток |
| `films_per_digest` / `NOTIFICATIONS_FILMS_PER_DIGEST` | `20` | Только самые свежие новинки по дате публикации в каталоге; остальные не переносятся в будущие выпуски |
| Дневное окно для `service` и `bulk` | С `10:00` включительно до `20:00` исключительно по часовому поясу получателя | Первичные отправки и повторы выполняются в дневное время пользователя |

Периоды формирования выпусков задаются в UTC с фиксированной точкой отсчёта `1970-01-01 00:00:00 UTC`, как в текущем scheduler. Для выбранных интервалов это означает начало подготовки выпуска лайков ежедневно в `00:00 UTC`, новинок — по четвергам в `00:00 UTC`. Подготовка выпуска и отправка писем разделены: каждому получателю назначается время в его дневном окне. Перезапуск процесса не сдвигает границы периодов.

Это начальные значения эксплуатационной конфигурации. Они передаются явно через настройки и могут быть изменены; обязательность параметров при запуске сохраняется. Общее расписание определяет подготовку выпусков, а часовой пояс профиля — допустимое время отправки конкретному получателю.

Порог лайков применяется отдельно к каждому комментарию. Прирост на двух комментариях по два лайка не проходит порог `3`. При этом прирост накапливается от последней успешной отправки, а не только за последние сутки: ежедневная проверка его не обнуляет.

### Дневное окно отправки по времени получателя

Дайджесты лайков и новинок, а также другие рассылки классов `service` и `bulk` отправляются с `10:00` включительно до `20:00` исключительно по локальному времени получателя. Для срочных писем класса `transactional`, включая welcome, сохраняется отправка сразу после события.

Часовой пояс берётся из актуального `tz` локального профиля Notifications, полученного из Auth. Используется именованный часовой пояс IANA, например `Europe/Moscow`, с его правилами изменения смещения. Дата следующего разрешённого времени рассчитывается в этом часовом поясе, затем переводится в UTC для хранения в `deliveries.next_attempt_at` и `outbox.available_at`.

При создании задания scheduler выбирает ближайший допустимый момент не раньше готовности задания или явно назначенного времени:

1. До `10:00` по времени получателя — в `10:00` этого местного дня.
2. С `10:00` до `20:00` — сразу, если остальные условия отправки выполнены.
3. В `20:00` и позже — в `10:00` следующего местного дня.

Например, если выпуск подготовлен в `00:00 UTC`, для получателя с `tz = Europe/Moscow` это `03:00`. Его задание получает `available_at = 07:00 UTC`, что соответствует `10:00` по Москве.

Worker повторно проверяет дневное окно непосредственно перед каждой SMTP-отправкой по актуальному часовому поясу профиля. Это требуется и после задержки в RabbitMQ, ожидания лимита Redis, изменения `tz` или восстановления процесса. Если окно закрылось, worker откладывает то же задание до следующего разрешённого времени: одной транзакцией обновляет `next_attempt_at`, сохраняет запись outbox с соответствующим `available_at` и освобождает lease; после `COMMIT` подтверждает текущее сообщение RabbitMQ. Ожидание дневного окна не считается SMTP-попыткой.

При временной ошибке сначала рассчитывается время повтора по правилам задержки, затем оно переносится вперёд до ближайшего разрешённого дневного времени, если необходимо. Повтор дайджеста новинок может состояться на следующий день; ждать следующего еженедельного выпуска для него не требуется. Повторы сохраняют прежние `delivery_id`, состав и содержимое письма.

Если `tz` отсутствует или некорректен, рассылки `service` и `bulk` этому получателю окончательно пропускаются с причиной `invalid_timezone`. Scheduler исключает такой профиль из аудитории; Campaign API сохраняет пропуск без создания delivery/outbox. Уже созданное задание worker переводит в `skipped`, освобождает lease и прекращает повторы через outbox, затем подтверждает сообщение RabbitMQ. Пропуск не является SMTP-попыткой и не меняет счётчик последней успешной отправки лайков. Восстановление заданий также не возобновляет такую доставку.

После появления корректного `tz` пользователь может попасть в будущие выпуски; завершённые пропуски и точные повторы принятых кампаний не переоткрываются. Общий `fallback_tz` не используется для разрешения отправки. Класс `transactional`, включая welcome, по-прежнему не зависит от дневного окна; требование `tz` при создании новых пользователей действует независимо от класса письма.

Дневное окно ограничивает время начала передачи письма SMTP-серверу. Фактическое поступление во входящие зависит от дальнейшей доставки почтовым провайдером.

### Что фиксируется в выпуске

Для дайджеста новинок сохраняются:

1. Идентификаторы до 20 самых свежих фильмов из ещё не обработанных `film_announcements` (лимит настраивается). Порядок выбора: `catalog_published_at` по убыванию, затем `film_id` по возрастанию. Все кандидаты закрепляются за выпуском, выбранные получают `included_in_digest=true`; остальные не отправляются и не переносятся в будущие выпуски. Выпуск без аудитории также расходует все свои новинки.
2. Идентификаторы получателей: активные на момент отбора профили с `new_films = true` и корректным `tz`.

Список фильмов и лимит сохраняются при создании выпуска; изменение настройки их не меняет. При подготовке письма worker одним запросом с сохранённым лимитом читает последние локальные версии выбранных карточек. Для старых неподготовленных заданий без лимита выпуска действует текущая настройка worker. После первой подготовки содержимое конкретного письма сохраняется для повторов.

Для дайджеста лайков сохраняются:

1. Идентификаторы комментариев, прошедших порог, их авторы и выбранные значения `likes_count`.
2. Список получателей из авторов выбранных комментариев: активные профили с `likes = true` и корректным `tz`.

Несколько комментариев одного пользователя объединяются в одно задание. Значения счётчиков для этого задания фиксируются при создании выпуска; последующие события меняют текущие счётчики, но не сохранённый состав. Один комментарий не резервируется в двух незавершённых выпусках или доставках одновременно. Проверка scheduler и резервирование не меняют `last_sent_likes_count` и `last_notification_sent_at`.

Новые профили и пользователи, включившие флаг после фиксации аудитории, не добавляются в уже созданный выпуск. При этом снимок аудитории не заменяет повторную проверку перед отправкой: удалённому пользователю или пользователю, отключившему соответствующий флаг, письмо не отправляется.

### Транзакция создания выпуска

Scheduler выполняет одной транзакцией PostgreSQL Notifications:

1. Проверяет, существует ли выпуск этого вида за выбранный период. Пара `(kind, period_start)` уникальна: повторный запуск продолжает существующий выпуск.
2. Создаёт запись выпуска в `schedule_runs`.
3. Сохраняет выбранные данные и закрепляет их за выпуском: для новинок — отметки в `film_announcements`, для лайков — комментарии и значения счётчиков в `schedule_items`.
4. Сохраняет аудиторию в `schedule_recipients`.

Запись выпуска, его состав, резервирование данных и аудитория сохраняются вместе. Сбой до `COMMIT` откатывает всё. После `COMMIT` следующие этапы работают с сохранённым снимком. Конкурентные экземпляры scheduler не создают второй выпуск того же вида за тот же период и не резервируют одни данные одновременно для разных выпусков.

### Создание заданий пачками

**Курсор обработки** — сохранённая позиция в списке получателей выпуска, до которой задания уже созданы. Scheduler получает lease на обработку выпуска и проходит сохранённую аудиторию в устойчивом порядке.

Для каждой ограниченной пачки получателей он выполняет отдельную транзакцию:

1. Создаёт `deliveries` — по одному заданию на получателя. Уникальность `(run_id, user_id)` защищает от повторного создания задания при восстановлении.
2. Создаёт `delivery_items`: выбранные `film_id` для новинок либо `review_id` и сохранённые значения счётчиков для лайков.
3. Рассчитывает каждому получателю ближайшее допустимое время в его дневном окне, сохраняет его в `deliveries.next_attempt_at` и создаёт запись outbox с таким же `available_at`. Если при обработке пачки корректный `tz` уже отсутствует, пропускает получателя без задания и продвигает курсор; резервирование комментариев не должно блокировать будущие выпуски. Publisher направляет готовые задания новинок в `email.bulk`, лайков — в `email.service`.
4. Продвигает курсор выпуска до обработанной позиции. Если получатели закончились, отмечает завершение создания заданий.

Задания, их состав, outbox и курсор пачки сохраняются одним `COMMIT`. Сбой до него откатывает всю пачку; сбой после него позволяет продолжить со следующей позиции. Сбой одного worker отправки не останавливает создание заданий остальным получателям.

Завершение создания заданий выпуска не означает, что все письма уже отправлены. Результат отправки хранится отдельно в каждом `delivery`; ошибки и повторы обрабатываются по общим правилам. Для лайков точка отсчёта обновляется только после успешной отправки и только до значений из отправленного письма.

## Файловые шаблоны и темы писем

Шаблоны пока хранятся файлами в `services/notifications/src/notifications/templates/` и поставляются вместе с сервисом. `template_id` выбирает зарегистрированный шаблон из этого набора. Хранение шаблонов в БД и API их редактирования в текущий вариант не входят.

Источник темы зависит от способа создания письма:

| Сценарий | Откуда берётся тема |
| --- | --- |
| Внешняя заявка через API | Из обязательного поля `subject`, переданного вызывающим сервисом |
| Welcome, внутренние дайджесты лайков и новинок | Из отдельного файла темы рядом с HTML-шаблоном: `welcome.subject.txt`, `likes.subject.txt`, `new_films.subject.txt` |

Тексты тем не хранятся в Python-словарях, условных ветках worker или других участках программной логики. Для внутренних писем worker читает файл темы соответствующего шаблона. Изменение темы такого письма требует обновления файлов сервиса, как и изменение его HTML-шаблона.

Для внешней заявки Notifications сохраняет переданный `subject` вместе с заданием и использует его как тему письма. Выбранный `template_id` не заменяет эту тему значением из файла или кода. `subject` должен быть непустой строкой без переводов строк; отсутствующее или некорректное значение отклоняется при приёме заявки, без подстановки темы по умолчанию. Переданный `subject` не исполняется как шаблон.

При первой подготовке любого письма worker сохраняет итоговые тему и тело вместе с `Message-ID`. Повтор использует эту сохранённую версию письма, даже если файлы шаблонов и тем после подготовки изменились.

## Внешние события свободного формата

Notifications принимает внешние заявки по варианту из `task.md`: вызывающий сервис передаёт получателя, выбранный шаблон, тему и основной текст сообщения. Одна рассылка определяется `campaign_id` и может поступать несколькими батчами. Каждый элемент батча описывает одно письмо одному пользователю. В массовой персональной рассылке вызывающий сервис подготавливает свой текст для каждого `user_id`; одинаковая рассылка использует одинаковые тему и текст для выбранных получателей.

Для согласованного сценария ручной рассылки вызывающим сервисом является backend админки, а инициатором — вошедший в неё менеджер. Реализация интерфейса и backend админки в текущий объём не входит. На стороне Notifications предусматриваются проверка сервисного ключа и сохранение автора кампании.

Общие поля батча:

| Поле | Назначение |
| --- | --- |
| `batch_id` | Стабильный UUID пачки внутри рассылки |
| `created_by_user_id` | Обязательный UUID менеджера, создавшего рассылку; backend админки получает его из проверенной сессии или токена |
| `items` | Непустой список писем описанного ниже формата |

Поля одного элемента батча:

| Поле | Назначение |
| --- | --- |
| `user_id` | Идентификатор получателя; email, имя и фамилию worker получает из Auth при подготовке письма |
| `template_id` | Идентификатор зарегистрированного в Notifications шаблона, разрешённого для внешних заявок |
| `subject` | Обязательная готовая тема сообщения; используется без подмены темой шаблона |
| `text` | Готовый основной текст сообщения, который worker вставляет в выбранный шаблон |
| `type` | Канал доставки: в первой версии поддерживается `email`; расширение на `sms` и `push` предусматривается отдельно |
| `available_at` | Необязательное время, раньше которого нельзя начинать отправку; правила приведены в следующем разделе |

Вызывающий сервис назначает стабильные UUID `campaign_id` для всей рассылки и `batch_id` для каждой её пачки. Повтор защищается парой `(campaign_id, batch_id)`; отдельный `request_id` для элемента не требуется. Повтор того же батча возвращает подтверждение его предыдущего приёма и не создаёт новые задания. Тот же `batch_id` с другим содержимым отклоняется как конфликт. Если `available_at` не передан, назначенное при первом приёме время сохраняется и не пересчитывается при повторе запроса.

Точный повтор уже принятого батча подтверждает факт его сохранения и не запускает повторную проверку допуска получателей. Изменившиеся флаги учитываются worker перед отправкой, но не меняют результат повторного приёма того же батча.

`created_by_user_id` включается в сравнение содержимого батча при повторном приёме. Смена автора при повторе того же `batch_id` является конфликтом содержимого. Проверка сервисного ключа обязательна и для точного повтора уже принятого батча.

В одной рассылке предусмотрено одно письмо на `user_id`. Повтор пользователя внутри батча отклоняется как ошибка схемы; попытка добавить его новым батчем в ту же рассылку отклоняется как конфликт. Проверка повтора уже принятого батча выполняется раньше этой проверки: безопасная повторная передача батча не является конфликтом получателей.

### Автор рассылки

Первый успешно принятый батч сохраняет `created_by_user_id` в записи `campaigns` вместе с созданием рассылки. Все следующие батчи с тем же `campaign_id` должны содержать того же автора. Новый батч с другим автором отклоняется целиком с `409 campaign_author_conflict`; сохранённый автор не изменяется. Конкурентный приём первых батчей согласуется той же транзакционной блокировкой кампании, что и остальные проверки приёма.

Автор кампании и получатель письма — разные роли: `created_by_user_id` относится ко всей кампании, а `items[].user_id` — к адресату конкретного письма. Автор не становится получателем автоматически; его email и флаги подписок не используются для допуска адресатов.

Поле фиксирует, кто создал кампанию, и не меняется при добавлении батчей, закрытии загрузки или отправке писем. Backend админки при продолжении загрузки сохраняет исходного автора, даже если операцию выполняет другой уполномоченный менеджер. Для закрытия и чтения статуса повторно передавать автора не требуется. Право менеджера работать с кампанией проверяет backend админки; само значение `created_by_user_id` не является подтверждением права доступа.

Ранее сохранённым кампаниям без сведений об авторе вымышленный пользователь не назначается. Для них отсутствие исторического значения явно сохраняется; обязательность автора относится к новым кампаниям после введения этого контракта.

### Что передаёт вызывающий сервис и что делает шаблон

Вызывающий сервис сам выбирает фильмы, рассчитывает предложения и превращает эти данные в готовый `text`. Например, он передаёт тему «Ваша подборка» и текст «Рекомендуем посмотреть „Прибытие“ и „Интерстеллар“». Notifications не требует отдельного массива фильмов, словаря промокодов, `data` или `recipient_data` для такого сообщения.

Шаблон задаёт оформление, приветствие и подпись письма. Для внешних заявок шаблоны используют общий набор данных: переданные `subject` и `text`, имя и фамилию из ответа Auth при подготовке письма. Worker может получить итоговое письмо вида: «Здравствуйте, Анна! Рекомендуем посмотреть „Прибытие“ и „Интерстеллар“» в оформлении выбранного шаблона.

`subject` и `text` являются содержимым сообщения, а не исполняемыми шаблонами. В первой версии `text` — обычный текст; при включении в HTML-письмо он отображается как текст, с сохранением переносов строк. Код шаблона хранится в Notifications и не передаётся вызывающим сервисом. Внешние письма используют общую систему шаблонизации с welcome и внутренними дайджестами; правила подготовки данных этих внутренних сценариев сохраняются.

### Приём и отправка

1. Notifications проверяет сервисный ключ, поля заявки, автора кампании, поддерживаемый канал, регистрацию выбранного шаблона для внешних заявок и совместимость шаблона с каналом.
2. Одной транзакцией сохраняет батч, его получателей и исходные поля писем, результаты пропуска получателей, задания разрешённым получателям и соответствующие записи outbox. Время каждого задания рассчитывает по правилам `available_at` и дневного окна. Подтверждает приём только после `COMMIT`.
3. Publisher передаёт в RabbitMQ только `delivery_id` по согласованным правилам.
4. Worker проверяет локальную активность, соответствующую подписку и допустимость `tz`, получает контакты из Auth и формирует тело письма по шаблону. Сохраняет его вместе с переданной темой `subject` и `Message-ID`; повтор использует это подготовленное письмо.
5. Перед SMTP worker проверяет дневное окно и лимиты скорости. При повторах использует сохранённое письмо; ошибки и отложенные попытки обрабатываются по общим правилам.

Канал `type` и класс отправки — разные признаки: `email` задаёт способ доставки, а `transactional`, `service` или `bulk` — очередь и правила обработки. Класс и необходимый флаг подписки определяются зарегистрированным шаблоном. Шаблоны массовых персональных предложений относятся к `bulk` и требуют `marketing = true`.

В первой версии запросы с `type = sms` или `type = push` отклоняются до создания задания как неподдерживаемый канал. Поддержка этих каналов потребует отдельных контактов и отправителей; существующие email-очереди для них не используются.

### Схема заявки и проверка подписок

Каждый шаблон, доступный для внешних заявок, связан с явной схемой принимаемых полей, поддерживаемым каналом, классом отправки и необходимым флагом подписки. Схема проверяется при приёме API; HTML-файл сам по себе не заменяет схему. В текущем контракте содержимое передаётся через `subject` и `text`, отдельные данные о фильмах или предложениях не добавляются.

Каждый батч проверяется целиком до сохранения. Ошибка формата, неизвестный шаблон, неподдерживаемый канал или несоответствие схеме в любом элементе отклоняют весь батч; API возвращает ошибки с указанием элемента и поля. Частично принятых батчей из-за ошибки формата нет.

Батч содержит непустой список `items`. Схема проверяет UUID идентификаторов, в том числе обязательный `created_by_user_id`, отсутствие повторных `user_id`, обязательные поля и их типы, непустые `subject` и `text`, однострочную тему, а также часовой пояс переданного `available_at`. Лимиты количества элементов, длины строк и размера запроса задаются явно в контракте реализации. Дополнительные неизвестные поля отклоняются.

Настройки получателя проверяются отдельно от формата заявки. Для массовых персональных предложений требуется активный профиль и `marketing = true`. Выключенный флаг не отклоняет весь батч: получатель учитывается в результате рассылки как пропущенный, с причиной `subscription_disabled`, и отправка ему не назначается. Если флаг выключен после приёма заявки, worker повторно проверяет его непосредственно перед SMTP и прекращает отправку этому получателю. Такой результат также входит в число пропущенных, а не в число ошибок отправки. Остальные получатели обрабатываются независимо.

Удалённый профиль даёт пропуск `profile_deleted`; отсутствие корректного `tz` для `service`/`bulk` — `invalid_timezone`. Наличие email проверяется позднее worker через Auth при подготовке: отсутствие адреса даёт `no_email` и отражается в статистике кампании. Campaign API за контактами в Auth не обращается. Если локального профиля ещё нет, API отклоняет весь батч с `409 profile_not_ready` и списком соответствующих `user_id`, ничего не сохраняя. Вызывающий сервис может повторить тот же батч после появления профилей; отсутствие локальной копии не считается окончательным результатом отправки.

### Методы приёма и завершения загрузки

`POST /api/v1/notifications/campaigns/{campaign_id}/batches` принимает объект с `batch_id`, `created_by_user_id` и массивом `items` описанного выше формата. Первый принятый батч создаёт рассылку и сохраняет автора, следующие дополняют её. После успешного сохранения API возвращает `202 Accepted` с `campaign_id`, `batch_id`, `status = accepted` и числом элементов батча. Подтверждение означает сохранение заявки, а не успешную отправку всех писем; пропущенные получатели тоже входят в сохранённый батч и доступны в статистике.

Каждый принятый батч сразу допускается к обработке по `available_at`. Ждать остальных батчей для отправки не требуется; черновика с блокировкой отправки до полной загрузки нет.

Когда вызывающий сервис получил подтверждение всех своих батчей, он вызывает `POST /api/v1/notifications/campaigns/{campaign_id}/close` и передаёт `expected_batches` — положительное ожидаемое число уникальных батчей. Notifications сверяет его с числом сохранённых батчей и закрывает приём новых данных в эту рассылку. Успешный ответ — `200 OK` с `campaign_id` и `intake_status = closed`. Несовпадение даёт `409 batch_count_mismatch` и оставляет приём открытым. Закрытие и приём очередного батча согласуются транзакционно, чтобы после закрытия не появился новый батч.

Повтор команды закрытия с тем же числом батчей возвращает успешный результат. После закрытия новый батч отклоняется с `409 campaign_closed`, но точный повтор уже принятого батча по-прежнему возвращает подтверждение без повторной отправки. Закрытие загрузки не останавливает принятые задания и их повторы.

Неизвестная рассылка при запросе статуса или закрытии даёт `404 campaign_not_found`. Ошибки схемы батча дают `422 validation_error`; повторное использование идентификатора батча с другим содержимым и повтор получателя новым батчем дают `409` с различимыми кодами ошибок. Неуспешная транзакция не подтверждается как принятая.

### Хранение и статус рассылки

В PostgreSQL Notifications сохраняются рассылки `campaigns` с автором `created_by_user_id`, принятые батчи `campaign_batches` и записи получателей `campaign_recipients`. Получатель учитывается в рассылке даже при пропуске, когда SMTP-задание ему не создаётся. Для отправляемого письма запись получателя связана с существующим механизмом `deliveries` и outbox. Ограничения уникальности на `(campaign_id, batch_id)` и `(campaign_id, user_id)` защищают от конкурентного создания дублей.

`GET /api/v1/notifications/campaigns/{campaign_id}` возвращает идентификатор, `created_by_user_id` (либо `null` для исторической кампании с неизвестным автором), `intake_status` (`open` или `closed`), общий `status`, число принятых батчей и счётчики:

| Счётчик | Что учитывается |
| --- | --- |
| `total` | Все получатели принятых батчей, включая пропущенных |
| `sent` | Письма, приём которых подтвердил SMTP-сервер |
| `failed` | Письма с окончательной ошибкой после прекращения повторов |
| `skipped` | Пропуски из-за подписки, удаления профиля, отсутствия email или корректного `tz`, включая отмену по этим причинам перед отправкой |
| `pending` | Все ещё не завершённые задания, включая подготовку, отправку, ожидание `available_at`, дневного окна, лимита или следующей попытки |

Всегда выполняется `total = sent + failed + skipped + pending`. Счётчики вычисляются по согласованному снимку сохранённых записей PostgreSQL, а не по числу обработанных сообщений RabbitMQ. Повторные публикации и SMTP-попытки не увеличивают `total`. Для `skipped` возвращается разбивка по причинам. Внутренние статусы `cancelled` и `skipped` отображаются в API как пропуски с сохранённой причиной. `sent` означает принятие SMTP-сервером, а не подтверждённое попадание во входящие.

Для окончательных ошибок API также возвращает разбивку по причинам, в том числе выделяет неопределённый результат SMTP после прекращения повторов. Такое письмо входит в `failed`, но этот результат не доказывает, что сервер его не принял: действует ранее согласованное ограничение неопределённой SMTP-доставки.

Пока `intake_status = open`, итог рассылки не считается окончательным даже при `pending = 0`: вызывающий сервис ещё может прислать батчи. До закрытия загрузки и завершения всех принятых заданий общий статус — `in_progress`; счётчики показывают текущий частичный результат. После закрытия при `pending = 0` статус определяется так:

- `completed` — все письма отправлены, `sent = total`;
- `partially_completed` — часть отправлена, а часть завершилась ошибкой или пропуском;
- `failed` — ни одно письмо не отправлено и есть окончательные ошибки;
- `skipped` — все получатели пропущены.

Например, `total = 1000`, `sent = 600`, `failed = 20`, `skipped = 80`, `pending = 300` означает, что обработка продолжается. Статус `partially_completed` появляется только после завершения загрузки и всех оставшихся заданий. Если вызывающий сервис не закрыл загрузку, API продолжает показывать открытый приём и промежуточный результат.

### Доступ к API

К API кампаний обращается backend админки по выделенному сервисному ключу в заголовке `X-API-Key`. Ключ хранится на backend и в секретной конфигурации Notifications; в браузер менеджера он не передаётся. Запросы передаются по защищённому соединению. Выдача отдельных сервисных ключей другим интеграциям не означает выдачу личных ключей менеджерам.

Notifications проверяет ключ перед приёмом батча, закрытием загрузки и чтением статуса. Отсутствующий, неверный или отозванный ключ даёт `401 Unauthorized`; кампании не создаются и не раскрываются. Процесс campaign API не запускается без настроенного механизма проверки сервисного ключа. Отзыв ключа прекращает доступ к API, но не отменяет ранее принятые задания на отправку.

Backend админки отвечает за вход менеджера, проверку его прав создавать, продолжать, закрывать и просматривать рассылки, а также за достоверность переданного `created_by_user_id`. Notifications доверяет этому полю только в запросе, прошедшем проверку сервисного ключа. Личный JWT менеджера в API кампаний не передаётся; API пользовательских настроек подписок проверяет JWT и актуальность токена через внутренний API Auth.

Админка, её backend, пользовательские роли и интерфейс управления ключами в текущем проекте не реализуются. Здесь фиксируется контракт взаимодействия с будущим backend админки; автор кампании сохраняется для учёта и просмотра, а не для автоматического ограничения доступа только её создателем.

## Время внешней заявки на рассылку

Во внешней заявке время, раньше которого нельзя начинать отправку, называется `available_at`. Отдельное поле `not_before` в контракт заявки не вводится. Если время не передано, заявка допускает начало обработки сразу после приёма, с соблюдением дневного окна и остальных ограничений отправки.

`available_at` заявки задаёт исходную нижнюю границу времени отправки. При создании конкретного задания Notifications выбирает ближайший допустимый момент не раньше этой границы и текущего времени, учитывая дневное окно получателя. Выбранное время сохраняется одновременно в существующих `deliveries.next_attempt_at` и `outbox.available_at`. Для неизвестного или некорректного `tz` классы `service` и `bulk` получают окончательный пропуск `invalid_timezone`, без отложенной проверки профиля. Время хранится в UTC.

Например, заявка с `available_at = 00:00 UTC` для получателя в `Europe/Moscow` при своевременной подготовке задания получает `deliveries.next_attempt_at = outbox.available_at = 07:00 UTC`, то есть `10:00` по местному времени.

Исходное `available_at` заявки сохраняется и не меняется при повторах отдельных писем. Повтор после ошибки, ожидание дневного окна или разрешения Redis меняют время конкретного задания и создают соответствующую запись outbox по уже согласованным правилам. Назначенное время не гарантирует отправку ровно в этот момент: отправка может начаться позже из-за ограничений или задержек обработки.
