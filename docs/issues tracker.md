Здравствуйте ! Отлично поработали ! Оставил небольшие рекомендации:

1. API принимает события, которые невозможно отправить в Kafka

[event_schema.py](https://github.com/feodal01/ugc_sprint_1/blob/main/services/ugc-events/src/services/event_schema.py#L10)

Для строк задана только минимальная длина, поэтому схема принимает, например, событие с полем `page` размером два мегабайта, которое также проходит лимит Nginx в восемь мегабайт. Производитель с текущими настройками отклонит такое сообщение по [ограничению размера Kafka-запроса](https://aiokafka.readthedocs.io/en/stable/_modules/aiokafka/producer/producer.html), а общий обработчик `KafkaError` вернёт 503 вместо ошибки входных данных. Ограничьте размеры полей и проверяйте размер каждого готового конверта в байтах до отправки всего пакета, возвращая 413 или 422 без частичной публикации.

**Исправлено.** У строковых полей отдельные `max_length` (page 2048, element_type 64, element_id 256, quality 32, фильтры 20×20×256, `X-Request-Id` 256). До `publish_batch` размер каждой записи считается через `DefaultRecordBatchBuilder.estimate_size_in_bytes`, как в aiokafka, против того же `max_request_size`. Схема → 422, слишком большой конверт → 413, пакет целиком не публикуется. Те же лимиты в ETL. Худший валидный UTF-8 конверт ~40% от 1 МБ.

2. Ограничение размера пакета приводит к потере уже прочитанных событий

[consumer.py](https://github.com/feodal01/ugc_sprint_1/blob/main/services/ugc-etl/src/services/consumer.py#L70)

После `getmany()` функция возвращает пакет сразу при достижении лимита байтов, оставляя остальные полученные сообщения необработанными. Позиция Kafka уже продвинулась для всей выдачи, поэтому последующий `commit()` без аргументов подтвердит также потерянный остаток, как следует из [правил работы со смещениями](https://aiokafka.readthedocs.io/en/stable/consumer.html#offsets-and-consumer-position). Сохраняйте остаток для следующего пакета, передавайте вместе с сообщением его раздел и смещение и подтверждайте только непрерывную последовательность успешно обработанных записей каждого раздела.

**Исправлено.** Ответ `getmany` целиком кладётся в хвост. Пока хвост не пуст, нового fetch нет: в пакет уходит кусок до `etl_batch_size` / 8 МБ. `commit({partition: last.offset + 1})` только по обработанным записям. Сообщение > 1 МБ — в DLQ и лог, не в ClickHouse.

3. Фоновая обработка может завершиться незаметно для проверки здоровья

[pipeline.py](https://github.com/feodal01/ugc_sprint_1/blob/main/services/ugc-etl/src/services/pipeline.py#L71)

`ensure_schema()` повторно вызывается внутри фоновой задачи до входа в блок обработки исключений, хотя схема уже проверена в `lifespan`. Если этот повторный вызов завершится ошибкой, задача остановится, а HTTP-приложение продолжит работать и после восстановления зависимостей сможет отвечать 200, поскольку health не проверяет состояние задачи. Уберите повторную инициализацию либо включите её в управляемые повторные попытки, сохраняйте задачу в состоянии приложения и сообщайте о её неожиданном завершении через health и журнал ошибок.

**Исправлено.** Повторный `ensure_schema()` убран из `run_forever`; схема остаётся в `lifespan`. Задача `etl-pipeline` лежит в `app.state.pipeline_task`, при неожиданном завершении пишется error. Health отдаёт `pipeline`: нет задачи или `done()` — 503, даже если ping Kafka и ClickHouse зелёные.

Приём событий не ограничивает частоту запросов
https://github.com/feodal01/ugc_sprint_2/blob/main/services/ugc-events/src/api/v1/events.py#L48

Ограничение числа событий в одном пакете есть, но ограничений на число пакетов от одного пользователя нет; в Nginx ограничение частоты включено только для Auth. Пользователь с действующим токеном может непрерывно отправлять пакеты и занять ресурсы API и Kafka. Добавьте лимит по user_id, дополнительный лимит по IP на входе и ответ 429 с Retry-After при превышении.

**Исправлено:** в API добавлен атомарный лимит Redis по `user_id` из проверенного JWT — всплеск до 10 пакетов и пополнение 1 пакет/с; смена токена не сбрасывает счётчик.
В Nginx добавлен отдельный лимит по IP: 20 запросов/с и burst 20.
При превышении лимита возвращается 429 с `Retry-After` без отправки пакета в Kafka.
При ошибке соединения или таймауте Redis действует fail-open: проверка пользовательского лимита пропускается, пакет принимается при исправной Kafka, ошибка записывается в warning. Лимит Nginx по IP сохраняется.
Health при недоступном Redis возвращает 200 со статусом `degraded`; отказ Kafka по-прежнему даёт 503. Повторы Redis отключены, circuit breaker пока нет.

Время события проверяется только на наличие часового пояса
https://github.com/feodal01/ugc_sprint_2/blob/main/services/ugc-events/src/services/event_schema.py#L77

Валидатор принимает любое время с часовым поясом, включая проверенный пример 2500-01-01T00:00:00Z. Клиент может отправлять события из далёкого будущего или произвольных прошлых месяцев, и они будут искажать отчёты по времени и создавать лишние месячные разделы в ClickHouse. Задайте допустимое отклонение в будущее и глубину приёма старых событий, учитывая повторную отправку накопленных событий, а отклонённые значения возвращайте как 422.

**Исправлено.** API фиксирует одно время UTC `received_at` для пакета и до лимитера
проверяет включённое окно от семи суток назад до пяти минут вперёд. При нарушении
возвращает `422` с индексами проблемных событий, без публикации всего пакета.
Ограничения вынесены в конфигурацию API и ETL, сервисные `.env.example` и общий Compose.
ETL проверяет окно относительно сохранённого `received_at`, отправляет нарушения в DLQ
и допускает задержанную обработку корректных событий. Тесты используют фиксированные часы.

Health сервиса событий может возвращать 200 после отключения Kafka
https://github.com/feodal01/ugc_sprint_2/blob/main/services/ugc-events/src/services/kafka_broker.py#L42

Проверка partitions_for() может вернуть уже известные producer сведения о партициях без нового обращения к брокеру. Поэтому health может сообщать о готовности сервиса, хотя новые запросы публикации уже завершаются ошибкой. Запрашивайте обновление метаданных с коротким таймаутом и возвращайте 503 при ошибке, как уже сделано в KafkaEventConsumer.ping(); получение известных партиций показано в исходном коде aiokafka.

**Исправлено.** `AIOKafkaEventBroker.ping()` обновляет метаданные через
`force_metadata_update()` с таймаутом две секунды и затем проверяет партиции топика.
Отказ обновления, ошибка Kafka, таймаут или отсутствие партиций приводят к `503`.
Регрессионные тесты покрывают кешированные метаданные, ошибки, таймаут и отмену.
На отдельном экземпляре API проверен цикл Docker/HTTP: `200` → потеря связи с Kafka
при доступном Redis → `503` примерно за две секунды → восстановление связи → `200`.

Health ETL считает работающим цикл, который больше не обрабатывает события
https://github.com/feodal01/ugc_sprint_2/blob/main/services/ugc-etl/src/api/v1/health.py#L51

Статус pipeline зависит только от того, завершилась ли фоновая задача, а run_forever() перехватывает ошибки и продолжает работать. Если пакет постоянно падает при вставке или отправке в очередь ошибок, Kafka и ClickHouse могут отвечать на проверки, и API health будет возвращать 200 при отсутствии продвижения. Храните время последней успешной обработки и число последовательных ошибок, а при наличии необработанного пакета и длительной остановке прогресса возвращайте 503.

**Исправлено.** ETL хранит в памяти процесса начало обработки текущего пакета,
время последнего успешного `commit` и число ошибок подряд. Возраст пакета считается
через `time.monotonic()` и не сбрасывается при ошибках и повторных попытках.
При достижении `ETL_STALL_TIMEOUT_SECONDS` (по умолчанию 360 секунд) health возвращает
`503` и `pipeline: unavailable`, даже при исправных Kafka и ClickHouse или зависшей
операции без завершённых ошибок. Простой без пакета остаётся нормальным состоянием.
После успешного `commit` пакет очищается, ошибки обнуляются и health восстанавливается.
Health показывает возраст пакета, время после последнего успеха и число ошибок.
Проверены ошибки INSERT, DLQ и commit, зависание, повторные попытки, простой и восстановление.
В отдельном Docker/HTTP экземпляре при настоящих проверках Kafka и ClickHouse
искусственные ошибка и зависание обработки дали `200` → `503` → `200`;
для ускорения проверки порог был уменьшен до одной секунды.

Ошибка запуска Kafka оставляет producer без закрытия
https://github.com/feodal01/ugc_sprint_2/blob/main/services/ugc-events/src/main.py#L46

producer.start() вызывается до входа в try/finally, поэтому при ошибке запуска producer.stop() не выполняется. Если клиент уже успел открыть сетевые ресурсы, они останутся без гарантированного закрытия, что особенно мешает повторным запускам приложения и тестам в одном процессе. Включите запуск producer в защищённый блок и вызывайте stop() в finally, сохраняя исходную ошибку запуска.

**Исправлено.** Запуск producer и инициализация зависимостей находятся внутри
`try/finally`: `producer.stop()` вызывается при ошибке запуска, отмене и завершении
приложения. Созданный Redis закрывается во вложенном `finally`.
Если закрытие producer после ошибки запуска тоже падает, ошибка закрытия
записывается в лог, а наружу передаётся исходная ошибка запуска.
Тесты покрывают эти сценарии и ошибки инициализации и закрытия Redis.
В Docker трижды проверена искусственная ошибка после подключения к настоящей Kafka:
соединения закрыты, фоновых задач и `ResourceWarning` не осталось.
