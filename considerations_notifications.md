Уведомления построены на событиях: вышла новая серия сериала, ваш комментарий лайкнули, в кинотеатре появились новые фильмы, система напомнила про отложенные фильмы. Последние два сценария не похожи на события в привычном их понимании. На самом деле природа событий для уведомлений немного иная. Разберём эти примеры:
Вышла новая серия. Событие происходит, когда новая серия публикуется в кинотеатре. Серию может опубликовать модератор, нажав на кнопку (событие). Серия может публиковаться автоматически системой или ботами, отправив запрос в API (событие).
Ваш комментарий лайкнули. Пользователь лайкнул комментарий, поэтому запрос улетел в API (событие).
Реклама киноновинок. Опубликованы несколько новинок в кинотеатре. Как превратить несколько публикаций в одно событие? Можно раз в некоторое время проверять наличие новинок, и при их наличии генерировать новое событие — появились новинки.
Напоминание про отложенные фильмы. Кажется, что тут ещё сложнее сгенерировать уведомление: его нужно отправить, когда ничего не произошло. Ведь уведомление не про изменение списка, а про то, что список отложенного не пустой. Но фактически можно применить подход из прошлого примера: раз в некоторое время проверять список отложенного и отправлять уведомление. Но тут же есть очередной подводный камень: если список меняется, то уведомлять пользователя не нужно. Ему стоит напоминать, когда он долгое время в него не заглядывал.
Один из главных компонентов системы уведомлений — процесс (или процессы в случае масштабирования системы), который может принимать события и отправлять уведомления.

Система уведомлений
Итак, вам удалось выяснить возможные компоненты системы уведомлений: 
- API для приёма событий для создания уведомлений;
- процесс, который отправляет уведомление (воркер);
- генератор автоматических событий;
- админ-панель.
Если посмотреть на эти компоненты, можно представить, как с их помощью отправлять уведомления пользователям.
Сценарий 1. Отправка письма о лайке комментария клиента:
UGC система, которая сохраняет лайк, отправляет запрос в API о новом событии.
API передаёт информацию о событии в воркер.
Воркер отправляет уведомление пользователю.
Данные для уведомления о пользователе, комментарии или лайке передаются в API или воркер достаёт их из UGC?
Сценарий 2. Еженедельная рассылка перед выходными:
Генератор автоматических событий создаёт событие еженедельная рассылка и отправляет его в API.
API передаёт информацию о событии в воркер.
Воркер отправляет уведомление пользователю.
Данные для уведомления собирает и передаёт в API генератор событий или воркер собирает их из UGC?
Сценарий 3. Ручная рассылка от менеджера:
Админ-панель создаёт рассылку и отправляет запрос в API о новом событии.
API передаёт информацию о событии в воркер.
Воркер отправляет уведомление пользователю.
Данные для уведомления собирает и передаёт в API админ-панель или воркер собирает их из UGC?
Какие выводы можно сделать? Пункты 2 и 3 везде повторяются, а пункт 1 везде разный — он зависит от сценария. Фактически этот пункт и есть событие, которое произошло. Оно может быть создано разными кусочками системы. 
Важно: этот набор компонент приводится только как пример и не является обязательным.

Единичные события
Единичные события могут генерироваться всей системой или только системой уведомлений. Рассмотрим пару примеров.
Пример 1. На комментарий поставили лайк. Это событие создано другим пользователем. В таком случае сервис уведомлений должен узнавать об этом от сервиса UGC (или нет?).
Пример 2. Вышла новая серия сериала, который смотрит пользователь. Откуда появляется новая серия? Если её добавляет администратор, тогда он создал событие новая серия. Если серия загружается автоматически, то событие создаёт загрузчик. В таком случае сервис уведомлений должен узнавать об этом от админ-панели или сервиса загрузки (или нет?)
а Если эти события будут создаваться «снаружи», возникает вопрос: как не отправлять пользователю письма на каждый чих? Ведь за сутки пользователь может получить сотни лайков к своему комментарию, но не должен получить сотни уведомлений. Для этого можно разделить единичные уведомления на два лагеря: мгновенные уведомления и те, которые можно отложить.
Мгновенные уведомления будут отправляться, как только произошло событие, тем способом, который был описан выше: событие попадает в API, из API — в воркер, а тот уже отправляет информацию. К мгновенным уведомлениям можно отнести, например, сообщение о новой серии сериала или чек об оплате на сайте.
Уведомления, которые можно отложить, стоит отправлять не чаще определённой периодичности. Можно сделать планировщик (Scheduler) — сервис, который периодически генерирует события. Например, раз в сутки он будет генерировать рассылку самых просматриваемых за сутки фильмов.
Шедулер должен работать с базой, в которой хранятся все уведомления. Само уведомление должно содержать поля:
notification_id;
content_id;
И опционально может содержать поля:
last_update;
last_notification_send;
Идея простая: notification_id — это ID конкретного уведомления. По нему можно его отслеживать, искать, править или удалять. Далее идёт content_id — ключ для доступа к данным. По нему можно найти сами данные, к изменениям которых привязано уведомление. Например, ID сериала, в котором выходит новая серия.
Но как в таком случае отслеживать изменения? Можно хранить последнюю версию данных, которая была отправлена пользователю в уведомлении. Например, последняя серия была седьмой, а сейчас вышла новая восьмая серия. В итоге придётся хранить в базе серию №7, пока пользователям не будет отправлено уведомление о новой серии, и тогда заменить её на №8. А если последняя восьмая и в базе она так и записана, уведомление слать не нужно. Для хранения таких изменений понадобиться одно SMALLINT поле.
Так же можно посмотреть на лайки к комментарию: хранить значение лайков, которое было при последнем уведомлении, и сравнивать его с текущим с определённой периодичностью. Если число изменилось, нужно уведомить об этом пользователя.
Поля last_update и last_notification_send могут облегчить жизнь в некоторых случаях, а могут и усложнить. Например, в поле last_update можно хранить информацию о последнем изменении данных и записывать новую сразу, как только данные изменились. При формировании уведомления не проверять базу с самими данными для сравнения, а смотреть в это поле и сравнивать его с датой отправки последнего уведомления.
Хорошая оптимизация нагрузки на UGC — не трогать базу с данными при отправке. Однако поддерживать это поле в актуальном состоянии достаточно сложно и поэтому легко допустить ошибку.
Поле last_notification_send поможет вам не искать данные по отправке последнего уведомления в базе данных с историей отправки уведомлений. Это тоже можно назвать оптимизацией нагрузки и скорости работы. Однако поддержка этого поля в актуальном состоянии является не менее сложной задачей.
Хранение уведомлений в базе данных также позволит пользователю управлять ими в своём личном кабинете. Ведь не все хотят получать рекламные рассылки или уведомления о новых лайках. Не все хотят получать напоминания о сериале, если смотрят его по собственному расписанию. 
Периодические события
Периодические уведомления — это уведомления, которые должны отправляться по расписанию. Для поддержки расписания можно использовать сервис-планировщик.
Однако, никто не отменял старый добрый Cron. Это unix-программа, которую используют для периодического выполнения заданий в определённое время. По указанному расписанию она выполняет одну любую bash-команду, а bash-команда уже может запустить и сделать что угодно. С помощью Cron можно легко выполнять любые задачи по гибконастриваемому расписанию. Например, вызывать ваш скрипт еженедельно по пятницам в обед или каждую последнюю пятницу месяца вечером.

Рассмотрим каждый этап с точки зрения подготовки данных. 
Любая часть сайта, которая просит отправить мгновенное уведомление. В этом случае компонент, который генерирует событие, напрямую обращается к API системы событий. Получается, здесь есть два места для сбора данных: источник события и API. В обоих случаях это может привести к задержке работы системы. Например, при выходе новой серии (особенно если это будет http-запрос от админа) система будет очень долго собирать данные для уведомления тысячи пользователей, смотрящих этот сериал. 
Собирать данные о событии в источнике события кажется логичным решением. Однако данные о событии — это не данные для уведомления. Ведь событием может быть новая серия, а для уведомления ещё нужен email-адрес и никнейм пользователя, а также другие данные, которые не относятся к событию.
Можно собирать данные в API, ведь в нём есть весь контекст шаблонов уведомлений и необходимых для них данных. Но сбор данных может привести к задержкам в работе остальных компонентов сайта. Лучший вариант — собирать данные воркером в неспешном режиме. Отправить быстрый запрос в API системы уведомлений, которая так же быстро положит его в очередь сообщений, — простое и элегантное решение.
Также нельзя забывать, что от момента создания события до попадания его в воркер может пройти много времени, и событие станет неактуальным для пользователя. Например, вышла новая серия, событие создалось, но попало в воркер через два часа. За эти два часа пользователь мог начать смотреть или полностью посмотреть новую серию, поэтому уведомление для него уже неактуально. В таком случае можно проверять актуальность события в воркере перед отправкой уведомления: дать воркеру право принимать решение отправлять уведомление или нет.
Генератор автоматических событий, который периодически отправляет не мгновенные уведомления. Этот компонент кардинально отличается от мгновенных уведомлений. Он не сказывается на других компонентах сайта и поэтому у него есть время на работу с данными. Но выгружать данные из базы нужно аккуратно, иначе можно нагрузить базу и другие компоненты сайта начнут тормозить. 
При генерации событий он уже обладает некоторыми данными. Ведь перед генерацией происходит проверка, изменились ли данные с прошлого уведомления.
В отличие от мгновенных уведомлений, которые создают события точечно по каждому пользователю, этот компонент может создавать событие для большого числа пользователей.
Также, обладая информацией о пачке событий, можно достать данные для неё одним запросом, что будет менее накладно, чем искать данные по каждому событию отдельно.
Но всё это никак не запрещает доставать данные для уведомления в воркере. Но и никак не запрещает доставать данные до воркера и пробрасывать в API события с уже готовыми данными по нему.
В этом случае стоит рассматривать более индивидуально реализацию системы. А именно — какие задачи может принимать и обрабатывать воркер. 
Ведь генератор автоматических событий может сгенерировать ежемесячную подборку фильмов всем пользователям сайта. Но как он отправит её в API? По одному событию для каждого пользователя или одно событие, охватывающее всех пользователей? А может, пачками по 1000 пользователей?
Умеет ли воркер работать с пачками событий и отправлять из одного сообщения в очереди несколько уведомлений или нет?
Админ-панель, в которой менеджеры вручную создают рассылки уведомлений пользователям. На первый взгляд это похоже на мгновенные уведомления, ведь событие создаёт менеджер. Но, с другой стороны, менеджеры создают рассылки для группы пользователей, и получается что воркер должен отправить много уведомлений.
Сама рассылка может создаваться двумя способами: по нажатию кнопки «Запустить» (http-запрос) или в определённое время с помощью шедулера. В первом случае он должен отправить пачку уведомлений, ведь рассылка делается по группе пользователей, но при этом обладать ограничениями мгновенных уведомлений. Во втором случае сценарий полностью перетекает в генератор автоматических уведомлений с его плюсами и минусами.
