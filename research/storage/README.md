# Исследование: хранилище лайков, закладок и оценок

Исследование к UGC API (`services/ugc-api`): где хранить оценки фильмов 0…10 (10 — лайк, 0 — дизлайк) и закладки. И нужен ли для этого отдельный сервис. Сравниваются MongoDB 8.0 и PostgreSQL 16 на одном наборе из 10 млн оценок и 2 млн закладок. Пункты чек-листа задания:

1. [Выбор хранилища](#1-выбор-хранилища)
2. [Генерация данных](#2-генерация-данных)
3. [Скорость записи и чтения](#3-скорость-записи-и-чтения)
4. [Отдельный сервис или расширение существующего](#4-отдельный-сервис-или-расширение-существующего)

## Запуск

Нужны Docker и [uv](https://docs.astral.sh/uv/). Команды выполняются из `research/storage`.

```bash
docker compose up -d --wait        # MongoDB (replica set rs0) и PostgreSQL
uv sync --all-groups
uv run python -m bench.generate    # набор в data/dataset.npz и загрузка в оба хранилища
uv run python -m bench.run         # замеры, results/bench-*.json и results/report.md
docker compose down -v             # удалить контейнеры и данные
```

Адреса соединений читает `bench/settings.py` через Pydantic Settings: `MONGO_URI` и `POSTGRES_DSN`. По умолчанию используются локальные адреса стенда (`127.0.0.1:27117` для MongoDB, `127.0.0.1:55432/ugc` для PostgreSQL). Значения хранятся как `SecretStr` и раскрываются при создании клиента; явный аргумент конструктора хранилища имеет приоритет. Проверка конфигурации без запуска стенда: `uv run python -m unittest discover -s tests -v`.

Одно хранилище: `--store mongo` или `--store postgres`. Параметры нагрузки: `uv run python -m bench.run --help`. Генерация идёт около 2,5 минуты, замеры — около 5 минут.

Стенду нужно около 8 ГБ свободной памяти Docker. Основной стек проекта занимает около 12 ГБ. Если запустить стенд рядом с ним в VM Docker Desktop на 16 ГБ, ядро VM при нехватке памяти убивает `mongod`. На время замеров основной стек останавливается командой `docker compose stop` в корне репозитория, а после замеров запускается снова командой `docker compose start`.

| Файл | Что внутри |
| --- | --- |
| `compose.yaml` | стенд: `mongo`, одноразовый `mongo-init`, `postgres` |
| `bench/dataset.py` | детерминированный набор данных (SEED 42) |
| `bench/settings.py` | настройки соединений из окружения |
| `bench/stores.py` | схема, индексы, загрузка и запросы для каждого хранилища |
| `bench/generate.py` | генерация и параллельная загрузка |
| `bench/run.py` | нагрузочное тестирование чтения и записи |
| `bench/report.py` | таблицы Markdown из результатов |
| `results/` | результаты прогона, описанного ниже |

## Стенд

У обоих хранилищ одинаковые лимиты: 2 CPU и 4 ГБ памяти. Кэш сопоставим: кэш WiredTiger 1,5 ГБ против `shared_buffers` 1 ГБ; остаток лимита у обоих уходит под страничный кэш ОС.

MongoDB запущена как replica set из одного узла. Запись подтверждается после попадания в журнал, как `COMMIT` в PostgreSQL. Standalone `mongod` отвечает раньше сброса журнала и выглядел бы быстрее за счёт надёжности. Replica set инициализирует отдельный контейнер `mongo-init`, а не healthcheck: запуск `mongosh` занимает около 270 МБ памяти и секунду CPU из лимита хранилища.

Запросы повторяют UGC API, индексы в обоих хранилищах одинаковые:

| Сценарий | Запрос | Индекс |
| --- | --- | --- |
| Список лайков пользователя | `user_id`, `score = 10`, новые первыми, 50 штук | `(user_id, score, updated_at desc)` |
| Список закладок | `user_id`, новые первыми, 50 штук | `(user_id, created_at desc)` |
| Лайки, дизлайки, число оценок и средняя оценка фильма | один агрегирующий запрос по `film_id` | `(film_id, score)` |
| Поставить или изменить оценку | upsert по `(user_id, film_id)` | уникальный `(user_id, film_id)` |

Планы проверены через `explain`. Для списков оба хранилища используют индекс, а документ или строку читают по ссылке из индекса: MongoDB — `IXSCAN → FETCH → LIMIT`, PostgreSQL — `Index Scan`. Сводку фильма оба считают только по индексу, не читая документов: MongoDB — `IXSCAN → PROJECTION_COVERED → GROUP` на движке SBE, PostgreSQL — `Index Only Scan`.

Клиент — Python на хосте (PyMongo 4, psycopg 3), по одному соединению на процесс. В задержку входит сеть Docker Desktop и разбор ответа драйвером, как у настоящего сервиса.

## 1. Выбор хранилища

**Выбрана MongoDB.** Для UGC API она уже работает в проекте как шардированный кластер: два шарда по три реплики. Причины выбора:

- **Горизонтальное масштабирование из коробки.** Оценки и закладки растут вместе с числом пользователей. В MongoDB шардирование встроено: `mongos` сам направляет запрос по ключу шарда и перераспределяет чанки. PostgreSQL для этого нужен Citus или шардирование в коде сервиса.
- **Документная модель рецензий.** Рецензия хранит текст, оценку автора и счётчики голосов, и её схема будет меняться. Счётчики меняются атомарно через `$inc` без миграций.
- **Скорости хватает.** На одном узле с 2 CPU списки и сводка отвечают за единицы миллисекунд: p99 не выше 9 мс, кроме сводки популярного фильма. Новый лайк виден в чтениях через 9 мс по медиане.

**Что показали замеры.** На одном узле PostgreSQL быстрее во всех сценариях: в 1,5–5 раз по задержке одного клиента и в 1,7–8 раз по пропускной способности. Особенно заметна разница на агрегате по популярному фильму: 73,8 тыс. оценок, 1 378 против 166 запросов/с. Если бы выбор делался только по скорости чтения на одной машине, выбор был бы PostgreSQL. MongoDB выбрана с учётом масштабирования. Этот стенд её выгоду не показывает: здесь один узел без шардов.

**Слабое место любого из вариантов — сводка популярного фильма.** Запрос пересчитывает все оценки фильма, и время растёт линейно с их числом. Дальнейший шаг — хранить счётчики (`likes`, `dislikes`, `count`, `sum`) в документе фильма и менять их через `$inc` при записи оценки. Тогда чтение сводки — чтение одного документа.

LSM-хранилища (Cassandra, ScyllaDB, ClickHouse) не рассматривались. В них быстрая запись, но медленнее чтение. Для лайков главный критерий — чтение, и оценку нужно менять и удалять точечно.

## 2. Генерация данных

`bench/generate.py` создаёт набор один раз и сохраняет его в `data/dataset.npz`. Оба хранилища загружают одни и те же данные. Генератор детерминирован (SEED 42). Каждая пара «пользователь — фильм» встречается один раз, как в уникальном индексе.

| Сущность | Объём | Распределение |
| --- | --- | --- |
| Пользователи | 100 000 | число оценок: медиана 89, максимум 1 560 (степенной закон, показатель 0,3) |
| Фильмы | 10 000 | число оценок: медиана 546, максимум 73 804; 100 популярных — от 8 026 (показатель 0,7) |
| Оценки | 10 000 000 | 35 % лайков (10), 15 % дизлайков (0), остальные 1…9 поровну; даты за два года, изменение — до 30 дней после создания |
| Закладки | 2 000 000 | на пользователя: медиана 18, максимум 396 |

Загрузка идёт шестью процессами пачками по 50 000: MongoDB — `insert_many`, PostgreSQL — `COPY` в бинарном формате. Индексы строятся после загрузки. PostgreSQL затем выполняет `VACUUM ANALYZE`: так планировщик получает статистику, а `Index Only Scan` — карту видимости.

| Хранилище | Оценки, с | Закладки, с | Индексы, с | Оценки: данные, МБ | Оценки: индексы, МБ | Закладки всего, МБ |
| --- | --- | --- | --- | --- | --- | --- |
| MongoDB | 34 | 6 | 36 | 724 | 771 | 250 |
| PostgreSQL | 8 | 2 | 19 | 806 | 1 019 | 303 |

MongoDB хранит данные компактнее: WiredTiger сжимает данные snappy, а индексы — префиксным сжатием.

## 3. Скорость записи и чтения

`bench/run.py` делает три замера. Пользователи и фильмы выбираются случайно по равномерному распределению. Популярный фильм — случайный из ста самых оцениваемых.

**Один клиент.** 2 000 последовательных запросов после 50 прогревочных.

| Сценарий | MongoDB p50 | MongoDB p99 | PostgreSQL p50 | PostgreSQL p99 |
| --- | --- | --- | --- | --- |
| Список лайков пользователя | 2.29 | 8.60 | 0.67 | 1.80 |
| Список закладок пользователя | 0.79 | 2.50 | 0.50 | 1.60 |
| Лайки, дизлайки и средняя оценка фильма | 1.01 | 5.57 | 0.46 | 1.61 |
| То же для популярного фильма | 4.97 | 23.21 | 1.09 | 3.56 |
| Поставить или изменить оценку | 2.06 | 4.21 | 0.44 | 1.31 |

Время в миллисекундах.

**16 клиентов одновременно.** 16 процессов выполняют один сценарий 15 секунд. Замер у всех начинается одновременно, после прогрева.

| Сценарий | MongoDB запросов/с | MongoDB p99, мс | PostgreSQL запросов/с | PostgreSQL p99, мс |
| --- | --- | --- | --- | --- |
| Список лайков пользователя | 1 439 | 77.84 | 6 059 | 49.15 |
| Список закладок пользователя | 7 670 | 29.55 | 12 954 | 4.62 |
| Лайки, дизлайки и средняя оценка фильма | 2 037 | 73.23 | 11 521 | 23.41 |
| То же для популярного фильма | 166 | 300.40 | 1 378 | 81.30 |
| Поставить или изменить оценку | 2 462 | 66.89 | 7 408 | 22.18 |

При 16 клиентах на 2 CPU запросы стоят в очереди, поэтому p99 растёт у обоих. Показатель этой таблицы — пропускная способность.

**Чтение данных в реальном времени.** Восемь фоновых клиентов непрерывно читают все четыре сценария. В это время 500 раз повторяется цикл:

1. новый пользователь ставит лайк случайному фильму;
2. сразу после подтверждения записи читаются список его лайков и сводка фильма;
3. цикл заканчивается, когда фильм есть в списке, а лайков в сводке на один больше, чем до записи.

| Хранилище | Фоновых чтений/с | Запись p50 | Запись p99 | Виден p50 | Виден p99 | Попыток чтения, max |
| --- | --- | --- | --- | --- | --- | --- |
| MongoDB | 560 | 4.07 | 89.08 | 8.71 | 96.07 | 1 |
| PostgreSQL | 1 981 | 1.39 | 260.54 | 3.18 | 262.75 | 1 |

Время в миллисекундах. «Виден» — от начала записи до чтения, в котором лайк есть в обоих запросах.

В обоих хранилищах лайк виден с первой попытки чтения: запись и чтение идут в primary, и подтверждённая запись сразу видна следующему запросу. Время появления лайка — это время записи плюс одно чтение. Хвост p99 у PostgreSQL выше. Фоновые клиенты успевают сделать у него в 3,5 раза больше запросов, поэтому запись чаще ждёт CPU. Контрольная точка WAL тоже могла дать хвост, отдельно это не проверялось. Для пользователя хватает обоих вариантов: лайк виден меньше чем через 0,3 с даже в худшем случае.

**Ограничения замеров.** Один узел на ноутбуке (Docker Desktop, macOS, Apple Silicon): диск и сеть общие с хостом. Клиенты — Python-процессы на том же хосте, поэтому часть CPU уходит на драйверы. Абсолютные числа на серверах будут другими. Сравнение честное: у хранилищ одинаковые лимиты, данные, индексы и гарантии записи.

## 4. Отдельный сервис или расширение существующего

Существующий сервис — UGC Events. Он принимает события просмотра, отвечает `202` и публикует их в Kafka, а UGC ETL складывает их в ClickHouse. Лайки, закладки и рецензии реализованы **отдельным сервисом UGC API** со своим хранилищем MongoDB.

### Почему отдельный сервис

1. **Разный профиль нагрузки.** UGC Events только принимает события и ничего не читает. UGC API выполняет CRUD и синхронно отдаёт данные, главный показатель у него — скорость чтения. Пользователь ждёт, что поставленный лайк сразу появится в списке. Требования к задержкам, масштабированию и ресурсам у сервисов разные.
2. **Хранилище всё равно другое.** ClickHouse рассчитан на аналитику и массовые вставки. Точечные `UPDATE` и `DELETE` в нём выполняются как мутации, а `ReplacingMergeTree` схлопывает дубли только при слияниях. Лайк, закладку и рецензию нужно изменять и удалять сразу. Если добавить MongoDB в UGC Events, в одном сервисе окажутся два хранилища. Отдельный сервис использует одно хранилище, выбранное под его задачи.
3. **Изоляция отказов.** Готовность UGC Events зависит только от Kafka. Если в него добавить MongoDB, её недоступность ухудшит health сервиса и может остановить приём событий просмотра. Отдельный сервис деградирует независимо: сбой MongoDB не мешает собирать события, а сбой Kafka не мешает ставить лайки.
4. **Раздельный жизненный цикл.** Каждый сервис в `services/*` собирается, деплоится и масштабируется отдельно, со своими линтерами, тестами, Sentry и логированием.
5. **Невысокая цена.** Стек тот же, что у UGC Events: FastAPI, pydantic-settings, локальная проверка access JWT. Паттерны переносятся из соседнего сервиса в том же репозитории.

### Какие проблемы у отдельного сервиса

- Ещё один контейнер, маршрут в Nginx, набор тестов и шаг CI.
- Код проверки JWT и настроек повторяется в UGC Events и UGC API. Общая библиотека стоит дороже, пока сервисов два.
- Если лайки и рецензии понадобятся аналитикам в ClickHouse, UGC API придётся дополнительно публиковать события в Kafka.
- Кластер MongoDB требует отдельной эксплуатации: девять `mongod`, два `mongos`, резервные копии и мониторинг.

### Когда подошло бы расширение UGC Events

Расширение оправдано, если новая функциональность закрывается уже выбранным хранилищем сервиса. Тогда не нужен новый деплой, а код авторизации и настроек переиспользуется. У UGC Events такого хранилища нет: он пишет в Kafka, а ClickHouse наполняет UGC ETL. Проблемы расширения:

- Для CRUD не подходит ни Kafka, ни ClickHouse. Пришлось бы добавить MongoDB или PostgreSQL в сервис сбора событий, и хранилищ стало бы два.
- Отказ хранилища лайков влиял бы на приём событий просмотра.
- Приём событий и чтение лайков пришлось бы масштабировать вместе, хотя нагрузка у них разная.
- Сервис с двумя ответственностями сложнее тестировать и выкатывать: изменение лайков требует релиза приёма событий.
